## Anthropic 在 harness 上做的减法

好，那我先帮大家 recap 一些 Anthropic 最近做的事情。为什么我们要谈 Anthropic 呢？我想请现场大家举一下手，今天有多少人用的 Claude Code？OK，已经证明了很多事情，基本上 80% 以上的人今天都用过 Claude Code。那我们来看一下，因为模型变得越来越强——Opus 5.5 出了，Fable 5.5 也马上要出了——Anthropic 在 Claude Code 的 harness 上做了哪些事情？ [seg 1535–1540]

第一件事情，Anthropic 曾经非常荣幸地宣布，他们砍掉了 harness 里面 80% 的系统提示词。曾经有很多系统提示词被我们这个行业的人奉若圭臬：有这个提示词，你的 agent 就能运行得更加稳定；有这个提示词，它就能够更好地和你沟通，明白在工具调用之前应该跟你说什么。但是这些能力慢慢地都已经被模型所内化，我们的提示词变得越来越简单，越来越少。 [seg 1541–1545]

第二个是最近一个非常重要的观察：Anthropic 发了一个博客，大意是"一个非常强大的 single agent，可能比你原来设计的非常精巧的 sub-agent system 要强非常多"。这是一个非常值得深思的问题，因为拆 sub-agent 这个事情也是 Anthropic 先告诉我们的，说拆 sub-agent 可以让你的 context 更好，把更宝贵的东西留下来。那为什么到今天这个推论又被推翻了呢？就是因为模型变得越来越强了，模型能够明白在什么样的情况下做什么样的事情，我们的一些工程上的手段是完全可以去除掉的。 [seg 1546–1551]

第三件事情，Anthropic 一开始推出 Claude Code 的时候，它有一个叫做 to-do list 的功能，当时大家就说，OK，你做一个 harness 怎么能没有 to-do 呢？后来它自己把 to-do 给去除了，加了一个叫 plan mode 的东西。然后它最近又做了一件事：plan mode 也不要了，没必要做 plan。为什么呢？因为我们的模型已经学会了 plan、execute and verify 这样的一个 loop。在这样的情况下，你就不需要再给用户提供一个叫做 plan mode 的命令，模型已经可以自己做。 [seg 1552–1560]

那我们在 MiniMax 内部推演，觉得到后面可能会再被从 harness 当中去除的一个高频使用的功能是什么？就是 goal 这个命令。因为在我们模型训练的整个过程当中，我们要训练模型明白：我们要去完成这个任务，一直到能够把这个任务的最终结果交付到用户手上。所以不需要你后面再去 /goal，去告诉它你就是要去完成这个目标——你的每一个任务就应该是一个目标。这是我们觉得的一个技术趋势。随着模型变得越来越强，你的 harness 应该是动态的，而且要慢慢地去审视你原来奉若圭臬、觉得非常宝贵的一些工程或者 prompt 上的 trick，是不是应该做减法，做一些删减。 [seg 1561–1568]

## harness 要决定的四件事

所以在这里我想跟大家说一个我个人的技术理念：我觉得一个 harness 要决定四件事情。在每一个 part 上，你都需要去看一下我们需要保留什么，什么事情其实是要随着模型能力的变化不断迭代的。 [seg 1569–1570]

第一个叫做 harness 要让模型看到什么，what it sees。在 harness 的设计过程当中，最重要的事情就是 context。在 context 里面，我们还会区分：OK，我要约束模型的行为，我要告诉模型什么时候你应该做什么，什么时候不应该做什么；我的工作流长什么样子，你应该先做什么，再做什么。在某些情况下这个事情是对的，但是随着模型能力变得越来越强，它吸收的知识越来越多，它的强化学习做得越来越好之后，很多事情可能就没有必要了。这里我举一个例子，应该是下半年以后开始慢慢出现一个技术浪潮，叫做"without skills is better than with skills"。就是为什么很多人开始说你应该对你的 skill 做一些必要的减法：很多我们日常都在用的 skill，你用它的时候会发现消耗的 token 更多，但它并没有给你带来更好的效果，反而没有它会变得更好。这就是在 harness 层面你需要考虑的：你的 context 需要怎么样随着模型能力的变化不断去调整。 [seg 1571–1585]

第二个叫做 what it can do。随着模型能力不断变强，我们的 harness 作为整个模型连通数字和物理世界的手和脚，决定了我们的 agent 能够干什么，what it can do。随着模型能力不断变强，我们跟物理世界交互的方式也应该不断发生变化。 [seg 1586–1590]

第三个叫做 how it continues。这个命题的原因是，我们现在 LLM 本身的 transformer 架构没有办法实现真正的无限上下文，而你和一个 agent 不断地聊天、不断地执行任务，本质上 harness 承担了一个非常重要的职责，就是怎么样让人有一个无限上下文的体验。在这个过程当中，我们做过非常多的工作：怎么样去拆 sub-agent，怎么样让 context 的 isolation 真正有意义；还有怎么去做一个非常好的 compaction，通过 compaction 留下必要的信息，让我的会话能够不断进行下去。但慢慢地我们发现了一些趋势：现在的模型开始倾向于明白，只要你告诉它 context 快满了，模型会自己说，好，我现在开始 hand off 这个任务，我要把它写到一个本地文件里面去。通过这种 hand off 的效果，可能会比你之前所有设计巧妙的 compaction 都要好。 [seg 1591–1601]

还有第四件事，叫 how it's proven〔?〕。就是我们的 harness 不仅仅要帮 agent 去做事情，或者说作为 agent 的一部分去做事情，还要能够验证这个事情到底做得怎么样。这是 harness 非常重要的一部分，而且我认为是最重要的一部分。 [seg 1602–1605]

所以在这里，我的想法是：我们所有的 judgment，我们都要认为是可变的。有一些东西是不变的，我认为不变的东西是两件事：一件是对 token 效率孜孜不倦的追寻，一件是对工作效率，或者叫任务完成率孜孜不倦的追寻。我们永远都需要保留那些能够让 token 消耗得更少、但能够让任务完成得更好的魔法。 [seg 1606–1609]

所以我觉得对于每一个功能，我们都需要去问四个问题：如果你把它删掉，会让这个事情变得更坏吗？你做的这个功能对于模型本身来说是否有意义？如果这个功能出错了，你怎么样能够去 undo 或者 redo 它？你的这个产品功能，你是怎么去设计它整个的 evaluation 的？在我们 MiniMax Code 的团队，如果没有人能够回答清楚这些问题，一般都会被我 push back：首先你需要给我一个你的 evaluation 的 process，不然的话这个事情我们可能还需要下来再想想。 [seg 1610–1615]

## Case study

OK，因为时间关系，我就快速给大家带来一些我们内部的 case study。这部分可能会比较偏 tech，但是我希望大家可以跟着我一起过一下这些 case。 [seg 1616–1617]

首先，在 2025 年有一个非常大的技术浪潮，就是大家都开始广泛使用 MCP，或者说广泛地把一些外部的 SaaS 之类的服务接入给我们的 agent。这也可能带来一个问题：我们注入的 MCP 越来越多，就会让我们整个的 tools 越来越多。MCP 有个问题，就是它在 agent 的运行过程当中是动态加载的，如果你直接全部放到 agent 的工具列表里面去，因为网络的原因，你的工具列表可能会产生变化，你也可能会增加新的 MCP 进去，那你的前缀缓存是没有办法严格保证的。这样的话，你的 agent 跑起来可能就会变得非常贵。所以我们做的一件事情叫做 discovery inside a tool call：我们把所有这样的 MCP 工具全都放到了一个 connector 的 CLI 里面去，通过在这个 CLI 里面做渐进式披露的方式，让你的 agent 去发现工具、调用工具、执行工具。通过这样的方式，保证整个前缀缓存是能够严格保证的。这是我们的一个思考：因为我们发现了这个问题，我们想让整个的 token 效率变得更高。这是一个 case study，其实业界很多同行也在做。 [seg 1618–1631]

第二个 case study，简而言之是三个字母，叫做 PTC，programmatic tool calling。这也是我认为现在 harness 圈子里面大家讨论得特别火热的一个词。大概是在上个 Q，Codex 完成了一次升级，把它 harness 的 default 行为变成了 programmatic tool calling，也就是 PTC 的行为。我给大家简单介绍一下：随着 coding agent 本身写代码越来越厉害，如果我们还要循环往复，不断让 LLM 去输出应该调用什么工具，好像显得有一些笨，有一些不讨巧。那最讨巧的方式是什么？让 LLM 一次性输出一段代码脚本，这个脚本可以把我这个时候执行这个任务要用的 tool call 全都放在里面，这样我的效率更高：我节省了和 LLM 之间循环往复的沟通，还节省了中间不必要的 tool result 所占用的 token。这就叫做 PTC：通过写一些调用工具的脚本，放在沙箱里面执行，可以更好地提高我们的 token 效率，而且可以通过代码本身的并发和异步能力，执行得更快、更强，有更高并发的特性。 [seg 1632–1648]

大家可能都看过 Codex 一个非常有意思的例子，就是 Codex 的 browser use 浏览器操纵可以弹钢琴。但如果你用其他非 PTC 的 agent 想复刻弹钢琴，你会觉得这不是在弹钢琴，它是很慢很慢才弹出来的。这就是为什么当时业界都开始聊 PTC。我们怎么样让用户有一个更心流的体验，让他觉得 agent 做事情可以做得更快、更强，而且 token 消耗更少，还是围绕这个命题。这是第二个 case study。 [seg 1649–1653]

第三个 case study 是我们这个圈子里很容易犯的一个错误。你的用户很有可能会做一件事，叫做"帮我复刻这个 GitHub 仓库"，或者"帮我把它跑起来"。他很多时候要做两件事：一件是 git clone 这个仓库，第二件是安装依赖。在第二件事情上，很有可能安装依赖就要超过 5 分钟，甚至要十几分钟。在这样的情况下，你怎么样能保证你的前缀缓存？那就要用到后台任务，把它转到后台。你怎么样把这种长的前台命令自动转后台，并且让 agent 非常好地感知到它转了后台，以及最后它的结果又能再回给你的 agent？这也是我们在这中间发现的一个非常有收益、也非常有意思的点。 [seg 1654–1662]

然后刚刚也提到，更多的 sub-agent 也不一定是更好的，因为你需要有一个非常清晰的上下文，还要有一个非常好的 evaluation benchmark。我们通过最近的 benchmark 发现，在我们的模型上面的表现也确实是这样：更多的 sub-agent 很多时候反而会造成 token 无意义的消耗。所以我们觉得 sub-agent 的开启应该是克制的，并且随着模型能力变强，这个事情是需要不断重新思考的。 [seg 1663–1667]

## 珍惜你的 context

OK，最后我想说，我们对待 LLM 的 context，或者说 agent 的 context 的态度，应该像我当年在北大计算机系学习计算机原理时老师说的那句话一样。老师会说："你对待你的内存要非常地珍惜。"所以我想跟大家说，对待你 agent 的 context 得非常地珍惜。你放进去的所有东西，都需要考虑它的信噪比，都需要考虑这个东西是否应该被放进去；如果不放进去，是不是也可以达到同样的效果？要实实在在地不断去思考和问自己这些问题，只有这样，你才能让你的 context 变得更加凝练，变得更加 efficient 一点。这里放了 context 的四层 layer，我也不赘述了，讲的是我们怎么样去做 global memory、project memory，以及怎么和 working context 做一些协作。 [seg 1668–1676]

## Harness engineering 是一门实验科学

OK，所以最后我想说，harness engineering 从来都不是我们直接把 idea 给到 agent、让 agent 去实现这样一个简单的流程。它是一个非常复杂的实验科学。我非常想说的一件事情是，我非常感谢我们当代的 AI agent，让我们真正把 computer science 变成了一门 science，而不是一门 engineering。因为 science 跟 engineering 的区别是，science 需要先提出假设，然后去验证，最后再去回答问题。 [seg 1677–1684]

在这里我想花最后的时间重点讲两页 slide，是我昨天晚上想了很久之后写的这两页：在现在做实验、或者说实现一个东西变得越来越 free 的情况下，什么东西是非常珍贵的？我昨天想了很久，总结了三个。 [seg 1685–1689]

第一个是好奇心。你在 AI 这个行业必须得保持十足的好奇心，只有当你有好奇心，你才会愿意去体验更好的产品、更优秀的设计，以及去探索你的 agent 可以做得怎么样、越来越好。 [seg 1690–1691]

第二件事情叫执行力。我见过太多的朋友跟我说：OK，这个 idea 不就是我三个月前跟你说过的吗？我一般都会反驳他一句："为什么三个月前做的人是他，而不是你呢？"所以我想说，执行力很重要，但执行力并不是说你做一个 0 到 1 的事情，执行力是说你做完 0 到 1 之后，还愿意把 1 到 100 给做了。因为 agent 做 0 到 1 真的太快了，但 agent 做 1 到 100 是需要人做非常多的 decision 的。 [seg 1692–1697]

第三件事情，是要真正用科学的方法跟科学的素养去做事情。无论是做对照实验、做消融实验，还是用假说演绎的方法，用这样最质朴的科学方法去做事情，就能够引导你的模型的迭代、你的 harness 的迭代，或者你的 agent 产品的设计。只要你能 scale up 你的实验数量，你就能 scale up 你整个产品、整个模型、整个迭代的效率和效果。 [seg 1698–1701]

所以我想跟大家说的是，在我们真正的产品研发、模型研发，还有整个 AI 的旅程里面，最重要的事情是带着你的好奇心，去提出你对这个世界的那一份假设。而且在和 AI 交互之前，就开始去想我怎么样去解决这个假设，或者说去验证这个假设，然后让 AI 去充当你假设验证的执行者和调度者。最后带着这样一个 loop 去看看，我想做的这个实验，在和 AI 一起之后到底有没有达成我的目的。如果没有达成，可能是我的假设有问题，也有可能是我想解决的这个问题本身就不存在。通过这样不断的 loop，会加深你 critical thinking 的能力。 [seg 1702–1709]

我现在越来越觉得，如果 AI agent 只是让人变得更累了，那不是我们创造 AI agent 的本质。AI agent 的本质是要让我们把时间花在更值得花时间的东西上。我个人觉得更值得花时间的东西，就应该是让你有好奇心，让你有欲望去不断探索，让你觉得这个东西能让你孜孜不倦——而这就是我们这个世界最重要的命题。 [seg 1710–1714]

所以我想说一句话：如果你真的对 AI 充满热情，你就应该先去提出在你现在这个产品上你最想做的事情是哪些，你的用户可能会非常需要什么东西，而不是说这个世界上某一个和我相似的产品做了什么，所以我也要去做。感谢大家，这就是我今天所有的分享，谢谢。 [seg 1715–1717]
