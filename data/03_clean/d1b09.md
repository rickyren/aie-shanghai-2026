Welcome. I'm talking about how we rebuilt Atlas. Atlas is an open-source application developed by OHDSI, an organization in observational health data research. The talk is not about the application itself, but about how we used agents to build the application and to verify its correctness — basically, to look into the problem of how you actually verify generated code without reviewing every single line of it. [seg 974–980]

## What is Atlas

Just to give a little bit of background on what Atlas is: on the left side you're seeing Atlas version 2, the old version of Atlas, which was developed with Knockout.js and was used for about a decade. We rebuilt it from scratch in Vue.js. We not only exchanged the tech stack — one of the challenges was that the application was hard to use, especially for new users, so we also wanted to change the visual design, the user flow and the user experience. [seg 981–987]

To go one level deeper in understanding Atlas: the researcher would like to answer research questions by looking at health records and building a patient cohort, a group of patients. He can visually create these filters in the Atlas UI. The Atlas UI sends a JSON to the backend, the WebAPI, and that's translated to SQL and queries the database. So if there's a bug that changes the JSON, it immediately leads to the wrong patient cohort, and the research question cannot be reliably analyzed. [seg 988–994]

What we did here: we rebuilt Atlas from scratch in Vue, and we also renewed the tech stack of the WebAPI. I will talk especially about the rewrite of the Atlas UI, as I think that's the more challenging part, since it involves the UI and not only a well-defined backend. [seg 995–997]

So if you look at what changed: when we rewrote it, it was nearly 300 PRs, about 150,000 lines of source code〔?〕 and 150,000 lines of test code〔?〕. And it was a small team: I started the rewrite and one other engineer joined me. So in the end it was too much code to really manually review every line. [seg 998–1002]

What does that mean? Atlas 2 actually didn't have a large test code base, so that also needed to be developed — Atlas 2 just had five unit tests〔?〕. Therefore we needed to develop the harness as well, and that was done alongside building the actual product. And of course we used the agents to write the tests as well. [seg 1003–1009]

## The harness

I will now talk about what the harness is that we built for rewriting the application. I think there are two parts to this. One is around the agent: we have the instructions, skills, permissions and sub-agents. Here we mostly used existing open-source and other software like Claude Code and skill frameworks. But especially for verification, I think you need to have the harness around the code. There we have, on one side, the specs to define what needs to be changed. Then the oracle, which is the legacy application Atlas 2 that you can compare our application to. The gates — that's the CI gates, the tests and other checks. And then visual verification via screenshots. [seg 1010–1019]

So how do these four components play together? You first look into the specs and define what you would like to do, give that to the agent that is generating the code, and then the other three components are there to validate the code: check it against the previous application Atlas 2, have the tests check the correctness, and do a visual validation — before the human does the final check. [seg 1020–1026]

### Specs

Now I'll go into a little more detail regarding these four gates. The specs, I think, are nothing new. In the past, I think, you wanted to give agents quite detailed context about what needs to be implemented. Nowadays, with newer LLMs, I think it's mostly about really well-defining what needs to be done, what needs to be achieved, what is actually considered done — basically an acceptance test for the task. [seg 1027–1031]

As we did the rewrite and really changed the whole UI, it actually starts a little before the spec: you need to define what the application should look like. For that, we did iterations letting the LLM create mockups for the specific changes, then selected a mockup, and maybe did another iteration where we refined the mockup based on feedback. On one side, that way you can make sure that what you wanted to change really looks the way you want. On the other side, it gives the AI the possibility to bring in ideas on how the usability can be improved. [seg 1032–1040]

### Comparing with the legacy system

So now you have the specs and the mockups, and you give them to the agents to generate the code. Now it's about validating that what was implemented is correct, or is what you wanted. The first component there is comparing it to the existing system. This is one example of what we did: there are over 1,000 published cohort definitions in the OHDSI network〔?〕, and these are validated. We took these, uploaded them into the front end, imported them, exported them, loaded them, modified them, and ensured that they're still correct — and by that ensured that Atlas 2 and Atlas 3 come to the same result. [seg 1041–1052]

So why did we do that, and what did we find by doing it? It actually started with a bug in the converter, where the result was not the same. Instead of just solving that specific issue, we thought about how we can ensure that in the future the agents detect these kinds of issues automatically. By running that, we discovered additional bugs in the converter, but also additional problems in how the structure was represented in the front end. [seg 1053–1060]

### Tests and mutation testing

The next component is the testing framework. Here we have our CI gates: type checks, linting, unit tests, end-to-end tests. In addition to that, because the agent also wrote the tests, we looked into how we actually ensure that the tests test the source code correctly. On one side, we had some static checks, because we noticed that the agents are sometimes cheating in a way and creating tests which are always true. On the other side, we did mutation testing. [seg 1061–1068]

So what is mutation testing? Mutation testing means that you modify the source code: you make small modifications, you introduce small bugs, and check whether the tests fail when these bugs are introduced. Here is one example on the left side: for one component we had a test coverage of nearly 90%, so it looked great. But when we did the mutation testing, we noticed that less than 15% of the modifications were caught by the tests. We used that to improve the testing via the agents, and now across the whole repository we have around 98% code coverage, and above 70% of the mutation tests are succeeding. [seg 1069–1079]

### Visual verification

Then the last component is the visual check. Once the tests are passing, you are somewhat confident that it is correct, but there is still a certain class of problems you might not catch. For that, we let agents really go through the application, take screenshots, interpret the screenshots, and check whether what's in the screenshot is actually what we expect. [seg 1080–1084]

## What stays human, what the harness owns

So what does that mean? What stays on the human side and what can be done by the harness? What stays human is the intent: you need to clearly specify what you would like to do, and when it is considered done. Then you have choices. Especially if you look at UI code, I think a lot of it is about taste — there's no single wrong and correct answer. So there we used the mockups, for example, and also for architecture you can let the agents suggest options and then choose. The user experience is another part — I already mentioned that UI has a lot of taste component. For us it was also the case that we still had some influence on the shape of the source code, where we noticed that certain suggestions of the agent were maybe not that future-proof, and we influenced it. [seg 1085–1102]

What the harness owns is the contracts: linting, type checks, all that can be handled automatically. Our comparison to the legacy system — we can do these fidelity checks. Then the testing, and checking that the tests are actually meaningful — that can be done by the harness. And also visual verification. [seg 1103–1108]

## What the harness caught, and the gaps

So where was our harness successful, and what gaps do we still have? We now detect fake tests〔?〕, which sometimes happens with AI. And even more important are the mutation tests, where the test is still working and still doing something, but it's not really completely checking the application. In Vue.js we also have compiler macros, which are situations where we cannot do the mutation testing, so that's at least something we highlight. And for new code, we ensure via code coverage reports that new code always gets tested. [seg 1109–1119]

What our harness is still missing, and what is currently still manual, is environment assumptions. We had bugs where the time zone played a role, or where different browsers gave different results; currently our CI is one environment that we test well. Then, I think an important part is always: if you have these kinds of gates and tests, you need to make sure they fail reliably. We had situations where something was timing out, and that's not automatically noticed by the harness. Also, the infrastructure can be unreliable: there are situations where websites are not reachable in the CI or things like that, and therefore there are failures, and the harness will not solve these automatically. I think most of these can, with additional effort, also be integrated into the harness. [seg 1120–1135]

The last part is probably the most important: domain judgment〔?〕. We also had bugs where the calculation was wrong. If you asked the AI whether that result is correct, I think it would catch it. But I think it's quite hard to reliably define it in a general way so that these kinds of situations always get caught. [seg 1136–1140]

## Managing community feedback with agents

That leads us to this: as it's an open-source project, we also get quite a bit of feedback. We got 163 issues, which is still manageable, but for two people already quite a lot. To manage the feedback, we also use agents. The agents scan the repository daily for new issues, check against a certain knowledge base, and then draft a reply, or create a PR if it's a small bug. So we just need to review the reply or the PR, and that way we can react quite quickly to feedback from the community. [seg 1141–1151]

## What's still to improve

So what is there still to improve? One I already mentioned: if you have certain checks, certain gates, you need to make sure they're reliable and that it gets detected if they fail. Then in the spec, I think it's good to make clear what's actually considered done, when it is really completely implemented. Another point is the environment: with different time zones, and especially for front end, different browsers, there's a lot of variation you need to handle. Then if you do visual verification and take screenshots, you also need to instruct the agent on how to actually verify that the screenshot is correct — what's actually correct there. And if you can do a deterministic check, if you can write a test, I think that's always more reliable over time than letting the LLM decide whether something is correct. [seg 1152–1166]

I think LLMs got quite far, and for certain classes of problems it's quite easy in a way to let the LLM generate the code and verify it. If you already have a reference implementation, all the input is structured, you have a lot of sample inputs, and already a very good testing framework, then using LLMs to generate the code and validate that the new implementation matches the old implementation is quite manageable. [seg 1167–1172]

It gets more challenging if you really start with a completely new product, a completely new solution. There I think it's a lot about specifying, at the right level of detail, what the solution should look like. I think that's the quite challenging part. If you involve UX, UX is also taste to a certain extent — there's not a right one and a wrong one. So quite often it makes more sense to have the human more involved in making the decisions. Another thing is that if certain behaviors only show up in a production system, that also makes it harder to test. It doesn't mean it's impossible, but it makes it more difficult, and you need to put in additional effort to build the harness around it and define it. [seg 1173–1184]

## Takeaways

So the three things I would say are important. One is still defining the problem well — what you want to implement, defining the spec at the right level of detail. Then, for the automated tests: if you do not have tests in an existing implementation, or you implement it from scratch — I think LLMs tend to sometimes write tests that are not that meaningful, so that includes testing the tests, in a way. And if possible, if there is an existing legacy application, that helps a lot in comparing against the legacy system. Even if you're not reimplementing an existing application, for parts of the problem it may make sense to look into whether there's a reference implementation you can compare to, which already specifies in a lot of detail what you would like to achieve. [seg 1185–1196]
