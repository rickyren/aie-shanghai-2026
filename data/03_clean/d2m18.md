在调试的时间，我可以先给大家介绍一下 LanceDB。LanceDB 是一家北美的创业公司，我们的目标就是去构建一个多模态的数据湖。我们公司的愿景，是帮助大模型公司更好、更快地基于正确的数据去构建他们的数据飞轮，从而构建出更好的模型，进而间接地推动整个人类的 AI、AGI 的发展。我们今天想分享的主题，就是关于机器人数据，它到底为什么会需要一个构建系统。 [seg 3284–3289]

## 问题：机器人数据的每一次更新都是一次重建

我们在模型训练的时候，经常会发现一个问题，就是我们的研究员会问：我们现在这个模型，它上一次训练，到底是基于哪一版的 caption？然后他们经常会发现一个非常严重的问题：比如说我们现在有一个 table，这个 table 有 6000 多帧，而且会随着数据采集不断有新的数据进来。他们会发现，每一次有了新的数据，我这个 episode 进行了追加，那我的每一列全都要进行补算；或者我的模型组提出了新的模型，或者我们决定采用一个新的 embedding API，那我们就会发现它的每一个数据时刻都在变。 [seg 3294–3303]

但是我们这个数据，从它的源头，也就是从机器人那边，只会采集一次。在后续不断的演进中，它会不断地需要进行重建，需要去追加新的 column。这种时候我们就会发现，我们这个数据每一次的模型和更新，都是一次对历史数据的重新构建。LanceDB 在跟用户沟通和在生产实践中就发现，其实每一家公司的所有机器人数据，本质上需要的是一个构建系统。 [seg 3304–3309]

也就是说，如果我们把它的原始数据作为我们的源代码，那么它就会需要一个 functions 的机制，可以把它从源代码构建成另一个形态。然后我们需要有一个方式，像 Git 一样，可以去标记某一个列的某一行——我们把它叫作 cell——这个 cell 需要有一个状态去对它做标记，说它到底是不是 dirty 的，我们是不是需要对它做更新。它最后产出的 artifacts，也就是我们这个系统里面的生成列。再进一步，对于完整的系统状态，我们会需要一个 lock file〔?〕，也就是说我们需要一个 snapshot，可以完整地去标记我们整个 table 在整个训练周期的状态。 [seg 3310–3316]

## Lance format

我们想要解决这个问题，就是从第一性原理去思考，自底向上地去构建一套完整的方案。首先就是我们的 Lance format。我们这个 Lance format 从设计最开始就是完全针对 AI 训练、针对模型的推理、后训练去设计的。我们的第一个要点就是它的 add column 基本上是没有开销的。也就是说，当用户对一个表增加新的 column 的时候，它不需要对已有的数据进行重写，也不需要对大量的数据做修改，只需要简单地写一个新的 data file，就可以在这个 table 里面增加新的一列。 [seg 3317–3326]

同时，Lance 本身有完整的自己的生命周期管理机制：它支持分支，支持 tag，也支持在分支之间去做 cherry pick、去做 merge。从而保证了我们的用户在任何一次训练中，都可以有一个完整的 snapshot，可以保证它整个数据的图谱是完全清晰又正确的。 [seg 3327–3332]

在此基础之上，我们的 Lance 还构建了全新的 Blob V2，也就是说我们可以在一个 table 里面完整地管理我们在训练中需要用到的所有类型的数据，包括 video、audio，或者各种不同的 embedding 数据，以及图片。我们可以非常自然地在同一个表里面对视频做切片，然后对切片再做 embedding，然后再对具体的切片做语义化〔?〕的分析和检索。根据我们实际测试的效果，我们把一个 blob 通过 Lance 来管理，可以比传统的 Parquet 快 89 倍。 [seg 3333–3338]

## Cell flag 与稀疏数据

下一个问题就是，当我们有了一个可以承载整个训练中所有数据的系统的时候，我们下一个需要解决的问题是：我们怎么去标记一个 column 有没有被计算过？因为我们知道在生产当中，我们很有可能会用 null 去标记这个列还没有数据。但是前面很多老师也分享过，我们要去做机器人的数据采集。那么当一个机器人的手柄、它的夹子还没有夹到物体的时候，我们怎么去标记它的状态？这个时候它的数据是一个有效的 null 状态，但是我们却没有把它完整地管理起来，这样就会导致我们的数据在后续做训练的时候，要对 null 做很多特殊的处理：我们要去区分这个值到底是有效的，是没有采集，还是采集了但是失败了，还是说采集到了，但这个夹子夹到它自己了，没有夹到正确的物体〔?〕。 [seg 3339–3347]

所以我们就设计了一个专门的 cell flag〔?〕机制，让用户可以在整个 Lance table 里面去管理它自己的表〔?〕。为了配合 cell flag 机制，我们还全新设计了一套完整的 encoding，这个 encoding 是专门针对稀疏数据去做处理的。也就是说，当一个机器人的数据表里面有大量稀疏数据的时候，我们可以对它做非常高效的压缩，从原始的 300 多兆压缩到只要 1 兆，同比的话就是可以把我们的存储降低高达 300 多倍。 [seg 3348–3353]

## LanceDB functions

当我们有了 Lance table、有了 cell flag 之后，LanceDB 下一步要推进的就是我们全新的产品线，叫做 LanceDB functions。也就是说，我们支持用户只需要写一个简单的 UDF，写一个简单的 Python，就可以去定义一个它自己的模型的计算，比如说一个 embedding 的计算。然后它可以注册到我们这个系统里面，再绑定到某一个具体的 column，就可以在后台自动地对这个 column 进行刷新。我们所有的数据会自动地根据系统去做切片，然后分发到不同的 GPU worker。同时我们还会保证这些所有调度出来的 worker 全都是可持久化的。也就是说，我们不会让用户宝贵的 GPU 资源去重复地做计算，我们尽可能地保证：只要你成功算出来了，我们就会帮你去做持久化。 [seg 3354–3365]

最终，当所有的计算全都算完之后，我们可以在一个新的 snapshot 里面把这些所有的数据做整体的发布。这样就避免了用户在某一个瞬间读到这个表的数据是错误的。LanceDB functions 从设计的最开始，就是要去做增量的计算。也就是说，不管你这个表之前有多大，当你新增了 100 帧的数据之后，我就只需要计算这新的 100 帧的数据，我只会去重试已经操作过的 range〔?〕，而且它只有在全部完成之后才会提交新的版本。 [seg 3366–3373]

## Snapshot 机制

最后一个就是我们 LanceDB 的 snapshot 机制。前面也提到了，在任何时候，你都可以通过一个具体的 version ID 去定位到 LanceDB 里面的某一个表。然后它可以在 LanceDB 这个表里面……〔无法辨识〕……的时候，最重要的就是要去做对齐。也就是说，我在这一帧看到的这个苹果是长这个样子的，这个苹果是放在这个 table 上面的，这个时候还有其他 18 个摄像头从不同的角度在同时拍摄这个苹果。那么我们 LanceDB 的 snapshot 机制，就可以保证这个苹果的位置始终是正确的，它不会陷入一个薛定谔的状态。最终，我们会通过 pin〔?〕的机制，把一个表是用哪个模型去训练的、在什么时候训练完成的，包括一些用户自己的 metadata，全都加到这个 snapshot 里面。 [seg 3374–3383]

## 性能与规模

我们在真实的业务场景里面，跟 LeRobot 做了一些性能对比，会发现 Lance 会比原生的 LeRobot 要快 3 到 5 倍。当然，我们现在也在跟上游做积极的合作，也就是现在 Hugging Face LeRobot 已经原生地支持了 Lance 去做这种数据〔?〕的摄入和训练。 [seg 3384–3388]

最后，也是最重要的一点，就是我们这个系统本身是可以 scale 的。也就是说，我们不是针对一个非常小的训练集去做这么一个运算。在我们一个真实的场景当中，我们的用户有一个 25 TB 的工厂视频数据集，它在里面不断地随机抽帧，然后对这些抽出来的帧做端到端的训练，最后再去更新它们的训练集。我们还跟比如 DeepSeek 和 Applied Intuition 去做一些包括大模型的训练，和多模态 search 的部署和推理。 [seg 3389–3398]

Lance 创立最开始的时候，是去做了 Lance 的 file format。然后我们发现，只有一个 Lance format 是解决不了实际问题的，所以我们在这个基础上还设计了新的 table format。现在在 table format 的基础上，我们更进一步地向前去探索：我们从一个 storage format 进化到了一个计算的 format，就是把 functions、物化视图、流式的物化视图，全都并入到了一个大的 Lance 体系里面。后面还会有更多开源相关的新闻宣布。主要就是这样，谢谢大家。 [seg 3399–3405]
