So, an LLM gateway — it sounds pretty simple, right? You take a request, you forward it to the upstream provider — it could be Anthropic, OpenAI, Alibaba Cloud and so on — you get the streamed response back and you forward it to your users. What could go wrong?

Well, actually quite a lot, as we've learned. I'm Xinghong, AI engineer from Optiver. We are a global trading firm where performance and reliability really matter. Today I want to share our journey setting up an LLM gateway for our users — developers, researchers, and also business users — some of the lessons we learned over the process of setting up this gateway, and how these lessons shaped our decision on building our own LLM gateway within Optiver. [seg 1637–1639]

## The scale of the problem

So this is the scale of the system, or the problem we are trying to solve. Every day our LLM gateway is serving around 3 million LLM requests for our users, across four data centers we have globally. We serve models from multiple upstream providers: we have about 22 models serving 95% of the requests, from several providers. They all speak different protocols — some speak the Anthropic Messages protocol, some the standard OpenAI-compatible protocols, Gemini, and so on. We need to reliably serve these requests to our users, because we have researchers testing their hypotheses, we have developers writing important code or even FPGA code, and we even have business users handling their Excel sheets and PowerPoints. But errors do happen. We observe around 0.4% error rate from upstream providers. This may not sound like a lot, but if you look at the base, it's actually a lot of errors. And if you are an individual user, one error will ruin your experience. [seg 1640–1640]

## Starting with an open-source gateway

Okay, so we started with an open-source LLM gateway, as many of you would probably do. It's a practical choice for us, because we wouldn't just jump in and build our own gateway. It actually gave us a very good starting point. It supports multiple LLM providers without us having to do any coding. It translates between protocols well, so you can call an upstream provider from any harness of your choice and the gateway does the translation nicely in between. It serves thousands of users internally, everything just works — so, mission accomplished, right? And what should I talk about for the rest of the talk?

Actually not, as we noticed. This is what happens next. In the morning you walk into the office, coffee in hand, you open your computer and Slack, and you see this. I don't know if anyone here has ever hosted an LLM gateway within your company — please raise your hand. Okay, yeah, so you may know what I'm talking about. This message is scary to people who host LLM gateways. You see someone saying that… [seg 1641–1641]

An individual user's problem? Maybe it's their prompts. But then you see the little plus icons under the message increasing — 10, 20, 30, sometimes 100. You see more and more users complaining about the same issue, and you start realizing: oh, this is not an isolated incident, this is actually a more serious matter. [seg 1642–1645]

So your position when operating an LLM gateway is that this is like electricity and water — it is becoming a utility. Everyone is depending on your work, and if you start having issues in your gateway, everybody knows. They can be faster than your monitoring system. [seg 1646–1650]

So what is the user saying? They're saying, basically, the request is retrying. They're trying to do something simple and it just doesn't work for them. As an operator, you know that many things can go wrong. It may not be the gateway. It could be the upstream providers, it could be one of the tool calls that failed, etc. But the user doesn't care. It's all the same to them. To them, the experience is simply broken; they don't care what in the middle is broken. So we need to jump in and figure out what's going on here. [seg 1651–1663]

## HTTP 200 does not mean success

Jumping into this: one tricky thing about an LLM gateway, compared with a typical web proxy, is that HTTP 200, the standard HTTP code for successful requests, does not always mean success here. You can get a perfect HTTP 200 from upstream initially and still have it go wrong in the middle. We've seen countless issues like that. You can have a request that started streaming nicely and suddenly stalled halfway, and the user stopped receiving the rest of the response. [seg 1664–1669]

Because we are doing protocol translation, we have seen broken cache in the middle. You should have a nice, high cache rate, which basically equals saving money for you, because you are usually paying one-tenth of the cost for cached requests. But if your cache is broken because something is wrong in the middle, you can see from the cost that it doubles, triples, quickly. [seg 1670–1674]

We have also seen silent failures. This one is recent, and it won't show up anywhere in your monitoring system. We found in some of our requests that the Anthropic thinking block — which nowadays is no longer sent in clear text; they send encrypted signatures, which are actually the thinking content itself, with a summary — in certain cases, the response was silently dropping these thinking blocks. This is scary, because you don't see it in the gateway. The user still sees the response to their request, but in the next request, because the thinking chain is broken, the gateway or the upstream provider needs to do more work to regenerate these thinking blocks. So in the end: increased latency and increased cost. One of our users found this with their agent, which detected this anomaly in the response. They let us know, and we found it was actually a bug in translating the protocol from Anthropic to OpenAI — I think they were calling Anthropic models from an OpenAI-compatible harness, right? [seg 1675–1685]

So as we can see, many of these issues eventually can be attributed to the fact that we are translating between harness protocols. This made us start thinking about what we should do about it. [seg 1686–1688]

## Provider failover

Okay, so assume now that you solved the translation problem — you educated your users to never call Anthropic models from OpenAI harnesses, and not the other way around either. Other things can fail. Upstream providers are not perfect. Whether it's AWS or Anthropic, every provider nowadays has certain periods of time when they can fail. They can fail for certain requests, or they can fail for an extended period of time. But business cannot be stopped by this. So the lesson learned here is that for every important language model we are using, we try to get at least two providers and fail over between them, so users won't notice or won't need to do anything in case one breaks down. [seg 1689–1694]

But how we do failover — again, I'm comparing this with a typical web proxy — you cannot simply load balance between them, because the nature of an LLM request is stateful. So we have a clear boundary on how we handle failover. If the user hasn't seen the response yet — say you send a request to one provider and it immediately gives you a 429, you are rate limited, or a 529, the server is busy — you can try the second provider and continue serving the user's request. But in case streaming has already started — your user has started seeing the response coming up on their screen and something goes wrong in the middle, which does happen as well — we have no choice but to surface the error to the user. They will see an error, and they can choose to retry or do something else. [seg 1695–1708]

I am aware that there are now some more advanced gateways that can fail over midstream — for example, they can continue streaming using the response returned by a second provider. But we evaluated the complexity and decided we'll probably not do it for now. We'll stick with the simpler option: fail early and let the user decide what they want to do. [seg 1709–1711]

But in certain cases, you will see that one provider simply breaks — it doesn't want to serve requests at all — while the other one is acting perfectly fine. In this case, another important mechanism we have is a circuit breaker. We have thresholds set for different types of errors, and our gateway can decide to stop sending requests to one provider altogether for a period of time if the circuit breaker is tripped. [seg 1712–1718]

## Failover can break things

All right, so now you have two providers, and you know you should be failing over between them — everything should be fine, right? But things can still go wrong. Again, this is back to the nature of LLMs being stateful. One thing we noticed is that if you simply split your traffic between two providers, even if they serve the same model, you can easily break your cache. Again, you pay much less when things are cached, right? [seg 1719–1727]

So, a few lessons we learned here. One: if you do want to fail over your requests, you should normally keep the session sticky. Even if you have two providers behind the same model ID, make sure that a single session from a single user always hits one model, even if you want the actual traffic to be split between the two. You can have two sessions calling two different models, but never one session across the two models. [seg 1728–1732]

In some cases, for some models, like some Anthropic models, there are also certain feature sets that are not supported on all providers. On Anthropic first party, they may support beta features hidden behind beta flags. Sometimes these can be super helpful — like tool search, which can massively save our tokens on MCP tools — and there are other features as well that we might want to use. But they may not be supported on AWS Bedrock for the moment, right? Compatibility and features are changing every day. One thing we learned is that if you want to have two models serving the same model ID, you need to hide this complexity from users, and you need feature parity between them. So if a feature doesn't work on both providers, just disable it, and have a common feature set for users to use. [seg 1733–1745]

The third lesson we learned from provider failover is that you should keep your fallback in exercise. Backup always breaks when you need it — you may have heard this one. We shouldn't start sending requests to the fallback only when the primary fails; we should keep exercising it even when everything is working fine. The way we deal with it is we always split 10% of the traffic, or sessions, to the secondary model provider. That gives us valuable data and metrics to understand how the secondary provider is working, even when we don't need it at the moment. [seg 1746–1753]

## Multi-region architecture

Okay, so all the external matters have been sorted. We know we can handle request-level issues, we can handle provider-level failover. Now the problem comes back to ourselves, right? I mentioned earlier that we are serving the LLM gateway across four regions, or four data centers. We have one problem: we have a requirement that access control be centrally managed. We want a single set of credentials and permissions for all users, so if they can access a model in one region, they should be able to do so from all regions. This is important because many of our applications are deployed globally, and we can't rely on users to manage the complexity, like keeping four API keys depending on where they're calling from. We want things to be simple for them: you have one API key, and it works everywhere. [seg 1754–1767]

But this comes with a cost. Our initial architecture was naive: we kept a single Postgres database for all this data. And what made matters worse: our compliance requirements ask us to keep track of all the prompt logs — basically everything we send to and get back from the upstream provider — and we chose to just flip a switch in this open-source gateway to say "store this in Postgres". Yeah, I see some of the audience smiling, so you probably know what I'm going to talk about. [seg 1768–1773]

The result: massive amounts of data being sent across the Atlantic — at some point over 200 gigs of data per day. Our main database was four terabytes large. This is the gateway database, not any kind of market data database. This is just absurd. And we also paid the price. You can see from the monitoring chart on the right our authentication latency — basically the overhead added on top of what the user experiences when they call our gateway. It's two seconds. It's just terrible. Our users were complaining even more that it just doesn't work for them. [seg 1774–1783]

So we did two things. First, we immediately turned off prompt logging in the database. Just don't send this massive amount of data to Postgres — it's the wrong storage. We send it to S3 object storage instead, directly from each region. The second thing we did was authentication: we moved all authentication local by creating local replicas. It does give us a few seconds' delay in propagating permission changes or newly created API keys, but it helped us drop authentication latency from two seconds to 20 milliseconds. [seg 1784–1793]

So, some of the points I've already covered: our gateway has global identity — a single key works everywhere — but inference stays local. We have no remote dependencies on the inference hot path. One remaining issue to explain is how we do accounting. We do want to understand how much each of our applications is spending, and we want to control and cap usage if they go over the limits. On this part we chose eventual consistency. That means if you are over the limit for a few minutes, that's fine, as long as we can stop you eventually if you are misbehaving, for example. It's a trade-off: between having accounting in the hot path versus eventual consistency, we picked eventual consistency. [seg 1794–1803]

## Observability and tracing

So after we had done all of this, you would think it's the end of the story. But we still had users complaining in the Slack channel: "Inference is slow. What are you guys doing?" This is very frustrating — we had exhausted everything we could think of. What else could be wrong? [seg 1804–1811]

This is when we thought it was time to introduce better observability. Previously we already had metrics and logs. Metrics help you understand overall gateway health; they answer questions like what's the latency, how many requests, what's the error rate, and so on. Logs help you answer compliance questions, like what you are sending. But one thing we were missing was tracing. We want to understand, for any given request, the path it has gone through — what tool it is calling, how long it takes, and so on. Tracing is the answer to this. So we set up distributed tracing across all the harnesses, all the gateways, and MCP tools, which allows us to build a full picture of what's going on. [seg 1812–1829]

I'll take one example here; the detail is not important. This is the trace from the user who complained that it was slow. I don't know if you can read it from there, but the actual inference time is 17 seconds — probably not too bad, right? We have a p95 of one minute, so 17 seconds is not too bad. But we found from this trace that one tool call was taking more than three minutes. That's why the prompt was slow. Without the trace, it would have been very difficult for us to tell. [seg 1830–1839]

## Building our own gateway

So in the end we have done a lot. We decoupled our spending pipeline — the spending calculation. We built our own cost control and so on. And we learned that protocol translation is not something we want, because it breaks things. So in the end we decided to build our own gateway, based on a much leaner feature set that we rely on. It gives us better control over how we do inference and monitoring. [seg 1840–1847]

It's not something that everyone should do. This is based on our current understanding of what we need. It doesn't mean we'll stick with it in the future: if there's an open-source gateway that does these things better, we won't hesitate to turn back to open-source options. [seg 1848–1852]

So to wrap up: protocol translation is hard. We are leaning more towards protocol-independent harnesses — harnesses that can speak multiple protocols, rather than translating between them. We learned that failover can break cache and other things. The request path of a gateway should be isolated across regions, and we need to enable tracing everywhere. So this is our story of building an inference gateway. If this is something you're also interested in, you're welcome to visit the Optiver stand over there. I'm Xinghong from Optiver. Thanks a lot. [seg 1853–1858]
