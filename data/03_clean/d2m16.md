Thank you. Today my talk addresses a common problem that we have to tackle in AI security, which is answering: should this agent be allowed to do that? [seg 2985–2986]

So let me start with an example. Suppose you're an engineer debugging a production issue. So you go to your coding agent and you say, "The checkout service is failing since the last deploy. Find out why." Your agent starts to propose tool calls. The first one is an AWS logs filter against your production account. It's read-only, so it gets the grant and the tool call executes. Then the agent looks at the logs. Well, based on the logs, the service was underscaled. So then it starts proposing the next tool call, which is to update the service. Well, is this command useful? Maybe. Is it safe? That's not really clear. [seg 2987–3003]

So how do we determine agent intent? In order to figure out whether your commands are safe, we need to know how to do that. For agents, intent becomes action through tool calls. So in this case, the user's task is to investigate a failing service, and the proposed tool call ended up being a modification to the production account. And the agent's reasoning isn't necessarily trustworthy. So we need to be able to answer with high confidence whether the call fits the task. And if it doesn't, we need to stop the agent from executing that call. [seg 3004–3010]

So how do we do that? Well, we can implement a component that is a runtime intent judge. It's able to take in as context the agent's session prior to the tool call, including the tool call information itself. It needs to be able to execute with low latency at runtime, so that it doesn't add user friction, because multiple tool calls can be executing all at once. And ideally it should run locally, so that the context, including sensitive information, doesn't go off-host. [seg 3011–3015]

## Approaches

Well, what are some of the approaches? Let me go over some of the common ones. One, you can write deterministic rules — for example, a regex that greps what the tool call contains and tries to classify what the tool call does. You can also try to use a hosted large language model, for example Kimi K3, or if you're in the US, you can use Claude or OpenAI models. These will be able to provide deeper reasoning over large amounts of context, but your context will still leave the host. They'll be slower and costlier. Third, you can also do custom-trained classifiers, such as an XGBoost model. However, these require labeling lots of data, which most teams don't have, and every time your tool call data changes, you'll have to retrain. [seg 3016–3026]

So here, I focus on a slightly different set of models: two kinds of smaller models. One is a generative small language model, and I compare that model with a set of open-source decision models to see how well they can perform in solving this specific problem. [seg 3027–3028]

## Experiment

Here's the experiment setup. I created synthetic tool calls that are basically command-line tools, and each of the models I mentioned was prompted with the same prompt, which includes the context — the task and the agent's reason — as well as a set of questions that probe whether the tool call is safe and what kind of operation it could be. And we ask the models to output an access-level classification for these tool calls. We then apply policy on top of these access levels. Each of these access levels indicates low risk or high risk, from read all the way to admin. [seg 3029–3036]

Let's look at the results. Here, in the green bars, we see the result for each model when it's asked to pick an exact label. For the decision models, I compare GEV, Clef, d1, as well as Laya, a much smaller 400-million-parameter model. With the exception of Laya, the decision models actually perform pretty similarly, between 91% and 93% accuracy. [seg 3037–3041]

However, there was a key difference. Some models are a little bit more cautious: when the prediction was low in confidence, they would defer and pick "unknown" when they had the chance to do so. And you can see that Liquid d1 actually did this about 50% of the time. So the decision model you choose matters, and the probabilities you get are not apples to apples, so we need to be careful not to compare them exactly. Then the SLM, Qwen 2.7〔?〕, 7 billion parameters, had only 72% — significantly lower accuracy. So again, I think this result reinforces that the decision model is a better solution. [seg 3042–3049]

## Failure modes and thresholds

Let's look at some failure modes in the classification, which is also really important in how we treat them. Some errors are riskier than others to let through. Here's an example where there's a nuance in the command being executed. Suppose the agent is trying to solve a task where AWS GuardDuty — the threat detection service on your production account — is causing lots of issues with the migration traffic, but the proposed tool call tries to delete this detector. This tool call can be classified as delete, or it can be classified as admin, since it's actually turning off a useful service on your production account. And when you look at how the different decision models classify this, there's actually a key difference. Some models classify this as delete — which is not exactly the right classification — with low confidence. [seg 3050–3061]

So how do we handle these cases? Well, we can choose a threshold at which we cut off the decision and say: if it's below a specific confidence level, we should defer that decision to a person for review. And we also need to be careful not to choose a single threshold across all models, because sometimes that threshold can be too high for one, and you end up deferring way too many calls to people, making that model not useful. [seg 3062–3066]

## Reference architecture and demo

So let me put this together in a reference production architecture for how we can implement an intent judge. A user initiates a session with their AI agent — typically, say, Claude or Codex or your favorite coding tool. The user submits a task, and the agent starts to propose tool calls. The tool calls can be intercepted by a gateway implemented as an MCP server. You can think of this gateway as an approval or access gateway. It forwards the context and the evidence, including the call, task, and reason, to an intent judge. The intent judge is essentially a harness that wraps around a decision model — the prompts, the questions, and the choices — and outputs the classification result. Then it can invoke a policy gate component, which can hold, for example, an enterprise's or a company's specific policies or rules, and retrieve the current grant authorization that the user has, to make a decision to either approve, deny, or escalate the tool call, returning that response to the AI agent. [seg 3067–3077]

So here I want to show a demo that illustrates an implementation of this and how it works. On the left-hand side is your agent session, and on the right-hand side is your access gateway response. You can see the agent session initiates the first task, and the user right now has a grant that's up to read — that's something we can set custom. Then the agent proposes a read tool call, which is permitted, and that response is returned to the agent, and the agent begins execution. Next, you have a denied request: a new tool call is sent to the access gateway, the classification is an update, and that does not meet policy. So this is an illustration of how this could work. [seg 3078–3086]

## Lessons in production

So let me summarize with some lessons in production. First, we need to test the whole system, specifically against two important metrics. The first one is how many risky calls we are letting through, via the intent judge and via the whole system — we want to minimize those. The second is how many safe calls we are letting through — we want to maximize those. And we also want to make sure that the evaluation input data for the intent judge includes examples of both. [seg 3087–3093]

The second aspect is tuning the intent judge. It's very rare that the first time you configure a decision agent using a decision model, you have the right context or the right question input. We need to examine all of the errors and fix that input, and make sure that all the information is in there and nothing is missing. Then we also need to look at our evaluation data and make sure that the labeling on all of the samples is unambiguous, and that if you have reviewers creating that dataset, the reviewers agree on those labels, because human expert judgment is very important in validating how good the performance of your intent judge is. [seg 3094–3098]

Third, as we've looked at before, how you choose those thresholds really matters, and they need to be calibrated on your validation data. And then finally, consider fine-tuning last, when there are still persistent errors. [seg 3099–3102]

Okay. In conclusion: should this agent be allowed to do that? Only if the call fits the task and your policy allows it. So judge each tool call against the user's task before it runs; use a decision model to judge intent; which model you choose matters; and when the model's unsure, escalate to a human approver. All right? That's it. Thank you very much. [seg 3103–3110]
