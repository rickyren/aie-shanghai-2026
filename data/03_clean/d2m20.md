## Jina Reader 是什么

先给大家简单介绍一下 Jina Reader。Jina Reader 是我们 Jina AI 开发的一个帮助大模型读网页的工具，一言以蔽之，它的核心功能就是 URL 转 Markdown。像这个功能，现在已经有很多 agent 软件都自带了，但 Jina Reader 的区别是它永远使用无头浏览器来渲染网页。这样有一个好处：无论目标网站使用的技术多么先进，你总是能够获得人能看到的内容。 [seg 3678–3684]

我们这个服务在形式上是一个 API，就是 SaaS API〔?〕的形式。使用方式比较简单，就是在你所关心的 URL 前面直接加上 r.jina.ai 的地址就可以。当然它也支持更多定制的高级功能，你可以直接登录 Jina AI 的网站获取更多的信息。我们这个服务的核心代码在 GitHub 上开源，如果有兴趣的话，可以让你的 coding agent 直接扫描我们的代码，然后给你讲解。 [seg 3685–3695]

我们服务有一个特点：它提供一定的 free quota，不仅是免费访问，而且是匿名访问，这样就允许 AI agent 自己来访问我们的服务。我们这个服务是运行在 serverless 平台上的，这样有一个好处：对于单个请求来讲，它的延时是一定的，而整个集群的容量是在不断变动的。 [seg 3696–3701]

## 技术细节

接下来是技术侧的一些细节。这两天的议程听了那么多新技术，我们这个软件其实是一种"老手艺"，在 AI 出现之前，我们就是手写编程〔?〕的这样一个流程，至今没有什么特别大的变动。我们有两种原生的输入，一种是网页，另一种是 PDF；两种原生的输出，一种是大模型友好的文本，另一种是截图或者 PDF 渲染图。 [seg 3702–3708]

中间我们比较关注的是浏览器渲染这个环节，我们主要的优化也集中在这个环节。我们的做法是：首先在本地启动浏览器，然后在网页加载之前，在 JS 环境里面注入脚本，也就是 preload script，同时审查所有的请求。为什么呢？因为这个环节的难点是如何尽早地检测或者判定网页加载完成的时间点。通过这两种方式，首先能够尽早地完成检测；并且在我们完成判定之后，我们在网页内部主动地截取当前网页的状态，然后把它主动地上报到网页之外。这样最终再结合你的请求所预期的返回内容，以最早的时间点完成返回。这就是大致的技术方面的内容。 [seg 3709–3720]

## 一个网页需要多少 token

接下来的时间我想留给我们的一些发现。首先，我们 Reader 是按 token 计费的，也算是参与 token 经济吧。那大家会不会有些好奇：一般来讲，一个网页需要多少 token 呢？这就是我们 Reader 后台的一些数据。总的来讲，经过 Reader 处理之后的网页，token 长度的中位数大概在 4.5K 到 5K 左右。网页 token 长度的分布，大家可以看到是一个大致上符合正态分布的曲线，但问题是我们这个轴是对数轴，所以它实际上是对数正态分布。如果看平均数的话，大概是中位数的四倍。数据上大概就是这样。 [seg 3721–3729]

如果不经过处理，直接是 HTML 的话——我们这边有一些奇异值，我们忽略它——只看分布的话，大概在 30K 左右。如果我们加大处理力度，比如说抛弃链接的地址以及图片的地址，可以把中位数再降低 1.5K 左右，到 3K 左右。这就是我们访问公开互联网任何一个网页大致上的 token 消费。如果是平均数，大概是四倍，基本上是这样的数据。 [seg 3730–3735]

## 算一笔经济账

接下来带大家算一下经济账。我们数据抓取这个行业，一般比价都是比千次调用的单价。我们就按中位数来比，恰好能够对应到大模型按百万 token 计价的模式上。我们会发现，如果你直接把网页的全部内容放到主流模型里面去处理，这个单价是非常惊人的，肯定是九刀以上；即便放到中国的模型里面，也会在三刀以上。作为对比，互联网广告每千次网页浏览的收入大概是三到十五刀。所以对比来看是非常惊人的。这还只是中位数，如果按照平均数算的话，那会乘四，就更多了。 [seg 3736–3746]

但是如果你第一步不直接放到模型里面，而是做一些预处理，或者用专门的模型来做信息抽取或者摘要的话，你可以拿到一个底价，就是 0.45。这给我们两个启示：启示一是我们 AI 用户的付费能力很高；二是也许把网页转成 Markdown 并不是最后一步，你还需要进一步用专用的模型，或者传统的切分、重排这样去处理。 [seg 3747–3751]

## 反爬与匿名访问

剩下的时间，我想加速给大家提一下反爬的事情。Reader 首先是一个抓取器，它要面对对方网站的反爬；另一方面，我们又提供匿名的额度，所以我们也需要防止滥用。Reader 不会帮助用户去突破对方网站的策略，我们还提供很多选项来帮助用户合规地爬取对方网站的内容。但是我们已经发现，从 Reader 后台看，匿名访问的比例已经从半年之前的 20% 提高到现在的 36.9%。如果这个趋势继续的话，我们服务的免费部分可能就会受到影响。 [seg 3752–3759]

所以这个我觉得可以大概过一下。各个网站做反爬的出发点可能不一样：大站主要是想保护数据，而小站，像我们 Reader，主要是想节省 IT 资源。当然还有一条暗线，就是互联网网站基于广告的这样一种商业模式。但是 Agent 确实改变了，时代也变了：Agent 已经显著地加入到我们现在互联网浏览的活动里面。 [seg 3760–3766]

## 让 Agent 付费？

那如何是好？我们有一个朴素的想法：要不然就直接收费吧。现在行业里面已经有一些探索，比如说有一些头部的玩家可能希望 AI 的运营方统一在网关上付费；另外一些可能想的是 AI Agent 的终端用户通过数字货币的形式分散地付费；还有一些其他付费网关的形式。但它们的意图都是让 Agent 直接按请求付费。 [seg 3767–3774]

对此我个人并不是特别看好。为什么呢？首先，我觉得渠道并不是问题，价格才是问题，而价格是不可能低的，因为刚才提到的 AI 访问网页，它的价格锚定就高。再有，我们也知道世界是参差的：如果以发达国家的网页定价来看，全球南方国家或者非洲国家〔?〕是很难跟上的，而且一般是美元定价。如果 Agent 上网还涉及到国际贸易的话，会产生其他的社会问题。再就是，"给钱就能抓"也并不会真正实现，因为其实有一个灰黑产的问题：如果真的给钱就能抓的话，很难防止数据倒卖。 [seg 3775–3786]

但是唯一一件我可以同意的事情是，控制 Agent 网页访问这件事务必要发生在网关这一层，就是 gateway。那现在 gateway 这个行业是一个什么格局呢？我们看到它的流量集中度还是非常高的，前四个机构已经占比超过 50%。这意味着，如果几家大的机构能够达成一致，那么行业的格局是有可能被改变的。 [seg 3787–3794]

## 一个不成熟的想法：Agent 时代的广告

所以我在这里也抛出一个不成熟的想法：如果和 Agent 达成主动的现金交易比较困难的话，我们可不可以借鉴早期互联网，也通过广告的形式来维持我们这样一个免费的服务呢？比如说，我们给 Agent 一段广告语，让 Agent 复述一下核心口播，比如说"今年过节不收礼"，对吧？请补全下半句。像这种。 [seg 3795–3802]

除了直接广告，也可以运用一些可以验证的任务，就像之前的 reCAPTCHA 一样。我们知道 reCAPTCHA 通过众包的形式完成了 OCR 数据的标注。那也许我们可以通过 embedding 模型或者 reranker 模型——当然我们这个广告也属于一种 QA 任务——自动化地完成这个验证工作，然后让其他人的 Agent 帮我们完成一些公开任务，比如说公开数据的翻译、摘要这种任务。这样也许能够保持住我们这个免费服务的未来吧。 [seg 3803–3809]

所以最后，无论怎样，我个人是非常希望行业能够最终重新达成一致：无论是人类也好，还是 Agent 也好，都可以继续享受免费的互联网。谢谢大家。 [seg 3810–3812]
