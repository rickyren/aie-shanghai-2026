## How do we build these?

So obviously, everyone's super excited about these models. How do we actually build these? Unfortunately, we can't really copy Jev, because all we know about Jev is from their release blog, and there they say something like: it's a new model architecture; they're using something called reinforcement learning for calibrated decisions. And to be honest, we have no idea what any of that means. But this is not criticism, right? Credit where credit is due. We have to give a huge shout-out to the TypeSafe AI team for making an entire industry rethink how we should be building these models to achieve true automation. [seg 2082–2090]

Okay. Jev gives us a target, but not the recipe. That's fine. This is where the open ecosystem is coming in. So the rest of this talk could also be titled "How the Open Ecosystem Is Reverse Engineering Jev." I'm going to be focusing on how we at Liquid build our decision models, but you'll see some of these points reflected in the open ecosystem as well. [seg 2091–2096]

Now, TypeSafe spent two years in stealth building Jev, and then after the release, it took less than a week for a copy to appear. Turns out all you need to make a decision model is any LLM and about this many lines of code. Don't read the code; just look at how few lines of code that is. So this is called an inference-only technique. And the idea is that you can use any LLM — in our case, since we're optimizing for on-device, we're using our LFM3 family — and then you prompt the model in a very specific way. So here you can see we give it the state, then the question, and then for each option we attach an option label token: so A, B, and C. And then we tell the model to only answer with the option label token. [seg 2097–2107]

The rest of this code is easier to understand if we look at it like this. So we do one forward pass, and then we're only looking at the logits of the last position, because we're only interested in the next token. And then we're only looking at the tokens of the possible option codes — so A, B, and C in this case. Then we do softmax over it, and boom, we have a decision model. This actually works, but it's clearly a naive approach. It's a good baseline to beat, but clearly, as you can guess, this comes with a lot of problems. [seg 2108–2115]

So problem number one: as all of you know, LLMs are trained to predict the next token, not really to make decisions. So that means different problems. For example, this one: when I change the order of the options, in this case the model returns me a different answer every time. Well, this is bad. Clearly, here in this example, the model is biased towards the letter B. So we need to train the model to actually make decisions. So how does that work? We take a bunch of different classification tasks, and we convert them into the prompt template that I just showed you earlier, and then we do SFT over it. Some teams do full fine-tuning; some teams do LoRA. In our case, we found that LoRA was more effective than full fine-tuning, and it's also cheaper. So we train the model over these classification tasks into a general-purpose classifier. [seg 2116–2129]

So speaking of general-purpose classifiers: now, is a decision model more like a classifier, or more like an LLM for structured outputs? This is actually where the open ecosystem kind of split into two. So we have encoder-based approaches, and we have decoder-based approaches. Luckily, at Liquid, we have both. So in our first release, we decided to do both an encoder-based approach and a decoder-based approach. Last week, we released our newest generation of decision models, and for this, we decided to take the best of both worlds and combine it. [seg 2130–2136]

So what does that mean? We now take a decoder-based approach, and then we lift the causal mask. Because if you think about it, an LLM that's trained to predict the next token is only supposed to look at all the past tokens, but not at any future tokens. That's why it has a causal mask. For a decision model, that doesn't make much sense. Why shouldn't the decision model be allowed to look at all of the tokens? So we lift the causal mask and give it bidirectional attention, so it can look at all of the tokens — kind of like an encoder, right? [seg 2137–2144]

Now we have a model that's trained to make decisions. There's another problem: right after training, these models are overconfident. That means a model can say "I'm 90% confident" but be right only 70% of the time. And remember, earlier I said the confidence score is actually what makes these models so useful. So when a model says it's 90% confident, it should only be wrong 1 out of 10 times. So how do we calibrate these confidence scores? [seg 2145–2150]

So apparently, TypeSafe uses something called reinforcement learning for calibrated decisions. But it turns out we actually don't need any reinforcement learning at all. At the moment, what a lot of teams are doing in the open ecosystem is called temperature scaling. And if you think about the temperature parameter, maybe you're thinking about the parameter that's used to kind of tune the creativity of your LLM outputs. But what you may not know is that it's also useful to shape the distribution over your tokens. So if you increase the temperature parameter, you can kind of flatten out the distribution, and if you decrease it, you can kind of sharpen it. And that allows us to calibrate the confidence scores without actually touching the order of the tokens. [seg 2151–2159]

So this is kind of the recipe we're using to make our decision models. And as you saw earlier, these are super powerful and competitive with the original Jev model. [seg 2160–2163]

## Where do we go from here?
