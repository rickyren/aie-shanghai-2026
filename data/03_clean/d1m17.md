哈喽，大家好。我是 TiDB 的李粒，负责 TiDB 的 AI 业务。今天我主要想在这里讲一个故事：TiDB 作为一家数据库公司，是怎么一步一步被 AI agent 公司推动出一个完整的 agent data infra 的。[seg 1864–1868]

这其实是我们客户里面、在用户调研里面非常常见的一个问题。我们服务了非常多的公司，包括线上的 agent 公司以及线下的 agent 公司，这些客户经常会问：如何把这些资料做成一个评审工作台，明天团队一起用，而且后面还要去修改？这句话里面其实已经包含了非常重的承诺：意味着客户不会一直守在电脑旁边，agent 要自己把事情推动下去；同事明天会接手，代码和资料得在；而且我们的工作台要上线，并且还要持续服务。[seg 1869–1869]

## agent 中断之后：meta 存在哪里

那我们就顺着这个情景往下看，一项任务是怎么把数据库一步一步推向新要求的。首先，agent 中断了。不管是因为我们内部服务的原因（internal error），还是刚才说的 LLM provider 的一些情况，agent 中断了，那我们做的事情还在不在？如果在的话，是存在哪里？对于数据库来说，这意味着什么？[seg 1870–1872]

对于数据库来说，我们常见的对 agent 的存储，第一个就是要存储它的元数据。我们在 agent 里面打下的所有东西，都会被存在 agent session record snapshot 和 agent session event 这两张表里面。像 session snapshot，核心是要存储每一个 agent 的上下文、计划以及工具调用的痕迹，这个非常大，像 40 到 80〔?〕是很常见的。agent events 就会更大了，它会事无巨细地把所有信息都存下来。这样整个 meta 就会从几 TB 到几百 TB，甚至到 PB 级别，这都是很常见的。[seg 1873–1873]

所以我们看整个 agent，前面我们在用，后面的数据层其实是非常重的一个工作量。并且我们要评估到底需要什么样的 agent 数据层，不能只看前面有多少用户，还要看每个用户让 agent 做多少事情，并且这个历史要存多久。[seg 1874–1875]

其实把结构拆开，这个事情就比较清楚了。一个是刚才说的 snapshot，另一个就是刚才说的 session event。session event 这张表，就是我们会把所有 agent session 的 event 信息都存下来，事无巨细，并且对执行的事件逐步叠加。对于一个用户操作，我们会用一个事务进行更新、插入，把进度对齐〔?〕，还有外部工具的调用，这些东西都会存下来。并且这也是在线事件和后面 trace 的衔接：我们先留下更可靠的执行依据，再由后面的应用把需要分析的历史数据汇入分析系统存下来，接着我们后面才有机会对 agent 做整体的优化。[seg 1876–1882]

数据增长之后，我们的应用还会遇到另外一个在数据库里面非常常见的问题，那就是分片。我们曾经见到过很多客户，举个例子，他们过去可能已经有非常多的数据库了，可能有 20 多个 DB，这种情况下整个运维、分片的路由以及跨库的协调就会非常复杂；而且容量在涨，应用里管理数据库分布的代码也在增长，这个代码就变得非常难以运维。像他们最后用了 TiDB，就会有统一的一个 SQL 入口，数据分布和分布式事务都是 TiDB 自己就能 handle 了，这样整个业务就能够更好地增长。所以有了存储 agent 元数据的 session meta 和 session events，就算 agent 中断之后，它也能快速地从这些元数据里面拉起来，再去使用。[seg 1883–1886]

## 文件怎么办：跨 sandbox 的持久存储

中断之后，我们找回了刚才的进度。但进度找回来了、meta 对上了，我们的文件怎么办？这就要看 agent 的文件到底是怎么存储的。agent 在 sandbox 里写代码，sandbox 又挂载 EBS；一般任务结束后，我们就会回收 sandbox，同时清理策略也会把对应的 EBS 清理掉。这种情况下，虽然 meta 记住了很多东西，但是我们的文件都丢了。这其实也是去年或者更往前 agent 比较常见的一个问题：短期的中间产物很容易被损毁。那为了释放算力，我们把用户所有的工作都删了吗？从用户视角来说，这就非常难以接受。[seg 1887–1890]

我们很容易想到一个事情：那我们就做备份。这个方向虽然是对的，但这个工作明显还没有完成。备份的时候，我们要协调写入、创建快照、登记项目；恢复的时候还要找到正确的快照、创建卷、挂载，要把文件和 meta 对齐。大家听了就知道这个过程非常繁琐。每一步都可能需要重试、校验和清理，还有留下的快照，所以平台最终要维护一整套非常复杂的、可靠的项目备份和恢复流程，并且承担它的存储、运维和代码成本，这其实是非常恐怖的一件事情。[seg 1891–1893]

所以我们真正想说什么？平台真正想要的，是一个能够跨 sandbox 持续存在的、真正的持久存储层。为了摒弃比较复杂的逻辑，右边 TiDB 这边也提供一个 file system，能够把工作区独立于当前的 sandbox 持久存储：session A 写完之后，就可以把 sandbox 释放掉，session B 可以 mount 同样的文件系统，然后直接去用。这样平台就不用再去维护一整套备份恢复的代码系统，文件就很容易处理。[seg 1894–1895]

并且大家也会发现一个问题：这种情况下，不同用户可能会有很多的 project、很多项目要去做，那隔离〔?〕怎么办？这也是之前常见的文件系统或者 NAS 方案遗留的问题。TiDB 其实就是解决这个问题：我们的文件系统能扩展到数百万、数千万这样一个级别，并且可以做到一个 project 就是一个完全独立的空间。这样就能够让 agent 在不同的 sandbox 里面快速流转，并且通过最小权限去做鉴权，还可以根据每一个 project 去做各种 quota 的管理和设置。这样，平台会把海量 FS 管理的这个 duty 承担掉，而 agent 或 agent platform 只需要正确地使用就没问题了。所以这一段很简单，记住一句话就够了：sandbox 删了，但我们的项目依然可以保存，并且很优雅、很简单地就能保存下来。[seg 1896–1898]

## 工作台上线：海量隔离数据库

接下来，刚才说了，我的任务是需要写个代码并且创建一个工作台。代码完成了，但真正的服务才开始。开发任务结束了，项目文件也留下来了，但我们现在可能要上线一个完整的工作台，并且明天让其他同事接着去用：他明天要可以登录、填写资料、更新状态，新的数据还要保存。所以在这三个生命周期里，平台就面临一个更大的问题：agent 不断交付新应用，后面要持续保存不同应用的数据库。这个长期管理，其实也是传统 agent 都会有的建站服务里一个比较痛苦的点。[seg 1899–1902]

传统来说，如果平台自己去维护这些实例，很快就会碰到很多问题。因为这并不是只需要创建一两个应用的事情：我们上面所有的客户，有几十万、几百万、上千万的用户，每人平均创建一到两个甚至 10 个应用，这是数量级的问题。海量应用的维护就会遇到这样的情况：创建超时了，数据库到底有没有建成？重试会不会再重建一份？回收的时候有没有丢掉资源？这些背后都是配置〔?〕、扩容、备份、升级、对账〔?〕、故障补偿等一系列的责任，都需要维护海量应用、海量数据库的平台去承担。所以代码生成越快，平台越需要一套能够跟上交付速度的数据库服务方式。[seg 1903–1903]

所以就像刚才说的，我们可以提供上千万个隔离的文件系统一样，of course，TiDB 这边也提供上千万个隔离的数据库。这样我们就能托管整个实例，底层共享存储设施；平台，也就是 agent platform，只需要创建数据库，然后把数据库和对应客户的应用关联起来，最后的权限、用量，以及所有底层计算资源的调度，都会由 TiDB Cloud 这边来处理。所以数百万到数千万这种量级是非常容易就能够支撑到的，能够让平台持续地交付应用，同时减少底层实例池的运维负担。[seg 1904–1907]

## tracing：效果和成本怎么说清

好，agent 收工了，终于把应用创建出来了。我们交出去的成果也开始拥有自己的用户了，也要开始有自己的基本业务数据了。那我们怎么去分析？效果和成本怎么说得清？一旦交付的功能上线之后，我们就必须要说清一个问题：agent 的效果怎么样，每个工具的表现如何，每个工具到底成功交付了多少。[seg 1908–1914]

这时候就需要 trace，of course。在 agent 的领域，tracing 是非常重要的一个事情，大家非常严肃地对待它也不过分。我们客户常用的 tracing 方法，都是把一次长任务拆解成能够关联和查询的模型调用、工具调用和返回，这样既能看到过程和错误，也能关联耗时、模型用量，以及最终客户自己业务的验收。这样的运行标识和 span 的关系，就由客户的应用串联起来。像我们客户使用的复杂 tracing，一个 trace 就可以达到上百 MB，并且有十万级别的步骤，因为我们非常容易看到超长时间——两三个小时甚至十几个小时——的一次 agent 任务。所有的平台每天写入数百 TB 都是比较常见的。[seg 1915–1919]

所以长任务产生的这种历史，非常值得单独建立分析链路。如果我们只看最后这个任务成功或失败，解释不了我们的成本花在哪里，因为 agent 可能在不断地重试，推高〔?〕这个成本。一条 trace 能够帮助我们查清楚一次运行，但只有一批 trace 才能帮助团队决定后面的优化方向。我们可以按工具、按任务类型来看重试、耗时、调用量，再关联验收结果，算出成功率以及包含失败重试的单位成本，最后可以筛选代表任务，做成评测样本。这些分析给我们的收益非常多：某个工具调用多，不代表它的价值更高，也有可能是因为它〔?〕效果不好；改动有没有收益，我们都需要去进一步评估。[seg 1920–1924]

历史 tracing 从数百 TB 到数十 TB〔?〕，这在大型 agent 厂商里面非常常见，最核心的关键就变成了整个数据的运维和我们持续查询、核算〔?〕的能力。原始的 trace 我们可以持续加载，然后用 SQL 去展开 JSON、提取字段，形成客户自己所需要的检索和聚合，最后在 TiDB Cloud 的 Lake 这个产品上、在对象存储上做保存。下面就会有两条分析链路：一条是排障时快速定位具体运行到了什么地方；另一条是在批量分析的时候，能够快速准备质量和成本的评测〔?〕数据，并按负载量计算配置。因此，团队就可以用一套方法去维护整个轨迹的加工、检索、聚合链路，采集、新鲜度这些东西都可以用一套方法去做，非常方便好用。[seg 1925–1929]

## 改进：checkpoint 与 fork

如果我们分析到值得改进的地方，接下来换了模型、prompt 或工具，我们怎么说这次到底是不是变好了？如果我们每次都从头重新跑，输入、工具返回、文件可能就发生了变化，结果就会有差异，这个变化到底来自策略还是来自现场的变化，就很难解释了。所以我们需要干什么？我们需要保留一个共同的起点：当时的 meta、当时的文件、当时必要的输入和配置，这些都要保存下来，然后再创建独立的分支，用同一个标准来验收。trace 只能告诉我们发生过什么，但我们要保存一些 checkpoint 或者当时的 snapshot，才能真正去做优化，以及还原当时的现场。[seg 1930–1930]

这种情况下，我们的客户就会用 TiDB 和我们文件系统的 checkpoint 联合去解决：把已经保存的 meta 快照和 events，与文件系统保存文件的 checkpoint 绑定。这样当我们要还原到某一个 agent 的某一个状态的时候，就可以通过整个 checkpoint 和 events 进行恢复，并且可以从文件系统里面 fork 出一个当时一模一样的文件内容，这样就可以去做优化。比如从一个 checkpoint 出发，一个分支连续调用一次工具〔?〕，另一个分支调整工具的选择策略，两个分支分别独立写入，最后整体验收，比较正确性、执行耗时〔?〕、总耗时。只有这种情况下，我们才能得到哪一种改法真正比较靠谱的结果，才得到真正值得保留的条件。[seg 1931–1934]

但一个任务做好了，不代表整个 agent 都做好了。我们客户的做法基本上是：先验证代表任务，再看收益是否能覆盖同类的任务，最后回归那些原本就能成功的任务，并且做各种重复实验，处理模型的随机性。只有质量、成本还有延迟的整体变化能够被评测机制接受，新版本才有理由推进上线，去观察真实的生产运行。这就是在 agent 系统里面去做的一套完整的事情。所以要先保住做对的部分——就是刚才说的，用文件系统 checkpoint 把已经做对的部分保留——然后发现用户反馈的错误部分，再验证另外一种做法。每一次运行，我们都应该在 exactly same 的配置上重新运行、重新评估，去看效果到底好不好。[seg 1935–1937]

把它连起来就叫闭环：由历史的 trace 提出问题，以保存的 checkpoint 提供现场，最后 fork 出来，产生一个新的验收证据，再到资料里面去分析。所以在整个 TiDB Cloud 给 agent 提供的 data layer 里，Lake、meta、file system 各自承担分析、状态和文件的责任，再把执行、验收关联起来，就能做到这件事。[seg 1938–1939]

## 回到开场

回到开场：第二天，我们的用户回来了，说昨天那个工作台我们要接着改。我们现在有很好的 meta 存储，所以进度能接上；有很好的文件系统持续保存，所以文件〔?〕也能跟上；我们的应用在提供服务，我们也知道这个应用是好是坏；后台的 agent platform 团队也能看清楚运行效果，验证下一次改造。用户只是说了一句〔?〕、提了一个要求，但这个要求背后，是整套 agent platform 所对应的 data layer 的一整套完整基建，我们才能持续地把这个服务迭代和运维下去。[seg 1940–1941]

所以为什么我们很多客户会选择 TiDB，其实就由这个来回答：meta 增长，我们可以用分布式 SQL 和事务减少分片；项目增长，我们可以提供海量的持久工作区，在这个工作区上持续维护；应用增长，我们可以用 TiDB Cloud Starter 这个 feature，提供海量的、独立的数据库服务〔?〕能力给客户；tracing 增长，我们可以用 Lake 这类产品做处理、清洗、检索、聚合，并且按负载配置计算。这些能力共同承担一个结果：我们希望团队更少地去维护底层的 infra layer 和支撑系统，把更多的精力用于交付业务任务以及 agent 的迭代。[seg 1942–1943]

所以如果今天大家有三个 takeaway，我希望是这样：核心是我们能够解决海量数据的问题、海量项目的问题，以及如果 agent 要改进，也可以参考我们这个方案去做改进。TiDB 的价值，其实就在不断扩大的这几个工程职责上。最后，没有人一开始就计划建设这么多的 AI infra，其实是用户的诉求把数据库推到了这里。我们认为 AI 时代，创业者的注意力是非常稀缺的，而 TiDB 要做的事情，就是协助创业者把这个稀缺的资源放给 agent 的下次迭代。这就是 TiDB 的产品方向。好，谢谢大家。[seg 1944–1945]
