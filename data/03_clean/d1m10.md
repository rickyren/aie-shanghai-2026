Hi, everyone. 大家好，我是 Vincent，OpenClaw Foundation。I'm Vincent Koc, Chief Architect of the OpenClaw Foundation. I'm going to be talking about how we've gone from dark factory to what we call Lobsterville. [seg 494–498]

## From factory manager to proof engineer

I was at AIE London and gave this talk about how engineers are essentially becoming factory managers. Our roles are changing from being developers to actually moving into the space of running factories. At OpenClaw we run the concept of a dark factory, a concept that's very familiar in China, where robots are essentially building robots, or building the parts to build themselves. But here we were building OpenClaw: we were building the harness to build the harness, and scaling this up to enormous scale. At the time I was making this, what did I say the bottleneck was? It was very much around what we call taste — the engineer having the ability to steer the model in the direction of what needs to happen and what needs to come out. But I think since then people have kind of realized this, and now we've seen many other versions of harnesses. Every model company has a harness, every technology company has a harness, everyone is building harnesses. [seg 499–504]

In my world, every morning I wake up and this kind of thing was happening. Even before, when I was running the dark factory, I'd either get rate limited on tokens, or run out of memory, or run out of compute, or there'd be some bottleneck on CI. The issue was never how fast I could go. At some point I went from running 10 to 15 agents to 60. Last I checked, yesterday I was running over 300 agents in parallel in my own personal factory. I think yesterday I shipped one and a half thousand to 1,000〔?〕 PRs, and the day before I think I shipped close to 2,000 PRs — and this is whilst I was in China, for reference, working from a hotel room on a laptop; half of those were from my phone on Telegram. So again, using the harness to build the harness. [seg 505–505]

But there's always some bottleneck, right? We can go as fast as we want, but we're always going to be limited by something. In my world, the limitation wasn't "can we get the PRs automatically merged, can we get the harness to do all the work." The limitation was actually around proof: how do we know that this thing is working, or is ideal? Yes, we can write unit tests; in some cases humans can verify it, but that's very slow〔?〕. Our release process is very heavily automated around AI being a factory, but there's always going to be this bottleneck. And in some cases that bottleneck isn't around testing; it's just the capacity to actually test — how many PRs can my machines verify and land onto the codebase at once. There is a theoretical limit to this. Being one of the fastest-moving open source codebases on GitHub, we realized this pretty quickly. We hit every single rate limit with every single company and provider you can possibly imagine. [seg 505–505]

So I'm still waiting for proof. I'm trying to merge this PR, my agents are working, but they're waiting for proof — they're waiting to validate that this thing actually works. In some ways they're writing a test, or they're putting it into Telegram or into some virtual environment, clicking and verifying it works. I'm waiting, so while I'm waiting I'm spinning up another agent. But there's a cost to this, right? I'm trying to land a change, and the faster I can land these changes, the faster the other agents can make use of them, because the harness is being used to build the harness at the same time. We're essentially building the plane whilst we're flying it, so the quicker we can make the plane faster, the better it's going to benefit everyone. But there is a snowball, there is a bottleneck to this. [seg 505–505]

A good example of this: Peter tweeted this, I think back in September. This is a new version of OpenClaw we call version two. It's a multiplayer environment, and we have things like computer use, fully open source; we have virtualization, many cool features. But we wanted to improve the computer use feature, so what do we do? We put Doom inside of it. We got the agent to play Doom, and then we sped that agent up in a loop: every time it found something that made it slow, make it faster. If the game moves faster, it's able to complete the game in a much better way, because the agent is aware of this game already. If it can win, if it can scale, it can move faster; the latency goes down, the agent's going to improve. But that latency improvement we're trying to drive is going to drive a better product outcome. It's ultimately going to make OpenClaw a faster harness, which is going to make it better for us as engineers using OpenClaw to build OpenClaw to reap the benefits. [seg 505–505]

So we have these two concepts. We have background work, where there's a clear attempt at something we're trying to do: we check it, we make an improvement, and we continue doing this. This is traditional loop engineering as we know it. But we also have this concept of foreground work. These might be features or things you're working on that require a lot of human attention. Even in these cases, more and more I'm getting to a point of asking: how can I define the proof or the outcome before the actual work happens? So a lot of my engineering effort in foreground work has shifted, and the background work just happens. Right now, if you look at the OpenClaw repository, at the Git commits, it's probably shipping code as we speak. I've got a laptop down here and my phone on me, and it's probably shipping code as we speak. In terms of background work — particular fixes and issues that can be validated — it's going to automatically test, validate, and merge. [seg 505–505]

But the shift here has been: in the past we did what is known as loop engineering. I started speaking about this concept of intent engineering, because the loops were good but they just didn't quite deliver what I wanted; they didn't match my intent. So the question became: how do I inject my intent, my behavior, my understanding, my outcomes into the harness or into the model? A lot of this is things like one of the systems we have, ClawSweeper, which is essentially our review agent that runs across every PR and issue, and which is also open source — our entire infrastructure is open source, by the way. The intent engineering part would go out and try to validate and sense-check, but even then things would regress, things would break after release, things would go wrong. [seg 505–505]

What I'm actually saying is we're moving from this concept of intent engineering, which I was speaking about and others have spoken about earlier this year, to concepts around proof engineering. How can we create proof as code? How can we tell machines that this is an ideal outcome and it's verifiable? This concept of proof engineering is essentially what I've realized I'm actually doing more of: how can I teach the machine that what it's done is valid? If we can prove that validity, then we can start to loop on this much better. So essentially I've gone from factory manager to what I'm calling proof engineer — or essentially a vibe eval guy. A lot of the proof engineering work is around evals, which I'm going to speak to in a minute. [seg 505–505]

So what we're trying to do here is choose a hill, and make climbing that hill cheaper. Once we can define the proof, or the reward, or a mechanism to create the task or whatever that outcome is, in a very clear manner that agents can understand, the question then becomes: how can I get the agent to that outcome as quickly as possible, and make that as cheap and as fast as possible as well? A lot of you have been speaking about harness engineering today, and we're seeing a lot of this sort of work. But I want to go beyond just "let's look at SWE-bench or code bench〔?〕 or whatever this benchmark is," and actually understand what this means in practice. Take the Doom example: was it able to play the game, was it able to get faster? With the CI/CD stuff, which I'm going to speak to in a little bit: did we catch the regressions? Because what we're trying to do there is make the CI cheaper and faster by turning off certain tests and doing some smart stuff, but we're doing it at a cost — we're hoping it's not going to cause a regression. We're skipping stuff, we're using common sense, we're like, "well, I know what's going on." [seg 505–505]

Can we teach models now, using computer use and other factors, to actually go in and behave like a user, use the product, and see if it actually works — to generate that proof? And then can it learn from that proof, cache that proof, and understand it, so the next time it encounters something similar it's able to act on it as well? It doesn't necessarily have to come from one particular PR; it might have seen something in another PR and learned from that. [seg 506–509]

So essentially we're going from this sort of feedback, where we want to close the gap when it comes to failure, and what we also want to be able to do is create this mechanism for hill climbing. You can call it recursive learning, you can call it looping, you can call it whatever you want, but essentially once the agent can understand this reward mechanism, it can understand my intent, and it has a way of verifiably understanding whether the task or outcome you wanted has happened — then we can just let these things run wild. Obviously there are some limitations, right? Some of these tasks might be novel, or in areas that we don't understand yet, or that the models have not been exposed to. But if it's something like making the UX better, or making the product faster in some areas, maybe there are some real quick gains we can make. [seg 510–517]

## Case study: CI cost and cycle time

An example of this was our CI. This is one month at the peak: we were spending about 1.27 million US dollars on just testing. For some of you this might be tiny, but for a team of, what, 5 or 6 engineers, as a nonprofit foundation, this is astronomical. Obviously the majority of this is compensated — sponsored compute that we receive from various companies, which we're grateful for — but free money and free compute never last, right? Eventually the lights have to go out. [seg 518–523]

So I was tasked with this, and my concern wasn't the cost of the compute; it was that more and more tests were being added by agents as they were coding. Many people here have gone, "let's just delete the tests." Well, if we delete the tests, then we have no way of verifying the agents have actually done any work, so that's not an option. Well, we can get rid of some tests — we did that, and that made things faster. But how can we actually speed things up? Because if the tests take too long — yes, they're cheap, they might run for 30 minutes — then I'm waiting 30 minutes on every single PR. This starts to slow down the whole entire factory, and I want to make the factory move fast. [seg 524–534]

There's this concept I'm going to talk about, cycle time, which comes from engineering metrics like DORA, which is used for measuring engineering performance. And these can be applied to agents as well. Agent cycle time looks at the time from when the PR was opened to when the PR was merged, and we track this over time. We want to see that number go down, because if agents can ship code faster, it means I can ship more agents with more code, and that becomes a compounding effect. If the factory slows down, the factory can't fix itself, so there is a point where it becomes unusable. [seg 535–542]

So bringing the CI cost down was one component, but we also had to bring the speed up, and usually those two things don't go hand in hand. On the left we have the number of CI jobs. We see that, yes, we're now running fewer jobs because of all the changes we've made, but at the same time the price of the jobs does go up, because we're adding more complexity, or we're spending more compute to make things faster. So those two things are asymmetrical, and they don't tend to go well together. We also have this problem where creating more work for ourselves doesn't equal more proof; it actually becomes worse. What we've noticed is that the more and more code we were shipping, it actually reached a point, I believe about a month or so ago, where the volume of commits actually eclipsed and started to become a real bottleneck for us. When we looked at that, we started seeing things slow down a little bit. [seg 543–551]

So one of the main factors in fixing this was that we turned off CI checks on main entirely. What happens now is you have a limited check that happens on a PR, the agent goes through the review process — there are some smarts in there about how often it reviews and when it doesn't — and then once that PR is merged, main doesn't do a CI check. That happens every, say, 30 minutes to an hour, and we have some more extensive testing that happens as part of our release process. Now, the more interesting thing I'm going to get to a little bit later. [seg 552–557]

You see on the left-hand side, the total cost of the runs has started to go down. 100 CI runs was costing us about 1,000-something US dollars, and we've been able to get that down to 200-something dollars, which is good. On the right-hand side you can see the time taken for CI. Yes, we've made the optimizations: the big spikes we were seeing, where it was taking 20 to 30 minutes to run a PR through CI checks — it no longer takes that long. The actual total time for a PR to get merged was something like an hour or two hours at the peak, because we run other agents doing security checks and things like that. So bringing the time down was critical for us, but keeping it cheap was also critical. [seg 558–564]

## Adaptive testing: a model of proof

Now, the real question actually became proof. If we had a more systematic way to understand the proof, in theory we wouldn't have to test everything every single time. We can be a bit smarter, actually understand what was affected, and only test that part. This concept is known as adaptive testing, where your tests adapt to the environment they're testing. It's a little bit different from just "hey, see what code changed and let's just test that." This was merged into our main codebase in the last few days and hasn't been fully activated yet — because my compute bill is about to arrive next week, so I've got a few more days to solve this problem before the compute becomes a problem. [seg 565–575]

Essentially, what we're doing here is building a model of proof, using classifiers and tree-based classifiers, to see — based on the code that was changed and what was executed — whether we can get a good understanding of what has a likelihood of regression, and then just test that component. By doing that, we're able to get the same hit rate of finding failures with just a very, very limited subset. This was before this huge change〔?〕 even happened. So what I'm hoping for is something close to a 90.5〔?〕 to 98 percent reduction in our total CI cost, and that's going to enable us to continue to hill climb across a number of other factors as well. The other component, like I mentioned, is understanding what was changed and getting a bit smarter around that, which is going to drastically speed things up — and also the order in which we run the tests. [seg 576–585]

## ShellBench: a benchmark for personal AI agents

Going beyond this: I talked about hill climbing, and CI was one example. But what we've actually been doing in the background, working on for the last two or three months with a number of partners, is building our own benchmark for personal AI agents. It's called ShellBench, and it's going to be released hopefully in the next few days — I keep putting my word on that〔?〕. It's 135 tasks, and a small subset will be public. This was our way of ensuring that we had a way of measuring the proof. It was designed by humans and covers a number of tasks, like tax returns, or what happens when two different people disagree on an outcome. These were a bit more ambiguous, and that level of ambiguity enabled us to test things like the harness, the memory, the messaging. By doing so, we could see at a grander scale whether we were getting worse or better as a product, and we could run these tests in a shorter space of time, rather than every day or every hour doing crappy unit tests that don't add any value. Can we run real benchmarks? [seg 586–597]

One thing we're seeing a lot of companies doing now is developing their own internal benchmarks. Try to stay away from synthetics and spend time building real datasets if you can. As a team we're going to continue to develop this, and this benchmark will be made public and cover a range of harness and model combinations, for coding agents and for non-coding agents for personal use. [seg 598–601]

So we talked about computer use, we talked about CI, we talked about UX changes. These are some of the ways we can take an existing loop, provide much better feedback, and by doing so start to engineer the proof into the system. [seg 602–603]

## What's next: mapping proof onto the codebase

An example of what's to come — these are some of the experiments I'm working on; this is a screenshot from two or three days ago — where we take a traditional index of a codebase. This is the OpenClaw codebase. What we've done is start to map out the proof components, or the areas of slop and high regression, using some of the stuff we're using for our CI engine. The little models that are helping us create better tests and decide which tests run and don't run — we can actually learn from them over a simulation going back, say, the last two or three months, and map this out onto our codebase. So one of the experiments I'm now running is: can this data be used to drive agents to go back and essentially de-slop the codebase, and change parts of it? Again, once this is stable and has been verified, it will also become an open source contribution to the community. [seg 604–613]

So lastly, just to reiterate: you want to turn recurring pain〔?〕 — not just a single pain that you have. In our case, the factory we'd built was working really well, but eventually that factory slowed down, and it was no longer working to my expectations. The factory couldn't build other factories, which was our biggest pain. So you want to turn that into a better machine. For us, going from the factory to Lobsterville was essentially creating these deeper levels of agentic engineering, and we're now going into the space of proof engineering: how do we get models and harnesses to better understand whether what they're doing is having a real-world impact, and is verifiable to some extent? Thank you. [seg 614–622]
