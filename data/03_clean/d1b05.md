Good afternoon, everyone. I'm Peng from Meta, Instagram Edits. In this talk, I'm going to cover how we enable agentic mobile verification on Edits. Edits is a video editing app — you can think of it as something like CapCut — providing video editing capabilities on mobile. [seg 703–707]

## Why agentic mobile verification

So why do we need agentic mobile verification? Agents are already able to operate a phone nowadays. For example, agents are already very good at doing simple operations. In this flow, it's basically just opening the display settings: the agent checks the screen, takes a screenshot, finds the useful stuff, taps, reacts, and decides what to do next. It's doing a very good job for simple daily operations. [seg 708–719]

However, in our case, Edits is a video editing app. It has lots of states and lots of gestures, and agents are pretty bad at gestures, especially multi-finger gestures or combinations of gestures. For example, let's say we are trying to zoom in or zoom out on a sticker, and the agent tries to figure out how to do that. Another case is a drag and drop, which usually involves a long press on a certain UI component, maybe for one second, then dragging, moving, and dropping it at a certain position. Agents are quite bad at this, because they have no idea how to compose all those operations, and at each step they need to think, which makes those combinations impossible. [seg 720–729]

The third case is hidden state, which applies to all mobile applications. For example, let's say we export a video from Edits. We tap the export button, but from the UI we really cannot tell whether the export really happened. Did the export finish? Does the file have the right configuration, 1080p 30 fps? Are there any internal errors? We cannot tell that from the UI. [seg 730–732]

## Making the app observable

So basically, current UI validation has the agent operating the app like a user. But to have it do actual engineering work, we need to provide an engineering view to the agent. In this case, we want to answer those questions — did the export really finish, is the file 1080p, are there any internal errors — and that's really hard to tell from just this UI. [seg 733–734]

But if we add more information — basically expose that information to the agent — for example, on top of the UI we provide the accessibility tree and component semantics, we expose the app state and the configuration of the output file — then the agent is able to answer those questions. Did it really finish? It can check the app state. Is the file 1080p 30 fps? It can go to the app storage and do a real validity check. Are there internal errors? It can just check the logging. [seg 735–737]

So by making the app observable, we provide an engineer's view to the agent, so the agent can operate the app much more efficiently, more like a developer than a normal user. [seg 738–738]

Here's another example, taken from our real world. In this case, we are trying to set the speed of a certain video to 2x. To set it to 2x, we basically need to adjust the slider. For an actual user it's easy: you drag this knob here and it's 2x. But for an agent it's surprisingly difficult, because it has no idea how the slider percentage maps to the actual speed value. In reality we found the agent keeps guessing: it slides a bit left, then right, then left, then right. In our experience it usually ends up with around 10 tool calls, and it costs lots of tokens and screenshots. It can get there, but it usually takes a very long time, which makes it 〔?〕 for useful validation. [seg 738–738]

So how do we fix this? We expose the semantics on this slider. This is a code snippet from Android Jetpack Compose, and what it does is provide the semantics of this slider — basically telling the agent that if you scroll to this percentage, this is the speed it maps to. By exposing the semantics, the agent knows how to do the proper scrolling. It can use one tool call instead of nine or ten, and it works out of the box. By our evaluation, it reduced tool calls on average from 38 to nine 〔?〕 and reduced tokens by over 90%. [seg 738–738]

## Semantic actions

The next thing here is semantic actions — for when observability in itself is not enough. Let's go back to the drag and drop example: say we're trying to long press here, drag, and drop. It is so difficult for the agent to do a combination of those gestures that it doesn't help much even when we have all those test IDs and the accessibility tree. So what we ended up doing is building a CLI — something like `edits reorder-clip`〔?〕 — where we give it the clip ID and the destination index, and by calling this CLI the agent directly finishes the reorder action in one tool call. And it can verify whether the action has finished from the CLI response. [seg 739–741]

## The verification agent

So combining discoverability and semantic actions, we built our verification agent. The verification agent is a combination of fixtures and the LLM. By fixtures I mean the deterministic stuff. For example, when doing mobile app verification, we need to do some pre-work: build the app, install it, log in, prepare the test media, and make sure all the gating is working. For those setups we do not need the LLM, because they are deterministic and we don't want to waste tokens there. [seg 742–742]

What needs the LLM is understanding the prompt. Once we finish the setup, we have the LLM interpret the prompt into the CLI and the discoverability tools we just built. For example, the prompt here is: "Create a video editing project from two 1080p clips and export it at 1080p 30 fps." The LLM agent interprets this and calls the corresponding CLI actions — create, select two videos, set up the export configuration, and start exporting — and at each step the agent checks the response from the CLI to make sure each step is proceeding correctly. Once the LLM execution is finished, we do the teardown, which is also deterministic, to make sure each verification run is isolated without interfering with each other. [seg 742–742]

## What it unlocks

In the next few slides I'll cover what the verification agent unlocks. The first is the inner and outer loop. By inner loop we mean that when writing code, the verification agent verifies the output of the coding agent, meaning it can fix itself — it can verify its changes and keep coding until it reaches a certain goal. By outer loop we mean that for every eligible change, we run verification in continuous integration to make sure the code being checked in is tested. [seg 743–744]

This example is testing video effects. In Edits we have lots of video effects, and due to the limited bandwidth of QA, in the past we could only test 15 video effects a week. But now, with the verification agent, we can wrap the agent call in a for-loop script, run each verification one by one, and have a validator verify the output. In this way we compressed the entire testing from maybe eight weeks to around three hours. [seg 745–746]

Another example is an editing 〔?〕 audit. In this case we want to make sure our app works great in Hindi, because about 4% of our users are Hindi users. But I don't know Hindi, and I don't know how to verify that — but large language models are particularly good at understanding languages. So we just asked the agent to exhaustively explore the app, check each screen, run the same flow one by one, and compare the English and Hindi UI side by side. In this way the agent was able to run 70 hours continuously, take around 2,000 screenshots, and produce over 200 findings with evidence, and generate a report. We had the report reviewed and verified by our engineers and content designers. This basically compressed what used to take maybe a quarter into around two weeks. [seg 747–747]

The last example is the self-improving verification agent. Because we have all those verification runs, and each verification run has telemetry, logging, and all the output, the agent is able to read its past telemetry and understand what is missing. For example, in mobile verification it might be missing a certain test ID or a certain semantic action, and the agent is actually good at analyzing what is missing and suggesting to add it. We have another agent scanning all those failures every day and proposing diffs to improve the agent. Humans review those diffs, and once the diffs get landed, they improve the verification agent, creating this flywheel. In this way we were able to improve the conclusive verification 〔?〕 rate from around 10% in the beginning to around 55% currently, in one month. And we are now running about 1,000 to 2,000 verifications every day. [seg 748–749]
