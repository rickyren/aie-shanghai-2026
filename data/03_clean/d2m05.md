## How voice agents work

So step back a bit. Let me explain a little bit how voice agents work. A good way to think about it is a voice agent is a pipeline. Audio comes in one end, and it's processed step by step. So a basic voice agent might have Daily to transport the audio, and then it'll use a speech-to-text processor to turn that into text, and then it'll use an LLM to generate some more text, and then another text-to-speech processor to create the voice, and that goes through another audio transport back to the user. [seg 913–918]

Now, Pipecat, which is the open source library I work on, is the glue that holds this all together. So you can use any processor you want. So for example, I'm at Deepgram, so you could use Deepgram for speech-to-text, you could use Deepgram for text-to-speech. Or maybe you wanna run this on a Chinese LLM on-device, or maybe you wanna use MiniMax for speech-to-text, text-to-speech. Pipecat doesn't care. It's completely open source, completely vendor-agnostic, and completely free to use. [seg 919–926]

## Agent loops, judges and evals

So I can't build this application on my own anymore. I've hit peak. So what I can do instead is I can build an agent loop to build the application for me. An agent loop is when an agent does the work, checks the result, and then keeps going until a condition is met. So this is kind of similar to test-driven development, where we wrote unit tests by hand first and then wrote the code to check if the unit tests pass. The tricky part here is, how do we test something without a clear answer, and especially when it's in Chinese? [seg 948–952]

Well, that's where judges and evals come in. So a judge is an LLM that reads a finished conversation and answers a yes/no question about it. So if you think a unit test checks, "Did 1 plus 1 equal 2?", a judge might be something like, "Was this voice agent polite?" So you would use an LLM to read the response and check that. [seg 953–958]

Now, an eval goes a little bit further. It lets you check an agent that says something different every run. So you could run an eval 10, 20, 100 times and see what percentage of the time it passed the check. [seg 959–961]

To go even further, evals can be scripted ahead of time, or we can give instructions to a third LLM to act as a simulation. So the way I like to think about it is, a scripted eval is like someone doing stand-up comedy. You write all the jokes in advance, and then you recite them. And then a simulation is more like improv. You give a general bit of information, like, "Oh, you're on a boat," or in this case, "Oh, you're working behind the counter at a bubble tea store," and just let it go wild. [seg 962–967]

So we can evaluate voice agents using a combination of all three. Tests are great for catching deterministic issues. Scripted evals are great for when there's specific cases we wanna check. And simulations are great when you actually don't know exactly what to check for. So that's the solution to number one: how do we check something when we don't know all the edge cases? [seg 968–972]

So I asked Claude to check the Pipecat docs and write a Pipecat audio simulation to simulate a Chinese speaker being really undecided when they're ordering their bubble tea. This is what it generated. You can see some of the Chinese characters there. Obviously, I'm not quite sure what this says, but luckily, I can have the success criteria written in English. So I don't necessarily need to know the test, but I can double-check the success criteria. [seg 973–980]

## Text mode vs. audio mode

So we can run these evaluations either in a text mode or audio mode. Text mode is way faster because you don't have to generate any of the audio. It also means you're using very few tokens, and you use basically no tokens if you're using a local LLM as a judge. And audio mode uncovers issues that text mode just won't surface. [seg 981–985]

So a great example is this. When I was running audio mode, I discovered there was a bug in the speech-to-text processor. Sometimes when I said "qu bing" (去冰), which means no ice, it heard it as "two 瓶", which is like a weird mix of English and Chinese. It was saying "two bottles."〔?〕 And that's an issue that a pure text mode test just would never have caught. [seg 986–991]

And that's problem number three. I don't have to speak the whole call every time anymore. I don't have to manually test this. I can run 10, 20, 100 simulations all at the same time every time I make a small change and see if that's improved my voice agent. ## Think in loops

So as Claude builds the checks, it adds new features and fixes bugs, which produces more checks, which adds new features and fixes bugs, which produces more checks and adds new features and fixes bugs. That's the loop. So machines are doing the work, judges are checking the work, and then humans check the judges. [seg 1004–1008]

So whatever you're building, I really challenge y'all to start thinking in loops. I've already got the bubble tea voice agent handled, so you're probably not gonna be building that. But the same ideas apply for any sort of agent where you don't have business domain expertise. So for example, you might be building an outbound sales agent selling insurance, but you don't know anything about insurance. You could tell the LLM to act like an insurance agent. You might be doing inbound support for an auto shop, and you don't know anything about cars or being a mechanic. Again, you can give the LLM a scenario to act like a mechanic. Or you could even build a voice agent to control a robot and go through and test simulations with that. [seg 1009–1016]
