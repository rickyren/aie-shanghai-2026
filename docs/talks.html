Agent Infra
身份与权限
Agent 身份的价值不在拟人化互动，而在让 agent 跑在独立安全上下文里、按最小权限约束，才能从根本上防止它越权；随着 agent 之间开始自发协作，行业必须用 rubric 评测和模拟环境来严格测试它们。
Agent harness / 运行时与沙箱 评测与可验证性
骨架
  1. 主流厂商（Meta Muse、OpenAI dots、Claude Tag、Gemini agent）都在给 agent 配身份，但 Meta 是为了拟人化和提升互动、变现，Microsoft 是为了安全。
  2. 让 agent 冒充用户（on-behalf-of）很危险：它继承用户全部权限，权限开关在 harness 里形同虚设，agent 总能绕过（shell、写 Python）。
  3. Microsoft 的做法：Autopilot 有自己的 Entra ID、邮箱、Teams、OneDrive，在独立安全上下文中按最小权限运行，由 Agent 365 统一管控。
  4. 接下来 6–12 个月 agent 之间将出现无编排的临时协作，测试负担上升：需要基于 rubric 的评测和模拟世界（OpenEnv）来隔离测试每个 agent。
讲者提出的框架
  • agent 身份的两种目的与深度：Meta 的身份只是名字深度、为互动变现而拟人化；Microsoft 的身份是系统级（Entra ID、邮箱、文件空间），目的是独立安全上下文与最小权限。
  • 幼儿园 vs 高中：编排式协作 vs 临时协作：现在的多 agent 是人来编排的幼儿园玩伴会，接下来 agent 会像高中生一样自己发起协作（ad hoc / unorchestrated collaboration）。
推出 / 提供
  • Microsoft Autopilot（有独立身份的 agent）：Copilot 的演进，拥有自己的 Entra ID、邮箱、Teams 和 OneDrive，可开箱即用或基于 Foundry 自建。
  • Microsoft Agent 365：agent 管理控制台，管理员可建 agent 模板、设定权限类别，用户据此创建实例。
为什么需要

相对于让 agent 冒充用户（Copilot、ChatGPT 等 on-behalf-of 模式）以及 harness 内可选的权限开关，独立身份让权限由身份系统在外部强制执行，agent 无法通过 shell 或写代码绕过。

非共识
  • agent 身份的真正用途是安全隔离而非拟人化；harness 内的权限开关不可靠，因为 agent 无所不用其极，只有身份层权限才真正约束得住。
  • 未来 6–12 个月 agent 将自行发起互相调用的协作，不再由人编排，测试需要为每个 agent 模拟一个“母体”式的世界。
信号
  • 市场格局 / 规律Meta、OpenAI、Anthropic、Google、Microsoft 都在推出带独立身份的 agent，但商业逻辑分化：消费端靠互动变现，企业端靠安全治理。
  • 市场格局 / 规律企业 agent 分为自建（Foundry）与开箱即用（Autopilot）两类，由 Agent 365 这类控制台统一管理，形成 agent 管理平台这一新层。
  • 数据信号模拟环境（OpenEnv，Hugging Face 与 Microsoft 等联合）成为 agent 测试与训练所需的新型数据与基础设施供给。

数据与训练
模型与数据 Infra
agent 架构已收敛到 coding-agent 模式，其产生的 trace 量远超人力可读，所以需要用 coding agent/后台 agent 在“压缩成 trajectory、聚类、排序”的数据之上自动跑“发现失败—写 eval—改—回测—发布”循环（Langfuse 做这个观测与评测底座）；人只保留对质量的定义、可信反馈信号和发布决策。
评测与可验证性 Agent harness / 运行时与沙箱
骨架
  1. agent 靠迭代改进而非事前写验收标准：跑起来、读 trace、修复、写测试，循环往复，更像手艺而非科学。
  2. agent 架构从直接调用、链式、RAG、agent graph 回到“模型+工具+沙箱+文件系统”的循环，本质趋同于 coding agent；Halo 是其内部参考实现。
  3. 人工读 trace 已不可扩展：先把 trace 压缩成 trajectory、摘要、聚类、排序（面向数据的渐进披露），再交给 coding agent 处理。
  4. 未来由后台 agent 接管改进循环，人保留质量定义、可信反馈信号和发布决策；循环产生的标注数据可进一步用于自建 RL 环境。
讲者提出的框架
  • 面向数据的渐进披露：trace 先压成 trajectory，再用小模型按领域维度摘要，嵌入聚类并排序，只把最严重的完整 trace 交给 coding agent。
  • 人机分工：agent 跑改进循环、人守质量：默认形态的任务可由 agent 自动改进，定制或超前沿任务仍需人写 eval 与 skill；人负责定义好坏、反馈信号和发布。
推出 / 提供
  • Langfuse：开源的 agent 评测与可观测平台，帮助开发者理解 agent 行为并在生产中改进。
  • Halo：Langfuse 内置 agent，帮助用户读 trace、发现问题，运行改进循环。
为什么需要

人工读 trace、手写 eval 的改进循环依赖稀缺的工程师时间，且 trace 体量已超出人和单个 coding agent 的上下文；需要在可观测平台上先做数据压缩再交给 coding agent，而不是直接把原始日志喂给它。

非共识
  • 最佳团队下一步会用改进循环产出的标注构建自己的 RL 环境，训练开源模型，在自身任务上做到饱和。
  • 前沿智能已足够解决许多问题，瓶颈在 agent 的可靠性而非智能。
  • agent 循环放在后端 worker 里，沙箱只作为一个按需调用的工具，以节省沙箱算力成本。
信号
  • 数据信号运行改进循环产生的 eval 与标注构成应用专属数据集，领先团队把它转化为任务、verifier 和 RL 环境。
  • 市场格局 / 规律可观测与评测平台的角色正从“给人看 trace”转向“为 coding agent 提供经过压缩的数据层”（MCP/API/CLI 接入）。
  • 市场格局 / 规律agent 架构趋同为 coding-agent 模式（工具循环+skill+沙箱+文件系统），并扩展到子 agent 与常驻的 ambient agent。
  • 关注的指标关注 agent 可靠性与失败类别（如工具调用报错），以失败 trace 而非整体分数驱动改进。

独立讲者
当 AI 能把一切做得又快又完整，真正稀缺的是自己的判断和在乎：好的 AI 工具应像工作台一样让人看得见计划、随时介入、小步修改，而不是只给一个让人只能接受或拒绝的成品，使用者也要保留选择何时不用 AI 以及与他人共创的空间。
个人 agent 与 AI 原生产品
骨架
  1. 当 AI 让人什么都能做，焦虑来自用自己能做什么证明自己；做事应回到好奇与在乎，而不是跟随别人的产出速度。
  2. 完整的 AI 答案会让人跳过自己的思考；知道自己想要什么常常是动手改一处之后才浮现的结果。
  3. 工具应该是可介入的工作台而非只交付成品的服务窗口，让人看见假设、小步修改、能拿回控制权。
  4. 工具一直在不代表一直要用，生活是创作的来源；与不同的人一起做东西像爵士乐团，才能让人被改变。
讲者提出的框架
  • 服务窗口 vs 工作台：服务窗口只交付成品，用户只能接受、拒绝或重新解释；工作台让用户看见计划、在动作前介入、事后用预览微调，从而接触正在改变的东西。
  • 工具设计三个小起点：让重要假设可见、修改小到可放心试、交出去的工作可拿回；不是只有接受或拒绝整个答案；拿掉阻碍而不是拿掉人形成判断的过程。
非共识
  • AI 时代的风险不只是错答案，而是完整答案替代了自己的思考；想清楚往往发生在动手之后，而不是之前。
  • 工具设计的透明不等于让人读每一行代码，而是想理解和想改的时候有入口；聊天也可以是工作台的一部分。
  • AI 容易回应的世界会让人失去与不同的人建立默契的机会，工具不应只让每个人更高效地待在自己的小世界。

You.com
Agent Infra
搜索与数据 API
You.com 把自己定位为 AI agent 和模型公司的搜索基础设施，并用与 NVIDIA/CoreWeave 后训练 Nemotron 的案例说明：用其 web graph 和搜索 API 生成经难度过滤的小规模可验证 RL 数据，就能让开源小模型的网页研究能力显著提升。
开源模型与后训练 / 推理工程 记忆、数据与上下文工程
骨架
  1. You.com 是为 AI agent 和 LLM 构建的网页搜索引擎，通过 Search、Contents、Answers、Research 等 API 以及授权的结构化数据提供，主打企业级规模、零数据留存和与模型公司的合作。
  2. 亚太负责人强调在亚洲设立总部和团队，服务中国模型公司与互联网大厂出海及全球实时信息接入，覆盖性能到成本的整条帕累托曲线。
  3. 案例：与 NVIDIA、CoreWeave 合作后训练开源 30B Nemotron，用 You.com 的 web graph 取中等热度网页生成难题，经难度过滤后做 SFT + RLVR。
  4. 结果与流程：很小的数据集和短时间训练即带来 BrowseComp 明显提升，且模型学会验证、减少工具调用；总结为强工具、真实网页造题、难度过滤、SFT、GRPO、度量准确率与效率的通用配方。
讲者提出的框架
  • 搜索型 agent 后训练通用配方：强工具起步，从真实网页造题，按难度过滤，用自有轨迹做拒绝采样 SFT 再 GRPO，最后同时度量准确率与效率。
  • RL 数据按热度与通过率筛选：取中等热度网页以避开模型已记住的内容和长尾垃圾，用 pass@8 过滤掉全对或全错的题，保留 1 到 7 次通过的题。
推出 / 提供
  • You.com Search / Contents / Answers / Research API：为 agent 和 LLM 提供全网搜索、整页内容抓取、多轮扇出研究，以及 World Bank、S&P、Polymarket 等授权结构化数据。
  • 模型公司搜索合作与后训练数据服务：为模型预训练、后训练和推理时联网搜索提供数据与搜索，案例为联合后训练 Nemotron。
为什么需要

对比 Baidu、Google、Bing 等面向人类设计的搜索引擎：agent 查得更快、消费信息更多，需要专为机器设计的搜索，并满足企业零数据留存、海量查询与实时 SLA 要求。

非共识
  • 搜索 agent 后训练中，RL 数据集的质量比工具或环境更重要，小而精的数据集即可达到比其大几倍的数据集相近的收益。
  • 只奖励答案正确性也会带来效率提升的副作用，模型学会验证后不再继续无谓搜索。
信号
  • 市场格局 / 规律搜索供应商把自己定位成模型公司的搜索伙伴，向上延伸到为开源模型做搜索后训练，并在亚洲设点服务中国模型公司和出海需求。
  • 数据信号RL 数据直接由搜索供应商的 web graph 与网页内容合成问答，辅以开源数据子集并做去污染，不依赖人工标注。
  • 关注的指标同时追踪 BrowseComp 准确率与工具调用数和 token 消耗，既要更准也要更省。
  • 市场格局 / 规律称机器搜索量已超过人类搜索，搜索被重新定义为面向 agent 的基础设施。

模型与数据 Infra
Baseten 提供覆盖编排到基础设施的全栈开源模型推理服务（serverless API、专属部署、微调），主张企业应在开源模型上掌握自己的客户信号和性能，而推理性能必须靠单节点优化与跨集群编排的整套垂直栈才能达成。
开源模型与后训练 / 推理工程 偏宣传
骨架
  1. 开源模型采用在过去一年多快速增长，企业按成本、规模和数据护城河分别选择 serverless API、专属部署或微调，开源推理也是避免权力集中的生态基础。
  2. 推理要在延迟、吞吐和成本之间权衡，单节点靠 prefill-decode 分离、量化、投机解码等技术。
  3. 生产环境是跨云跨区域的系统级编排：按 KV cache 命中路由、扩缩容、故障转移。
  4. Baseten 覆盖从编排到基础设施的整条垂直栈，各层必要但单独不充分。
讲者提出的框架
  • 开源模型三种采用路径：关注成本用 serverless API，规模化用专属部署，数据是护城河则微调开源模型。
推出 / 提供
  • Baseten 推理平台：开源模型的 serverless API、专属部署和微调，覆盖从编排到基础设施的全栈。
为什么需要

相对于闭源前沿模型 API 以及直接从 Hugging Face 下载权重自行运行的未优化基线，开源推理平台可降低成本、保留客户信号，并通过全栈优化取得高性能与高可用。

非共识
  • 把开源推理视为防止 AI 权力集中、避免赛博朋克式未来的生态基础设施，而不仅是技术或商业选择。
  • 企业微调开源模型的一大动机，是不再把客户信号无偿交给闭源模型厂商改进其产品。
信号
  • 市场格局 / 规律开源模型在 OpenRouter 上的 token 消耗已超过闭源模型，并且差距仍在扩大。
  • 数据信号客户使用产生的信号被视为企业核心资产，开源微调让企业自己保留而非流向模型厂商。
  • 关注的指标同时关注 TTFT、token 间延迟、单 GPU 聚合吞吐、P90 延迟和可用性，说明其卖点是企业级性能与稳定性。

数据与训练
评测与 RL 数据
Arena 把消费者产品当成评测数据工厂：用 agent mode 的真实长任务会话做随机对照实验来评 agent，再把评测、私测和 rubric/RL 环境卖给模型公司，形成评测到后训练的闭环。
评测与可验证性 记忆、数据与上下文工程
骨架
  1. Arena 靠数百万真实用户的并排对战投票做评测，避免静态基准易被刷、易饱和的问题。
  2. 评测 agent 更难，所以 Arena 自己做了 agent mode 产品，并用随机分配编排模型的随机对照实验，从真实会话轨迹中挖掘成功率、夸奖/投诉、可引导性等信号打分。
  3. 结果：美国前沿实验室领先，中国开源模型在性价比帕累托前沿上有位置；并在做对齐指数、harness 评测、用户模拟器自动评测。
  4. 最终面向模型公司卖共同发布、私测，并把轨迹转成 rubric 和 RL 环境，形成从评测到后训练的闭环。
讲者提出的框架
  • 随机对照实验式 agent 评测：每个 agent 会话随机分配编排模型，使各模型面对可比的任务分布，再从轨迹中用 LLM 评判加人工整理提取五类信号汇总成分数。
推出 / 提供
  • Agent Arena / agent mode 与榜单：类似 Manus 或 Genspark 的 agent 产品，同时产出 agent 能力榜、性价比帕累托前沿和对齐指数。
  • 模型公司服务与后训练数据产品：联合发布、联合营销、发布前私有测试，以及由轨迹生成的 rubric 和 RL 环境，另有用户模拟器自动评测。
为什么需要

静态基准用预定义题集，容易被刷也容易饱和；Arena 主张用真实用户和真实任务的实时数据评测，并把 harness、编排模型等变量随机化。

非共识
  • 评测不再只看能力，加入对齐行为（未授权操作、错误归因、欺骗性完成）并与成本做帕累托比较。
  • 评测平台向上游延伸：把真实轨迹变成 rubric 与 RL 环境，卖后训练数据给模型公司。
信号
  • 数据信号Arena 以消费者免费产品换取海量用户提示、投票和 agent 会话轨迹，这些数据被转为评测榜单、rubric 和 RL 环境出售给模型公司。

个人 agent 与 AI 原生产品 记忆、数据与上下文工程 偏宣传
骨架
  1. 从聊天机器人到云端 agent 再到个人 agent，搜索的用法发生了质变；个人 agent 的关键是跨请求的连续性（记忆、搜索、工具、持久化）。

  4. Exa 索引不止网页（新闻、SEC、播客、POI、天气），并可通过 Exa Monitors 或定时搜索加 browser use 实现按条件才打扰用户的主动助理。
讲者提出的框架
  • 先搜索、再升级工具（search first）：先读搜索返回的 highlights，判断任务还缺什么，再升级到 browser use 等工具，使每次工具调用只针对任务的一部分。
推出 / 提供
  • Exa 搜索 API 与 highlights：独立网页索引加数据合作伙伴，按查询抽取式返回页面中相关 token，避免整页进入模型上下文。
  • Exa 实体索引（POI、新闻、播客、财报、天气）：除网页外，新增大规模兴趣点索引，并覆盖新闻、SEC 文件、播客转写、活动和天气。

为什么需要

相对闭源个人 agent（Muse、Instinct、Grok Bot）把用户信息全交给厂商且无法检视，开发者可用开源组件加 Exa 搭一个能看到记忆内容、工具调用原因和失败时间的版本；相对直接抓整页喂给模型，highlights 只取下一步决策所需的最少 token，适合小模型和快速 agent。

非共识
  • 个人 agent 应以搜索为第一步，只在 highlights 不足时才升级到浏览器，闭源产品大概也是这样设计的。

模型与数据 Infra
Zilliz 认为 AI 数据指数增长使传统数据库像端着不断被灌酒的扎啤杯，必然撑不住，所以把向量数据库升级为以对象存储为底座的湖库：成本接近对象存储、体验接近数据库，并用热温冷分层让 agent 的记忆与 trace 数据能直接用于下一轮训练迭代。
记忆、数据与上下文工程 Agent harness / 运行时与沙箱 偏宣传
骨架
  1. AI 能力每升一级，同任务 token 消耗涨一个数量级；头部业务背后的数据量也逐年上升一个数量级，且合成、模拟数据会让增速继续加快。
  2. 数据量到十倍以内靠服务器内的性能与成本取舍，到百倍千倍后单机架构没有取舍空间，只能围绕对象存储重构，即 lakebase（湖库）。
  3. 湖库 = 数据库的使用体验和性能 + 湖的容量和成本；用本地缓存、远端缓存、对象存储的热温冷三层，让所有数据都能查询，只在需要时把数据提升到热层。
  4. 同一份底层数据同时支撑实时检索、交互式探索和批量挖掘，缩短数据迭代飞轮；下一步是把查询的共性和历史下沉到基础设施，再争取一到两个数量级。
讲者提出的框架
  • 湖库（lakebase）四条定义：使用体验像数据库、容量像湖可无限扩张、单位成本接近对象存储、性能接近数据库，四点合到一个系统里。
  • 热温冷三层与按活跃度分层：本地缓存、远端缓存、对象存储三层成本各差一个数量级，按用户活跃度或查询需要动态在层间提升数据。
推出 / 提供
  • Zilliz 湖库架构（lakebase）：围绕对象存储重新设计的 AI 数据基础设施，在其上承载向量、文本、JSON、标签等语义数据的检索与分析。
  • Milvus：自 2018 年开源的向量数据库，Zilliz 同时提供商业化服务。
为什么需要

相对于继续用传统向量数据库或普通数据库（数据放服务器本地资源上）来扛数据增长，湖库用对象存储的无限容量对抗指数增长，并引用 Cursor 在几个月内换了四套数据库后转向围绕对象存储的架构作为佐证。

非共识
  • 数据增长的真正瓶颈是资源与数据的匹配问题：有限容量对抗指数增长不可持续，必须把假设改为无限容量底座，而不是继续做服务器内优化。
  • 未来数据更多来自生成和模拟，随 token 消耗积累，数据增速在 27、28 年可能进一步加快。
信号
  • 数据信号头部业务背后的数据条目逐年上升一个数量级，来源从现有系统和人转向生成与模拟数据，世界模型、自动驾驶、短剧是典型场景。

  • 关注的指标追踪每 GB 的存储成本与各层服务质量的取舍，并关注数据迭代飞轮的效率。

骨架
  1. LLM 网关看似简单转发，实际 HTTP 200 不等于成功，协议翻译会导致流中断、缓存失效和 thinking block 被静默丢弃。

讲者提出的框架
  • Failover 边界：流开始前可切换，流开始后直接报错：未向用户输出前遇到 429/529 可换 provider；一旦已开始流式输出就把错误交给用户，不做中途切换。
非共识
  • 备用 provider 要长期常态承接一部分流量，而不是只在主路故障时才启用。
  • 明知有更高级的流中途 failover 网关，仍选择尽早失败、由用户决定是否重试，以降低复杂度。
信号

Agent Infra
存储
TiDB 把自己定位成 agent platform 的完整 data layer：用分布式 SQL 存 session meta、可跨 sandbox 的海量隔离文件系统、海量隔离数据库（Starter）和 trace 分析 Lake，加上 checkpoint 与 fork 支撑优化闭环，让 agent 团队不必自建分片、备份恢复和实例池。要点是这一整套并非事先规划，而是被 agent 客户的需求一步步推出来的。
Agent harness / 运行时与沙箱 记忆、数据与上下文工程 偏宣传
骨架
  1. 从一个客户请求（做成评审工作台、明天同事接手、还要持续修改）出发，说明 agent 任务会把数据库逐步推向新需求。
  2. 状态与文件：agent 中断后的 session 快照与事件需要大规模、免分片的 meta 存储；sandbox 被回收后文件需要独立于 sandbox 的持久文件系统，取代自建备份恢复。
  3. 交付与运营：agent 不断产出应用，平台需要海量隔离的数据库；长任务 trace 数据巨大，需要 Lake 做排障与成本、成功率分析。
  4. 改进闭环：用 trace 提问题、checkpoint 保存现场、fork 出分支在同一起点比较改法；最终主张用一套 TiDB data layer 让团队少维护底层，把精力放在 agent 迭代上。
讲者提出的框架
  • agent 数据层四类增长与对应能力：meta 增长用分布式 SQL 免分片，项目增长用持久工作区，应用增长用海量隔离数据库，trace 增长用 Lake 做清洗检索聚合。
  • trace 到 checkpoint 再到 fork 的优化闭环：由历史 trace 发现问题，用保存的 checkpoint 还原现场，fork 出多个分支在同一起点上比较改法，产生新的验收证据。
推出 / 提供
  • TiDB 文件系统（跨 sandbox 持久工作区）：把 agent 工作区独立于 sandbox 持久保存，每个 project 独立空间，支持最小权限与 quota，并可 fork。
  • TiDB Cloud Starter：为 agent 交付的每个应用提供海量隔离的数据库实例，共享底层存储，由 TiDB Cloud 处理权限、用量与计算调度。
  • TiDB Cloud Lake：在对象存储上加载原始 trace，用 SQL 展开 JSON，支持排障定位和批量的质量与成本分析、评测样本准备。
为什么需要

对比自建方案：平台自己做 sandbox 加 EBS 快照备份恢复、多库分片路由、实例池维护和 trace 流水线，工程与运维成本很高；TiDB 用统一 SQL 入口、持久文件系统和海量隔离数据库把这些职责接过去。

非共识
  • 只有 trace 不足以做 agent 优化：trace 只说明发生过什么，必须保留 checkpoint 与现场快照才能做可比的分支实验。
  • AI infra 不是预先规划出来的，而是 agent 客户的真实需求把数据库一步步推向 agent 数据层。
信号

  • 关注的指标客户关注含失败重试的单位成本和任务成功率，而不是只看单次成败，用于判断工具价值与改动收益。

骨架

  • Efficiency Point（效率点）：分子是 provisioned GPU 的月成本，分母是按 token 付费的有效混合单价，得到月 token 量盈亏点，超过才切换到自托管。
