Baseten 提供覆盖编排到基础设施的全栈开源模型推理服务（serverless API、专属部署、微调），主张企业应在开源模型上掌握自己的客户信号和性能，而推理性能必须靠单节点优化与跨集群编排的整套垂直栈才能达成。

演讲骨架

  1. 开源模型采用在过去一年多快速增长，企业按成本、规模和数据护城河分别选择 serverless API、专属部署或微调，开源推理也是避免权力集中的生态基础。
  2. 推理要在延迟、吞吐和成本之间权衡，单节点靠 prefill-decode 分离、量化、投机解码等技术。
  3. 生产环境是跨云跨区域的系统级编排：按 KV cache 命中路由、扩缩容、故障转移。
  4. Baseten 覆盖从编排到基础设施的整条垂直栈，各层必要但单独不充分。

  • 开源模型三种采用路径：关注成本用 serverless API，规模化用专属部署，数据是护城河则微调开源模型。

推出 / 提供

  • Baseten 推理平台：开源模型的 serverless API、专属部署和微调，覆盖从编排到基础设施的全栈。

Latency, throughput and cost

So what do we do in inference? Well, the first thing to consider is your goal: what kind of performance requirements do you have for your workloads? And there are trade-offs you have to consider between latency, throughput and cost. To realize the trade-off, here's a Pareto frontier for running DeepSeek V4.1 Flash on different GPU types. The Y axis is the aggregated throughput of a GPU, and the X axis is the output speed per user request, which is essentially the inverse of inter-token latency. So let's say you're using B200, which is the green line in the middle, to host the model: with different concurrency, you will land on different dots on this line, right? A low concurrency yields a higher output speed for each request but lower overall throughput. If you're running high concurrency, it will give you high overall throughput, but each user will have to wait longer for their request to complete. In the case where you have very high traffic volume and a limited number of GPUs, optimizing for high throughput with a tolerable end-to-end latency could be the right choice. seg 1154–1154

There are many, many inference techniques to improve throughput and latency; here I highlighted a few. Inference engines like vLLM and SGLang are built largely to optimize one model deployed to a single GPU node. The first thing to notice here is that inference can be divided into two stages, prefill and decode. In prefill, on this side, the KV cache is produced along with the first output token, so the prefill stage determines the time-to-first-token latency, TTFT. Prefill is mostly doing matrix multiplication, right, which makes it compute-bound. In the decode stage, it takes the KV cache and recursively generates the next token, so the decode stage determines your inter-token latency, ITL. At every step it reads the updated KV cache, so the memory bandwidth for transferring the KV cache becomes the bottleneck here. And because the requirements for prefill and decode are very different, running them on separate replicas can improve the GPU utilization rate. This is called prefill–decode disaggregation. On the top left, chunked prefill; FlashAttention in the middle; and down at the bottom, the paged KV cache — these are all different techniques that break large chunks of compute and memory into smaller pieces to improve efficiency. Quantization here helps to reduce the size of model weights; you can also apply it to activations and the KV cache as well, and when done properly, you can preserve the quantized model's fidelity to the original full-precision model. seg 1155–1155

Also, different parallelisms can be applied, which distribute model weights and input data to different GPUs for faster inference. Here I highlighted expert parallelism, which essentially applies to MoE models, to host different experts on different GPUs. And lastly, speculative decoding, down in the bottom-right corner, generates multiple draft tokens really, really fast with a small draft model or MTP heads, and then the large target model verifies all the draft tokens in a single pass, for high throughput. At the core, all these inference techniques are really about reducing repeated compute, removing unnecessary operations, minimizing data movement, and maximizing the hardware utilization rate. And that's inference in a single GPU node. seg 1156–1156

System-level orchestration

Today it's very common for an inference provider to serve trillions of tokens in just one hour, right? So inference workloads are obviously not running on a stack of Mac minis under someone's desk; they're running in distributed GPU clusters across different clouds and regions, and customers expect low latency and high reliability with ever-changing traffic patterns. This is a whole system-level orchestration problem. User requests are routed not only by geo-proximity and capacity availability, but also by matching KV cache: if a large chunk of the query has been cached somewhere, routing the request accordingly is a lot faster to get the first token out, and also a lot cheaper for the user as well. And to increase the cache hit rate, the KV cache is offloaded to different memory hierarchies, so more prefix cache can be stored. When the workload exceeds the capacity of existing replicas, the system needs to recognize early that more capacity is needed — often with data residency requirements as well — then locate available clusters across different clouds and regions, warm up instances as fast as possible, and also have failover resilience for any particular cluster. If you don't do any of these, your P90 latency can go through the roof. seg 1157–1157

All these techniques improve inference performance compared to a baseline implementation where you just download the weights from Hugging Face and run them with no optimization. Here are some published performance-uplift metrics from the community: you can realize massive, massive improvements on throughput and latency with any of these techniques, and when you combine all the techniques together, the improvements can be several orders of magnitude higher. At Baseten, we cover the entire vertical stack, from the orchestration layer all the way down to infrastructure, and that's how we achieve really high output speed and throughput while maintaining four nines of reliability and uptime for enterprise customers. So for a highly performant inference platform, each of these layers is necessary but not sufficient by itself. While integrating well with this very integrated stack, it is also critical to provide the right level of abstractions for developers to maintain control and visibility. seg 1157–1158

The journey of a token

All right, so now we're at the end, and I did promise a story. Now you're looking at the journey of a token in this end-to-end inference process. Again, the token starts by turning into an embedding, is processed in layers after layers of matrix multiplication, goes through latent space and quadrillions of floating-point operations, the memories are scattered, and out of thousands of choices a new token is chosen and returned. If a token is a hero in the story, the entire inference stack is a universe: it contains every single token, with every encounter, all the resources and constraints. The language model is fate: it determines the next token in ways that are nuanced and mysterious. And you all, my friends — the AI users and AI builders — are gods to the token. The god has a thousand masks, and the hero has a thousand faces. And that is Joseph Campbell, and that's my story for you. Thank you. seg 1159–1159
