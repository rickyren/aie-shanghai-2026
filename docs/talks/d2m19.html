演讲骨架

  1. 组织和 agent 都会“遗忘”，所以要做 Knowledge Layer；Nowledge Mem 的 memory engineering 包括保留全量轨迹、时间维度、关系与健康维护、遗忘衰减（FSRS）和超图结构。
  2. memory benchmark 基本只测检索，不能当全部；团队内部用四五十个自建评测，并在春季后转向半闭环的 RSI-like（自动研究式）自我优化。
  3. 团队运转进入“dark office”：夜间和周末 agent 持续产出，半闭环下验证仍离不开人，因此需要团队知识层来减少对专家的依赖。
  4. 对 team context 的实验显示：把它内化到模型参数收效有限，编译成 harness adapter 效果更好；并开源 HawDB 等项目。

讲者提出的框架

  • 全闭环 vs 半闭环 RSI-like 任务：最值得研究且最常见的是半闭环：验证环节无法完全脱离人，只能以批量方式用品味和判断来 steer。
  • 团队上下文连续性四级（L1–L4）：按团队上下文连续性分四级，讲者团队实践中 L3、L4 带来最多“aha”。

推出 / 提供

  • Nowledge Mem：面向 agent 与个人/组织的记忆与知识层产品，含全量轨迹、语义记忆、工作记忆、身份图与超图。
  • HawDB 与 RSI 式优化项目：面向上下文的原生数据库，以及讲者个人的 terminal 模拟器自动研究项目，均开源，优化记录公开。

非共识

  • 遗忘/衰减是记忆系统的功能而非缺陷；糟糕的记忆比没有更糟。
    decay of your knowledge 是非常重要的，是一个 feature，而不是一个 bug。
  • 主流 memory benchmark 基本只测检索，对真实 agent 场景有偏，只能当低垂果实的提示。
    简单来说，大部分的这种 memory benchmark，哪怕是针对 agent 已经设计过的，其实都是 retrieval based 的。
  • 将团队上下文内化进模型参数的多数实验无收益，编译成 harness adapter 反而更好。
    我们发现最好的方式是让 team context 以 harness adapter 的方式被 leverage。

信号

  • 数据信号记忆产品选择保存全量原始轨迹作为情景记忆，再按需蒸馏，轨迹本身被视作长期资产；评测集靠真实数据与用户反馈自建，并有专家参与。
  • 市场格局 / 规律agent memory 已经商品化、同质竞争，差异化转向团队层知识、时间/关系结构与 harness 集成。
  • 关注的指标团队不依赖公共 memory benchmark，而是跟踪记忆整合、蒸馏、实体图抽取等自建评测，并用来驱动 RSI-like 自动优化。
  • 市场格局 / 规律AI 原生团队出现“dark office”工作方式：夜间和周末 agent 无人值守产出，瓶颈在人的验证与品味。

Memory Engineering

第一个，如果大家留意刚才那个图的话，在 memory 里边，我们会存比较 raw 的 trace 或者是 thread 的 trajectory，也会有一些中间态处理过的 memory，比如说 semantic memory。我们在存 semantic memory 的时候，有一个非常重要的问题，就是到底哪些东西值得被我们蒸馏，distill 成为 semantic memory。简单来说，你不太能真的知道在 6 个月之后，还有哪些被升华过、被蒸馏的知识值得被再记录。所以我们最终的实践，简单来说就是，在我们最早版本的系统里就决定把所有的 trace trajectory 作为 episodic memory 完全地存储。然后我们在决定是否要记录的时候，做了很多有意思的尝试。比如说我在三四月份的时候还分享过我们当时的一个方法，是用一个小模型、用很简单的定制 prompt 去做 triage。比较有意思的是，当我们有像 JVLAC〔?〕 这样的工作的话，这个事情就变得更有意思。详细的话，大家可以看我们做过的一些公开分享。 seg 3443–3457

第二个就比较 straightforward：本身我们的 memory 系统在一定程度上是个 retrieval system、retriever。当然我后边会介绍，如果我们只做成 retrieval based 的话，会有很大的问题。但当我们想构建一个真的能够 enable 你各种各样 agent 场景的 memory 的时候，这个工作也是蛮枯燥和复杂的。简单来说，我们要对 fast path 做很多很多面向 memory nature 的结构设计，以及 retrieval 的一些 weighting 和策略的调优。后边我提到所谓 RSI 的工作的时候，也会提到我们做调优的一些工作。 seg 3458–3466

第三个也是比较常见的问题：当我们在构建非常重要的状态和 memory 的时候，temporal 这个 factor 是非常重要的。一般来说，memory 系统里边至少有两个维度的时间因素：一个是你那个 memory 所涉及的 event 本身的时间，其次是这个 memory record 本身被创建和更改的时间。这个因素在很多场景下，我们可能要在系统内部做 intent 的识别和 filter 的填充，也可能直接暴露给消费 memory 的 agent，让它 aware，去做相应的 leverage。当然还有我们前面提到的 working memory 的机制，我们维护了每一天你当时 focus 的 working memory，这也是另一个时间维度。 seg 3467–3474

第四个是，我们知道，比如说我们用 Obsidian〔?〕，让我们的 agent system 非常好地去维护你的状态，在很大程度上是一个可以 work 的场景。但是实际上，memory 系统并不只是一个 storage 的问题。我们怎么样保证你所存储的这些信息是被充分 correlated、充分 maintained 的，保证它的健康性？比如说同样一个话题，它在不同的 topic、不同的时间点有很多演进的脉络，如果你把它们完完整整地全都存储好，但并没有 aware 这种脉络关系的话，是有很大问题的。有的时候会造成你在消费这些相关 memory 的时候，如果没有完整地获得它的最新版本，或者它完整的脉络，有时候还不如没有这样的记忆系统的维护。我觉得应该会有一些人能够 relate：有一些系统的 memory 做得比较差的话，其实是不如没有的。 seg 3475–3486

还有一个，也 echo 到我前面说的，无论是人脑还是我们硅基的这种大脑，其实都有很多有意思的事情。这个就是老生常谈：我们知道，无论对我们的心智健康，还是对系统的可用、可维护，decay of your knowledge 是非常重要的，是一个 feature，而不是一个 bug。这里边我们做了很多有意思的尝试，其中我们用到了一个叫 FSRS 的算法，它本来是帮助我们用抽认卡记忆单词的一种方式。我们找到了一种方式，能够收集我们在 leverage memory 时候的 feedback，做到一个有点像推荐系统一样的机制，去辅助我们做 decay 的计算。我们前面提到的那个分享里有完整版的介绍。 seg 3487–3499

最后，这个大概是我们系统现在里边长的样子，它最后会成为一个 super graph。我们可以看到有很多的 spectrum，是在我们所有需要关心的上下文中不同层面的事情，它们其实在一整张 graph 中。当你需要不同情况的时候，可以从不同的维度去了解它。比如有一个层面我没有画进来，我们还有一个 identity graph，它能够获得你整个个人或者 organization 里边所有的 agent card 和你的 human，它们之间各种各样的关系，以及它们和这些上下文之间的关系。你可以按照某一个切片去使用，也可以把所有的抽象提供给 agent，让它在整个 super graph 中自由地去探索。由于它跟我们碳基大脑的工作方式是一致的，所以实际上它是非常符合我们要维护知识的本质的，我们在这个上面可以看到非常非常好的效果。 seg 3500–3514

最后一点，我们想引出后边 RSI 的工作。我们浓缩了好几个事情在这一页上。首先，如果大家在做 memory system 的话，我们会很自然地拿一些 benchmark 来帮助我们优化和 evaluate 自己的工作。但是在我们看来，how do you evolve your memory 也是我们跟别人分享的时候经常被问到的一个问题。第一个问题就是 benchmark：我们要充分利用，但是不能把它当作全部。简单来说，大部分的这种 memory benchmark，哪怕是针对 agent 已经设计过的，其实都是 retrieval based 的。而实际上在 real world 的情况下，当你真的想要充分地利用你复杂的、拉满的设计和累积的 memory 系统的时候，它在很多维度都不是 retrieval based 的。你需要精心地 structure、设计你不同维度的上下文，然后跟你各种各样的 harness 充分地 integration，它们之间的那些交互和 consuming 的 pipeline 大部分其实都不是 retrieval based 的。所以那个是非常 biased 的一个工作。但是如果你的 memory system 跑一个基本的 benchmark 分数很低的话，那你确实可以借鉴它，看看哪里有一些低垂的果实丢掉了。 seg 3515–3535

其次，回到 how do you evaluate your memory system。在今年春天之前的十几个月，我们的做法一直是：我们维护了系统里边四五十个不同维度的 evaluation，关于 memory consolidation、distillation，还有 memory 的 entity graph 的 extraction 等等不同任务的维度。我们其实是用比较笨的方法，用我们真实的数据和用户的反馈，自己一点一点地去构造不同的 benchmark，然后很多都是用 expert in the loop 的方式、用比较启发式的方式去一点点优化。当然我们这个工作还是蛮有经验的，所以效果还是非常非常好的。但是这件事情在今年四月份的时候开始产生了变化，蛮有意思的。 seg 3536–3550

RSI

这就引出我们第二部分的 topic。我们蹭了一个 buzzword，RSI。但这是我们真的在日常工作中——我们并不是 offer RSI 给我们的客户——在我们每天团队的工作中，自己走到了 RSI-like 的这样一种范式。在我们看来，RSI 这类问题可以被 categorize 成几种。对我们来说最大的一个区别就是：你是一个 fully closed loop 的任务，还是一个半闭环的任务。一会儿我会稍微介绍一下这里边的一些细节。 seg 3551–3562

这里我想给大家比一下。刚才那一页我没有很清楚地展开，但大家可以看到我提到了 Google 的 AlphaEvolve，在 Borg 上做了一些工作。这里很有意思，是我们亲身的经历：上面是一九年的时候，我当时为了准备 MWC，在 OpenStack 上做的一个优化工作，当然用的是上一代的优化方法，就是贝叶斯优化。它是一种统计方法，帮助我们把一个复杂的系统作为黑盒，在一个多维的空间中，以相对比较高效、又不需要领域知识的方式，找到一个很好的向量，能够反映你这个系统的优化程度。下边就是最近，已经是二五年，Google 做了完全类似的目标，他们是在内部所有的 infrastructure 上做调优。但区别在于，他们所有中间的 trajectory，甚至他们定义的 environment 的优化和可观测性的优化，所有的工作都是 human readable 的。所以这两个工作变得特别不一样。 seg 3563–3579

时间有限，我没有控制好，后边我就快速地给大家过一下。基本上，这是一个开源项目，是我个人的开源项目。我在四月份做这个项目的时候，刚好是 Opus 4.8〔?〕 和 GPT-5.4 的时候，那个时候 Warp 还没有开源。我自己在家庭旅行的时候构建了一个非常优雅的、带有 Copilot 的 terminal simulator 环境，使得这个 terminal 的 assistant 可以充分地理解我所有的 panes、tabs，以及内部各种各样的 tmux、SSH over tmux，里边再嵌套比如说 Claude Code 这样的 TUI。我让我的这个 agent harness 能够完完全全地理解整个环境，然后做各种各样的任务。比较有意思的是，我当时在休假期间独自走到了一个 autoresearch 的方法，后来 autoresearch 方法被发出来。有意思的是，这个工作我其实在之前的一个大会上分享过，然后九月份的时候 Anthropic 发了一个跟我这个工作方法完完全全一样的 blog，大家如果刚好没有看到，可以去看一下。时间有限，我就快速地过一下。经过那个时间点之后，因为 harness 和模型到了 GPT-5.4 那个时间点之后，semi-closed loop 的这种 self-improvement 的复杂系统优化的工作，就完全成为可能了。从那之后，这大大地改变了我们做 memory system 的方式。时间有限，我就不完全去讲了。 seg 3580–3603

Team Knowledge Layer

我快速地讲第三部分。在我们团队的工作环境里，以及我们一些比较 AI native 的客户的工作中，我们发现很大一部分工作的形式是我们叫 dark office 的，就是像 dark factory 一样没有人的。但是在这种 agentic 的环境下，你晚上的十二个小时和周末的四十八个小时，我们团队里的工作产出依然是非常大的。这里边很多很多任务是 RSI-like 的，而且是 semi 的——我前面没有提到——这种 semi-closed loop 的 RSI-like 工作，我们认为是目前最值得我们去研究的，而且也是我们真实世界工作中最主要的一种范式。而这种 semi-loop 的核心就在于它的 verification 环节是不能完全 decouple human 的。我们可以一点点地让 human in the loop 的程度趋向于小，但是你大概还是要以 batch 的方式去 steer、去 verify，去用你的 taste 和你实际的 judgment 去做这个工作。 seg 3604–3618

在我们看来和我们的探索中，这里边一个非常非常重要的环节，就是怎么能够让我们团队的智慧在这里边帮助尽量地 decouple expert，或者是让晚上这个工作能够尽量地 move forward。时间关系我就不展开说了。我们做了很多的工作，其中包括我们构建了一个 team harness 的 memory system。大家感兴趣可以去看，我们定义了一个叫 new corp.co〔?〕 的 reference 公司的工作方式，定义了四种 level 的团队 context continuity，就是上下文连续性的级别，并给出了不同的参考方式。从我们自己的实践来看，L3 和 L4 给我们带来了很多很多 aha moment。 seg 3619–3629

在这个基础之上，这是我今天第一次分享我们的研究工作：我们跟 Cornell 大学的一个年轻的 researcher 做了不少实验。我们第一个尝试是，能不能把 team context 这些团队的智慧，一定程度上内化到你的参数模型中。我们试了九个不同的场景，有的是能不能在人离开 loop 的时候往前推一点，有的是能不能帮助你更好地找到应该对的 agent 或人等等。比较有意思的是，我们做了九个不同的实验，只有三个情况是有收益的。而这三个实验的方向其实就是我们后边做的一个方式：我们发现把 team harness 做相应的 compile，就是相应的编译，使得它更好地被 harness 去 leverage，去跟 harness 做好结合，效果反而更好，在很多其他的场景里效果也更好。时间关系我就不展开。上个月 CMU 有一个 paper，叫 harness adapter，这个名字起得非常好。我们发现我们的工作和他们的——虽然他们不是 for team context 的——是一脉相承的，非常有意思。所以我们也用了同样的词，有点像 module adapter 一样。我们发现最好的方式是让 team context 以 harness adapter 的方式被 leverage。时间关系就不展开了。 seg 3630–3653
