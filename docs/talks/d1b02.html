Trust Your Own Evals, Not the Leaderboard: What 10k+ Internal Agent PRs Taught Us About Adopting Open Models

Joey Wang（王仲宇） · Harvey · 2026-11-05 分会场 · 14:07–14:22 · 场次 d1b02

Harvey 用内部 agent 产生的大量真实 PR 作为自建评测集，发现换用更便宜的开放权重模型常常接近 Opus 的效果，真正的差距往往在自己的代码与流程而不在模型或 harness，因此应该相信自己公司内部数据的 eval 而不是公开 leaderboard。

演讲骨架

  1. Harvey 做了内部协作 agent Specter，让多人在 Slack 里与同一个云端 agent 协作，同时把每个 PR 的完整流程沉淀为可重放的内部评测集。
  2. 模型每隔几周发布一次，是直接换新模型、信 benchmark，还是自己测，成为新问题；论点是别人的 leaderboard 不能代表自己的 harness、context 与任务，应该相信自己的 eval。
  3. 三个案例（PR description、code review、fix CI）用每次只改一个变量加 LLM judge 重放：多数时候要改的不是模型或 harness，而是自己的代码 bug、评测集筛选和流程，开放权重模型接近闭源前沿。
  4. 结论：差距常常来自没花时间优化流程；不要因为开放模型首次结果差就放弃，要在自己的 eval 上 hill climb。

讲者提出的框架

  • 单变量重放评测法：把 agent 完成任务的固定流程变成可重放的评测 case，用 LLM judge 打分，每次只改模型、harness 或 prompt 中的一个变量来判断瓶颈在哪里。

推出 / 提供

  • Specter：Harvey 内部的云端 agent，在 Slack、GitHub、Linear 中让多人协作，从产品设计到 PR、修 CI、上线，并保留完整 context 和 traces。

非共识

  • 换模型或改 harness 往往不是答案，评测中最先暴露的是自己代码里的小 bug 和流程问题，修掉这些就能显著提升，不需要训练模型。
    最后我们发现，模型和 harness 都不是真正要改的东西。
  • 在 code review 任务上，当 prompt 与 harness 优化后，更便宜的开放权重模型（DeepSeek Flash 级）接近 Opus，最贵配置多抓出的问题经人工审查并不重要，应降级用便宜模型。
    所以与其用 Opus Max，不如直接用 Opus；与其用 Opus，不如直接用 DeepSeek 的 Flash。
  • 构建评测集时，最耗时的是判断收集到的数据哪些可用（回放会被后续 review 或新改动污染），测试本身比测试结果更重要。
    所以我发现花更多时间的是研究这个评测集该怎么选出来。

信号

  • 数据信号云端协作 agent 把人与 agent 的完整 context 和 thinking traces 留在公司内部，转化为可重放的内部评测数据，而本地 agent 这些数据会丢失。
  • 关注的指标关注每个任务的成本、完成速度（thinking 时长与 CI 重试）和质量的权衡，而不是公开榜单分数；开放权重模型思考更多、耗时更长，会占用沙箱运行时间。
  • 市场格局 / 规律法律 AI 公司同时自建法律评测集（Big Law Bench、Legal Agent Bench）、对开放权重模型做后训练，并在内部用开放权重替代昂贵的闭源模型。

大家好。我叫 Joey，中文名王仲宇，来自 Harvey。Harvey 是美国硅谷的一家法律 AI 公司，算是最近几年做垂类里比较前沿的一家公司。今天主要分享来自一些内部的实践，也给大家讲讲我的一些心得体会。我在公司做了大概三年，主要是从给律师服务，到给内部用户服务，最后学到的经验可能还是会回归到我们的客户。seg 181–186

我非常同意刚才那位的观点：创作是一种很好的学习方式，包括输出你的一些东西；用 AI 去创作，更能让你把自己的想法表达出来。我今天做这个创作也是因为 AIE 这个契机，大概 20 多天前开始研究到底要做一个什么样的演讲，然后就开始跟 Agent 一起做 experiment。所以今天最后的这些结果我也会给大家讲一讲：我花了多长时间，花了多少钱，甚至能为公司省多少钱，也给大家一些小的启发。seg 187–193

Harvey 与 Specter

Harvey 主要是做法律方向的 AI。我们对法律 AI 的一个想法是：Agent 可以直接在一个案件分析里展开工作，带着所有这些 context。我们也针对法律的各种场景做过一些 benchmark，也就是评测集：24 年就开始做 Big Law Bench，到今年做了 Legal Agent Bench，它主要解决的是非常长时间运行的 Agent。我们也对 open weight model 做了一些 post training，包括 GLM 或者 Kimi K3 这些。我们在做对外的 training 的同时，也用这些 open weight model 做了一些内部的尝试。今天主要讲几个具体的案例，以及在内部尝试里我学到了什么。seg 194–204

首先是我今年做的一个项目，叫 Specter，是 Harvey 内部的一个 Agent。为什么要做内部的 Agent 呢？从今年早期开始，大家会发现 Coding Agent harness 都变得非常厉害，但我觉得有两件事我一直没看到别人解决。在自己做一个东西的 cost 变得非常低的情况下，我就开始在内部着手做这两件事。seg 205–207

第一件事，是大家都在 Slack 这个协作工具里，去做多人和一个 Agent 的协作。传统意义上，所有人都拿 Agent 去做事，最后你把一个 PPT 或者 PR 交给同事的时候，同事拿到的是一个最后的缩影，并不知道 Agent 背后的故事。我希望的是，大家能把 Agent 所有的这些 context 一起放在我们的讨论中。于是多个人可以跟一个 Agent 协作，结果是所有人都可以认同的。大家可以在 Slack、网页、手机上，或者做一些自动化〔?〕，让这些活就把它做完了。seg 208–213

这个产品现在公司大概 500 多人都在非常活跃地使用，产生了大概上万个 PR。我们根据这上万个 PR 得到的结果，成为了我们现在可以用的评测集。seg 214–215

传统意义上一个 PR 是怎么走完流程的？大家可以在 Slack 里开始说"我要做这个事"，或者一个 PM 有一个来自客户的产品需求，我们就可以把这个 Agent 从最初的产品设计，到最后的 engineering 交付，甚至到测试迭代、上线，都直接从 Slack 里开始。但 PR 并不是我们结束的地方，我们其实也需要一直去修 CI。CI 就是 continuous integration，我们需要 run 一些 test，然后知道这个 PR 究竟是给整个产品带来了正向的东西，还是带来了一些错误。seg 216–222

这些我们现在都非常自动化，而且因为 harness 和模型都是可以替换的，所以一个 task 从最开始到最结束，这个固定的流程都是可以重放的。这个固定流程就变成了我们的一个 evaluation case，我们可以用它作为评测集。seg 223–225

这是我刚才讲的：从本地的 Agent 到云端的 Agent，会有一些区别。我们真正的工作都是在 Slack、GitHub、Linear 上做的，所以我们会想，如果把这个 Agent 沙箱带到我们工作运行的环境里，怎么能让 Agent 运行得更好。另外一个 side effect 是，当我们有了云端的 Agent 之后，我们拥有了更多的评测集。大家在本地跑的这些 Agent，最后 Agent 的 context、thinking traces 都不见了。但一旦我们有了这么一个大家都可以协作的 Agent，这就成了我们可以在线上收集的数据，并且是内部数据，我们可以更好地做一些实验。seg 226–232

新的问题

当然，现在做了这么多个月之后，我们会面临一些新的问题。第一个问题是，新的模型每隔几周都会发布一个，你到底是直接上这些新模型，还是要测一遍，还是相信这些公开的 benchmark？这是大家可能会花越来越多时间去思考的。比如现在 DeepSeek 或者千问都有新模型出来了，我是不是应该马上上，还是应该等一等，还是应该自己做评测，该怎么做？这是我今天想讲的。seg 233–237

第二个，如果你运行在云上，会有很多时间上的感知，很难减少，因为你在本地的 Agent 运行很快，那我们怎么提升这个速度？换一个更快的模型，是不是一个更好的方式？这也是一个问题。seg 238–241

第三个，因为现在每个人都有更多的 output，所以 review，也就是审核 PR，也变成了瓶颈，大家渐渐会用 Agent 去审核 PR。那用什么样的模型、harness 或者 prompt 去审核 PR？也是我们最近在研究的问题。seg 242–247

还有 cost，大家可能会思考：我用越来越多的 Agent 花这些 cost，究竟能不能达到我要的效果？是不是应该换一个模型？这也就是我做这个实验的初衷。seg 248–251

实验：相信自己的 eval

首先，别人的 leaderboard 或者别人的 benchmark，并不一定是你做自己工作的时候能直接切换过去的。比如他用的 REPL 和我们这么多年自己搭建的整个 context 是不一样的，我们的 Agent 不一样，harness 也不一样，甚至真正做的事情也不一样。很多时候你有一大半的事情并不是生成代码，而是怎么让这个代码达到产品上线的 quality。seg 252–256

我们用 Agent 解决这个过程时，有很多任务是非常固定的，比如 review 代码、fix CI，甚至小到从一个代码变成一个 PR，然后写 PR description，也就是你这个 PR 具体做了什么、为什么做、测了什么。这其实是人与人之间交互的一座桥梁，怎么把这座桥搭得更好，也是促进组织架构生长的一个很重要的地方。如果所有人的 PR 都只有一句话解释，大家不理解这个 PR 在干什么，就会增加 review 的时间。所以我们希望能做得很好。seg 257–263

像我刚才讲的，我们把这个流程分成这么多步，通过 replay 的方式，再通过一个 LLM judge 去评分，最后就可以判断出我们到底是改模型、改 harness，还是改其他东西。我先剧透一下：最后我们发现，模型和 harness 都不是真正要改的东西。很多时候你一旦开始做评测，就会发现你代码本身有很多东西可以改，流程上可以改。甚至因为我做这个 slides、要讲这个东西，做实验的时候发现有很多 low hanging fruit，也就是很容易做到的事情，结果最后就有很多效果。所以当你试了之后，你才会发现，你可能真的不需要训一个模型就可以做到很好的效果。做实验有一种很常见的方式：每次只改一个变量，你就可以确定是要改 harness、模型，还是其他东西。seg 264–273

三个例子

三个例子，我刚才已经提到几个了：第一个是 PR description，也就是具体的描述；第二个是怎么审核代码；第三个是怎么 fix 修复我们的 CI。seg 274–275

第一个例子比较小，我快速带过。我们真正给别人看 PR 的时候，会有一个人类的描述和一个 Agent 生成的描述，我们有一个语言模型专门做 PR 生成描述的工作流。为什么？因为你的 PR 可能一直在变，今天让 Agent 做了 A，明天让 Agent 做了 B，都放到一个 PR 里，它一直在变。我们需要做的是，人写的那段话要维持，因为我们希望人最后还是有一些 judgement；Agent 能生成的东西也要保持；另外比如测试的结果，我也希望能放进去。seg 275–281

结果发现，即使我换了模型、换了 harness、换了真正的 prompt，也没有什么变化。很多问题其实发生在我丢给它的数据上，结果发现 code 里有很多小 bug，比如当你这个 PR 的描述太长的时候，你最后给它的东西并不是真正能用上的东西，于是它漏了很多东西。所以通过这个测试，我发现只要修一些 bug，基本上不用换任何模型或者 prompt，就可以做得非常好。seg 282–285

第二个例子是 code review。这里我想讲的是：测试本身比测试的结果更重要。当你发现你测试的数据集……（现场调整视频）seg 286–288

总的来说，我们发现收集了那么多数据，真正能用的并不多，所以真正能判断数据好不好用，这个过程可能是我跟做实验的 Agent 聊得最多的事。比如 code review，如果你要把它重放一遍，有可能这个 code review 本身有另外的人或者 Agent 在上面留了更多的 code review，那你重放的过程中，这个 Agent 可能会受到后来那些 signal 的影响，它就不是一个很好的 case。或者这个 PR 之后有人又加了新的 change，也会影响到这个 PR。所以我发现花更多时间的是研究这个评测集该怎么选出来。seg 289–295

我们最后的结果是：当我们保证 prompt 是 optimal 的，并且 harness 是比较通用的情况下，DeepSeek V4.1 的 Flash 已经能够接近 Opus 的效果。我们会发现 Opus Max 会花非常多的钱，但它真正能 catch 住的东西有多重要呢？进行了一些人类审查之后，发现其实可能并不重要。所以与其用 Opus Max，不如直接用 Opus；与其用 Opus，不如直接用 DeepSeek 的 Flash。这个结果也比较出乎我的意料。seg 296–301

第三个例子是 fix CI，我可以快速跳过。同样，fix CI 的结果是非常好确定的：CI 到底是过了还是没过。这时候如果你把 Agent 放在那边，其实质量都差不多，因为它们最后都会把它跑过。所以有一个很好的验证，是你对 Agent harness 最能提效的地方。区别在于 Opus，它有时候一遍就过，但其他模型可能需要不断反复地尝试，所以会花很多很多时间，甚至有可能浪费你的沙盒运行时间，你可能需要去共享你的沙盒。seg 302–307

那它究竟是怎么回事？因为我们现在跑在云上，我可以分析它很多的 trace，最后发现这些 open weight 模型大部分时间都在思考更多，需要更多的 thinking trace 才能解决这个问题，有更多的 reasoning。而 Opus 可能很快就能得到结果，甚至会减少它自己对 CI 的 retry。seg 308–314

结论

那么当我们发现这个结果之后，该做什么呢？不应该直接放弃，而应该通过刚才的结果去 hill climb，也就是怎么真正提升这个系统，让 open weight 的 model 在你的使用场景下，既保证质量，又减少时间。后来发现，其实你可以不需要全部跑这些测试，也不用思考那么多，也可以得到这个结果。seg 315–318

最后，法律方面我们做 benchmark 的思路，和我们为代码做 benchmark 的思路都很像：需要思考评测集是什么样的，怎么评分，甚至能有自己的数据、自己的任务来衡量，并且让 open weight 在不断的尝试中追上来。你差的可能不是模型，也不是 harness，差的只是你有没有花时间精力把你的流程优化。所以你要相信你自己公司内部数据的 eval，而不是别人给你的 benchmark。seg 319–324

最后的结果是：我大概一共花了 7 个小时和 Agent 交流，花了大概 7,000 美元，但我预计可以给公司每个月省下上万美元。大概是这么回事。seg 325–326
