Building Agents: Yesterday, Today, Tomorrow

Clemens Rawert · Langfuse by ClickHouse · 2026-11-05 主会场 · 10:07–10:22 · 场次 d1m03

演讲骨架

  1. agent 靠迭代改进而非事前写验收标准：跑起来、读 trace、修复、写测试，循环往复，更像手艺而非科学。
  2. agent 架构从直接调用、链式、RAG、agent graph 回到“模型+工具+沙箱+文件系统”的循环，本质趋同于 coding agent；Halo 是其内部参考实现。
  3. 人工读 trace 已不可扩展：先把 trace 压缩成 trajectory、摘要、聚类、排序（面向数据的渐进披露），再交给 coding agent 处理。
  4. 未来由后台 agent 接管改进循环，人保留质量定义、可信反馈信号和发布决策；循环产生的标注数据可进一步用于自建 RL 环境。

讲者提出的框架

  • 面向数据的渐进披露：trace 先压成 trajectory，再用小模型按领域维度摘要，嵌入聚类并排序，只把最严重的完整 trace 交给 coding agent。
  • 人机分工：agent 跑改进循环、人守质量：默认形态的任务可由 agent 自动改进，定制或超前沿任务仍需人写 eval 与 skill；人负责定义好坏、反馈信号和发布。

推出 / 提供

  • Langfuse：开源的 agent 评测与可观测平台，帮助开发者理解 agent 行为并在生产中改进。
  • Halo：Langfuse 内置 agent，帮助用户读 trace、发现问题，运行改进循环。

非共识

  • 最佳团队下一步会用改进循环产出的标注构建自己的 RL 环境，训练开源模型，在自身任务上做到饱和。
    And the next step that we see the best teams starting to take right now is to build their own reinforcement learning environments, because the labels you get from running the improvement loop are signals you can use to build tasks, build verifiers, and in the end train your own open-source models that saturate on task quality for what you need.
  • 前沿智能已足够解决许多问题，瓶颈在 agent 的可靠性而非智能。
    In general, at Langfuse we think frontier intelligence is already very close to helping you solve many of the problems out there, and that the reliability of your agents is generally the bigger issue.
  • agent 循环放在后端 worker 里，沙箱只作为一个按需调用的工具，以节省沙箱算力成本。
    And, which might be interesting, this loop runs in our backend workers, not in a sandbox.

信号

  • 数据信号运行改进循环产生的 eval 与标注构成应用专属数据集，领先团队把它转化为任务、verifier 和 RL 环境。
  • 市场格局 / 规律可观测与评测平台的角色正从“给人看 trace”转向“为 coding agent 提供经过压缩的数据层”（MCP/API/CLI 接入）。
  • 市场格局 / 规律agent 架构趋同为 coding-agent 模式（工具循环+skill+沙箱+文件系统），并扩展到子 agent 与常驻的 ambient agent。
  • 关注的指标关注 agent 可靠性与失败类别（如工具调用报错），以失败 trace 而非整体分数驱动改进。

All right. Hi, everyone. It's great to be here and to see the room so full, with standing room only at the back. My name is Clemens, and I'm one of the co-founders of Langfuse, which was acquired by ClickHouse, the real-time database company, at the start of the year. Langfuse is an open-source platform for agent evals and observability. Basically, what we do is help developers understand what their agents do and then improve them in production. seg 423–431

And that's exactly what I want to talk about today: agent architectures — how agents are built, how agents are improved, how that evolved over the past couple of years, and what I think this is going to look like in the future. seg 432–438

Agents are improved iteratively

All right. The main message that I want to start with is that we found that agents are improved iteratively. It's not like traditional software engineering, where you write down acceptance criteria and think hard about tests before you start building your application. Agents are unpredictable, and you need to learn from what they do. What the industry and many of our users have converged on is the improvement loop that you can see at the top of this slide. You run your agent — not necessarily in production — yourself, with internal users, with external users, and you see where it breaks, where it fails. You go into your data, look at your traces, ship a fix, write a test. Rinse and repeat. So basically you just keep on fixing the issues that you find within your agent in production. seg 439–452

A quick example from one of our own agents. We have an agent in Langfuse called Halo. It's our in-app agent that helps developers run this improvement loop: it helps you look at your traces, find issues that pop up, and get a better view of the things you want to improve in your agent. One of the bugs we came across by reading our own traces of how users use it was a lot of tool call errors. A very simple example: our agent wanted to sort by total_cost_sum, while the tool was expecting sum_total_cost. Super simple example, but the only way to figure this out is to start looking at your traces, fix the application, and release it back into production. seg 453–465

The takeaway here is that building agents is much more artisanal than it is scientific. It's not a scientific process you do at your desktop. You need to get your hands dirty and ship many iterations. seg 466–469

How agents were built

Let's start with a quick walk down memory lane. How were agents built? Three, four years ago, we really started with just direct calls to the model: you immediately call the LLM. Then we started chaining, using the output of one model further down the line. This quickly led to problems with context windows, which were relatively small with the early models in 2023, 2024. seg 470–478

RAG was the next architecture that started happening. Before actually using any LLM, we would do a search over your documents and then feed the output from that search, the chunks that would fit, into the LLM's context, and run your application that way. seg 479–482

Next was tools and loops. This is an architecture that we see again today, and it came up pretty early. But models were actually not good enough yet for this more free-form architecture — where the model keeps running in a loop with tools it can use to access other systems — to be very useful. seg 483–488

What happened then was that we saw agent graphs pop up. With models not being good enough yet, we would split the problem up into graphs, into workflows — smaller individual pieces that the models could handle at their given capability frontier. The problem, though, is that you have to design these by hand. That takes quite a bit of time, and you need to understand very well all the paths your agent might need to take to come to an answer. seg 489–494

Then we basically got back to the architecture that I just showed you, as models got better in 2025 and now especially this year in 2026. The architecture we're now seeing lots and lots of teams use is again a model with tools in a loop, using a skill, with access to a sandbox to run code and a file system available to it. This architecture really started to work last year and then this year. seg 495–501

And you can extend this architecture. You can let the same architecture run sub-agents as well: you have one orchestrator agent at the top, you fan out tasks to different agents, and then bring it all back together for the results. And, as was just shown in the keynote before me, what we're seeing now as well is ambient agents — agents that are always on, triggered by things happening in your orbit: an email, a schedule, an event happening outside. These agents now run for much, much longer than they used to, and they are usually also able to hand off work to other agents. seg 502–514

What we use internally: Halo

I want to talk a tiny bit about what we are using internally, which might be an example of a reference architecture that works today. Halo, as I said, is the agent we use to run the improvement loop for our users. What does the Halo agent look like? It actually looks a lot like a coding agent. It runs in a loop and has access to a lot of tools, one of those tools being a sandbox with a file system and bash. It also runs with a skill in which we feed it a lot of context about how Langfuse works and the actions that are available to this agent. seg 515–523

And, which might be interesting, this loop runs in our backend workers, not in a sandbox. The sandbox is just one tool available to it. That's what we would usually recommend folks do, because you save a lot of compute cost for the sandbox if you only use it when you actually need it and have the agent run outside it at first. This is not the only design that we see working for agent architectures, but it's one that we see repeatedly within our user base and also within ourselves. seg 524–532

Improving agents at scale

Now we come to the question of how we improve these agent architectures that get more and more difficult, more and more complex over time. In the past, especially when agent architectures were simpler, humans could eyeball everything. You could look at your traces; they were generally pretty short. You could read them, see where things break, and fix your application. Today that's a little bit harder, as agents get bigger and the traffic that runs on these systems increases. seg 533–541

What we've seen is that the industry has converged on this improvement loop for agents: you find failures in the application, you write evals for these failures, you change your application, you backtest the application against these evals, and then you release to production. And then you start all over again. seg 542–548

This process is mostly run by humans today, and that means there are a lot of judgment calls involved. Which failures do you care about in your application? Which do you need to turn into evals? What do these evals look like? When do you release? In the diagram here, everything that's orange is still run by humans — and that's all of it right now. seg 549–556

The good news is that this process works, and we've seen it really take hold as a best practice in the industry. The bad news is that it's slow and expensive, because it uses the one resource you probably can't scale in your organization: the engineers working on your agents. seg 557–561

And there's another problem: agent traces and the amount of data also increase a lot. In the past, with a simpler agent architecture like the one at the top left, you were usually able to read the entire trace and follow everything the agent was doing. Increasingly, with tool-loop agents, sub-agents, et cetera, it's not possible anymore to read everything that's happening in your agent. And as you go to production — lots of you will know — the amount of traffic you get really explodes. So no one can actually read all traces by hand anymore. How do you improve agents with that much traffic? seg 562–567

The good news is that at this point you can already hand off a lot of the improvement loop to agents. Coding agents have gotten a lot better at helping you traverse your data, find failures, propose fixes to your prompts, to your evals, in your datasets, and backtest your application against the evals you've set. So you can use AI to get a hold on all the data being produced by your AI systems. It's important that you're able to connect all of your application data, your traces, to coding agents via MCP, API, or CLI. seg 568–577

Shaping the data: progressive disclosure for data

But there is a catch: an agent's context usually doesn't fit millions of traces. As the data you want to analyze explodes, you can't just feed everything into a coding agent. At most, you can actually analyze maybe dozens, hundreds, thousands of traces within your coding agent, depending on how large they are. So you need to shape your data first. That means you start from all the data that you have and summarize it down to the things you really care about, that your agent should look at and reference. seg 578–585

How we see this play out in the industry right now is basically progressive disclosure, but for data. What does that mean? You take traces and summarize them as trajectories, which are short textual representations of your traces. Then you use smaller, less expensive language models to summarize these trajectories along dimensions that you care about. That comes from your domain expertise, what you know about your agents: where they break, what you care about, how you want them summarized, where you expect things to fail, what you want to know about how your users use your application. seg 586–594

Then you take these summaries, embed them, and cluster them. You label these clusters and again use language models to rank them. If you have, for example, a class of failures where tool calls fail, you can use a model to rank these issues, look only at the failures that are most egregious, and then pass the full traces for these failures back to your model. This is how you go from millions of rows of traces and logs to a smaller amount that you can actually send back to your coding agent. seg 595–600

Background agents and the role of humans

All right. What we see happening next is that background agents take over this process. LLM applications and agents that are running constantly produce traces, and because they constantly produce traces, they constantly come up with new failures that need to be evaluated and improved. So what we see happening, and where we think the industry is going, is that teams will use background agents: agents that take the data you ingest into the systems, maintain this data, and, long-running, find failures, propose fixes, and backtest these changes to your applications. seg 601–607

A couple of minutes left — OK, I'll speed up a bit. Once agents take over this loop, what remains for humans to do? In our view, that's mostly quality. You need to own the outcome. What does good look like for your application? What are the feedback signals you use to determine what a good outcome is? And then the decision to actually release fixes to your application. seg 608–616

Predictions and bets

I'll just skip over this here to get to the end, where I will share some of the predictions and bets that we're making at Langfuse as we build for this transition into agentic improvement of applications. In general, at Langfuse we think frontier intelligence is already very close to helping you solve many of the problems out there, and that the reliability of your agents is generally the bigger issue. seg 617–620

If your task has a default shape and it's not incredibly complex or custom, improvement will get a lot easier, as you can get agents in the loop to automate it. If you have a custom-shaped problem, or something way above the current intelligence frontier of models, you will need to continue running the loop: write evals, rewrite the skills that you use for your application to give them the manual for the things they need to do, and run backtests against your application. seg 621–623

The good news is that when you run this loop — write evals, label data — you collect a lot of data that's incredibly valuable. It's a unique, application-specific dataset that you can use to improve your application going forward. And the next step that we see the best teams starting to take right now is to build their own reinforcement learning environments, because the labels you get from running the improvement loop are signals you can use to build tasks, build verifiers, and in the end train your own open-source models that saturate on task quality for what you need. seg 624–628

Wrap-up

All right, to wrap up, what do we find? Agent architectures are very much converging on a coding-agent pattern. The traces these generate really outpace anything humans can read, which means we need background agents and AI to automate the improvement loop that we've seen take hold for AI agents. But it's important that we as humans keep the big pieces to ourselves, and that's mostly quality: What does a good application look like? What are the feedback signals you can trust — like user feedback, implicit or explicit, that you can collect from your product? seg 629–636

I think that's it, and I'm out of time. Thank you so much, everyone, and I'm looking forward to spending the next two days with you here at the conference. seg 637–638
