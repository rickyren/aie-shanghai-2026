Powering open source personal agents with Exa search

Jakub Hojsan · Exa · 2026-11-05 主会场 · 15:36–15:49 · 场次 d1m14 · 偏宣传

Exa 定位为个人 agent 的搜索层：既有独立网页索引，又有 POI、天气、新闻等实体数据，并用只返回相关片段的 highlights 控制 token；讲者用一个开源个人 agent 示例说明，闭源个人 agent（Muse、Instinct、Grok Bot）之外，开发者也能用 Mem0 + Qwen + Browser Use + Exa 搭出可检视、能主动提醒的版本。

演讲骨架

  1. 从聊天机器人到云端 agent 再到个人 agent，搜索的用法发生了质变；个人 agent 的关键是跨请求的连续性（记忆、搜索、工具、持久化）。
  2. 用「在上海找餐厅」一个请求演示全流程：读取预算记忆、搜索候选、用 browser use 看照片、按同行人偏好分别存记忆、查天气、保存计划。
  3. 用 Mem0 + Browser Use + Qwen 开源权重模型 + Exa 搭出可检视的开源个人 agent，原则是「先搜索、再按需升级工具」，并用 highlights 只取最少 token。
  4. Exa 索引不止网页（新闻、SEC、播客、POI、天气），并可通过 Exa Monitors 或定时搜索加 browser use 实现按条件才打扰用户的主动助理。

讲者提出的框架

  • 先搜索、再升级工具（search first）：先读搜索返回的 highlights，判断任务还缺什么，再升级到 browser use 等工具，使每次工具调用只针对任务的一部分。

推出 / 提供

  • Exa 搜索 API 与 highlights：独立网页索引加数据合作伙伴，按查询抽取式返回页面中相关 token，避免整页进入模型上下文。
  • Exa 实体索引（POI、新闻、播客、财报、天气）：除网页外，新增大规模兴趣点索引，并覆盖新闻、SEC 文件、播客转写、活动和天气。
  • Exa Monitors：按计划监测网页事件，用于主动通知类 agent。

非共识

  • 个人 agent 应以搜索为第一步，只在 highlights 不足时才升级到浏览器，闭源产品大概也是这样设计的。
    So I think the guiding principle here is search first.
  • 主动助理的关键不是推送，而是用记忆里的条件过滤，大多数事件应当静默。
    Only when these conditions match would it notify me; otherwise it would just stay quiet.

信号

  • 市场格局 / 规律搜索 API 的客户从 coding agent 和 CRM 数据补全，扩展到个人 agent，被视为增长最快的垂直方向。
  • 数据信号搜索供应商因个人 agent 兴起，专门购买或抓取并索引大规模兴趣点（含中国地点）、天气、新闻、播客转写等实体数据。
  • 关注的指标追踪每次决策送入模型的 token 量和端到端任务时间，说明搜索供应商在为小模型和快速 agent 优化。

What is Exa

First of all, what is Exa? Exa is a search layer for AI agents. We bring together our independent web search index and a network of data partnerships to power a versatile API for LLMs and personal agents. Exa has indexed over 100 billion web pages and growing, constantly crawling and updating them for our customers. We serve said web pages in as little as 300 milliseconds on average. Later, we'll talk about how we serve token-rich highlights for those pages, which are important for keeping end-to-end task time〔?〕 low when using Exa alongside LLMs. seg 1243–1250

Today, companies like Cursor and Cognition use us for web search within their coding agent products to serve up-to-date coding documentation, and companies like HubSpot use us to keep CRM data enriched and up to date. But today I want to focus on a rapidly growing vertical, alongside Grok, Instinct and Muse: personal agents — systems that use information about the world to help with decisions in your own life. seg 1251–1255

From chatbots to personal agents

In the last year I've spent at Exa, I've seen a seismic shift in how search is used. I'm sure we all know about the chatbot paradigm: you can ask DeepSeek Chat a question, and you get an answer. Then came agent SDKs that let you delegate a task to a system that can search, browse, and write code on your behalf to complete a task. We now see this cloud agent model in products from OpenAI, Anthropic, Cognition, and Cursor, as well as DeepSeek and MiniMax here in China. seg 1260–1264

A personal agent adds continuity. It can carry context from one request into the next: my budget, my preferences, and the plan we already started. It also opens the door to the famed idea of proactive assistance — an agent that can pick up where we left off and help with what comes next. The building blocks are context, search, tools, and persistence. Let's give one something to do. seg 1265–1271

The open-source system behind it

Now, we've used personal context, we've retrieved the evidence and done a visual check. So now we can take a look at the open-source system behind this interaction. First of all, something important to note is that there are a lot of closed-source personal agents out there — we obviously have Muse, Instinct, and Grok Bot. But not everyone's super comfortable with sending all their information to these closed-source systems. So I thought it was important to share how you might architect an open-source system for a personal agent. More than anything, I myself would love a system that could be inspected for what it remembers, and to be able to see why a tool was called, why it failed, and when it failed. That would help me improve the system instead of relying on someone else's. seg 1302–1311

Instinct was one of the design references for this little demo, and I think it's a really good starting point to create a small, inspectable version of what we have there. For the sake of this demo, it's running in this small demo environment, but there are several useful APIs that allow you to connect to iMessage, such as Linq, and I believe there might also be an API for WeChat, for example. So all of these concepts can be pulled into whatever interface you'd like. seg 1312–1317

We have Mem0 for the memory — we're leveraging that as an open-source library. We have the Browser Use library, which allows us to do browser use over whatever context we pull from search. And then we have a Qwen open-weight model, accessed through OpenRouter. Exa is specifically supplying web search with token-dense highlights, but every component here has a clear job. seg 1318–1323

Here's how it works. First you have the memory supplying the relevant personal context, and then you have Qwen conducting the reasoning over it, so whenever it deems it necessary to make a memory tool call, it's able to do that. Exa is able to bring back search results with highlights — I'll show you what that looks like in a second — and these results return to the model. Now, a highlight will not always be sufficient to answer a question. For example, when I was looking for a screenshot, I could find the restaurant from the search results, and I might be able to find the page that contains an image, but then I might want to pull up the browser to go do that. seg 1324–1331

So I think the guiding principle here is search first. You're able to read the highlights of the page, and then identify what the task still needs. This keeps every single tool call very focused on one specific part of the task, for efficiency. For developers, I think this is a very useful paradigm to design around, and I believe this is how most of the closed-source systems seem to be designed, given my heavy use of personal agents in iMessage. seg 1332–1337

Highlights

So that brings us to how Exa leverages highlights. Every single page we send to an LLM adds input tokens, and for smaller models this is just not efficient: for one, you might overflow the context of the model, and then you will have more hallucinations. More text takes more input processing. For a fast agent, you should be retrieving the minimum amount of tokens possible for the next decision. seg 1338–1345

A restaurant page, for example, will contain a lot more information than you need: navigation, the owner's story, maybe some old announcements and a newsletter signup, a table of contents. But the relevant passages that you actually care about might describe the dining room, the price, the location, or the hours. seg 1346–1349

The request on the left is how you call highlights within Exa. It's probably the most important feature besides search. It basically allows you, with no transformation of the page, to pull extractively the relevant tokens for the query — so we're doing query interpretation over the search. This keeps the whole page out of the model context, and there's way less text for the model to process, which leaves way more room for the actual conversation, images, and tool results. If a passage does contain enough information, we can just respond. If the user wants a photo, like I presented before, or an important detail is absent, we can escalate to a different tool like Browser Use. seg 1350–1358

More than dinner: what Exa indexes

Now, that same personal agent that I showed you, where you're able to locate a restaurant — I think it's so much more than dinner. What Exa provides in these instances is not just the 100-billion-web-page index; we also index news sources within 15 minutes. We have SEC filings and earnings calls for finance, we have over 3 million podcasts with full transcripts, we also have events, and recently, due to this large boom of personal agents, we've actually indexed over 200 million points of interest. So if you want to find pizza in San Francisco, you can find all 100 pizza places in San Francisco, with their prices and their menus. And there are actually a lot of Chinese locations as well. seg 1359–1364

My preferences definitely matter when it comes to a personal agent, and with these places in the index it's very easy to locate exactly what I need. In this instance, I might find 43 restaurants that serve crab roe noodles. I was really looking forward to eating crab roe noodles, and thankfully one of my colleagues took me out to eat those. But let's say I want a place with crab roe noodles that has a nice atmosphere — maybe it has a view or something, not your traditional crab roe noodle place. And then maybe I want it under 300 yuan per head, which should be pretty easy to do, I think. You'd be able to narrow this down, and this is how an agent would work: looking at all the different place entities, looking at the menus, escalating to browser use, determining the criteria, and then narrowing it down. seg 1365–1376

Back to the evening: preferences, weather, and saving the plan

Now let's return to the personal agent example. We found a place, we looked at the room, we saw the image. Now I add something the agent didn't know: the friend I'm going with prefers milder〔?〕 food — they do not like spicy chilies. So this is context for the evening together. The system should keep track of who the preference belongs to and which plan it affects, so we'll load that back into memory. The agent also found dishes we can ask the waiter about, and it gives us a useful question: can these be made without chilies? seg 1377–1384

And here's an interesting memory design detail. Not everything within a personal agent will be assigned to me myself; you have to have this concept of different people in your life, right? This specific person might not like chilies, but I love chilies, so if I'm going to hang out with this one person, we'll want to keep that object stored separately. I think this is a very useful outcome: we know what to ask when we get there, and we still have the original budget and restaurant in the context. seg 1385–1392

And then maybe we'll add something afterwards — maybe I want to go for a walk around the Bund, because it's my first time in Shanghai. So then it's going to actually check: would it be nice to walk around the Bund after dinner? I believe the answer yesterday was yes, but before that it was no, because it was raining. What you're able to do here is that Exa also indexes the weather across all different places around the world, and it determined, when I actually made this demo, that it was going to rain and it would be a bad idea to go walk around — so go ahead and do something else. seg 1393–1401

Each turn added context to the same evening, so then we want to save that. We get the restaurant, the budget, the photo, and the food preferences all saved, so we're able to return to it later. The memory carries all the personal context between the requests, and the saved plan and the decisions are kept here as well. seg 1402–1405

Proactive assistance

So far I've been asking the questions. But one important concept I touched upon at the start was what happens when something useful arrives while I'm doing something else. In this instance, the agent remembered that I like jazz, and then I got an email from Jazz at Lincoln Center Shanghai saying two seats have opened up. The email alone is not a reason to interrupt me — if I wanted everything to interrupt me, I'd just have all my email notifications on. So I wanted it to check all my conditions from memory. Am I free that evening? It'll go check my calendar. Is it within my ticket budget — do I want to spend more money than I'm willing to? And are there two seats available, because I want to go with my friend? Only when these conditions match would it notify me; otherwise it would just stay quiet. seg 1406–1416

So how is this possible? You'd be able to monitor for these sorts of events by leveraging Exa, as well as a clever browser use escalation policy. We have a product called Exa Monitors, but we can also just leverage our normal search and then take a look at the web page every so often with browser use. And that's how I believe the closed-source providers are doing it as well. So that's the proactive part: it was able to remember the intent and an incoming event, and then decide whether or not it deserves my attention. And I could still choose to reserve my seats. seg 1417–1423

Closing

This all started with one request: go find me somewhere to hang out in Shanghai. But anyone with a little engineering, I believe, can build the flow I've shown on their own, leveraging Linq as well as all those standard libraries I've shown, with Exa. I think we should all start with one recurring task in our lives; I believe using personal agents would make our lives a lot easier. You can decide what the agent should remember, what it needs to look up, and what should still exist when the chat ends. I'm Jakub from Exa. Thank you. seg 1424–1428
