Your Agent's Memory Is Next Quarter's Training Data

郭人通（Rentong Guo） · Zilliz · 2026-11-05 主会场 · 15:50–16:16 · 场次 d1m15 · 偏宣传

Zilliz 认为 AI 数据指数增长使传统数据库像端着不断被灌酒的扎啤杯，必然撑不住，所以把向量数据库升级为以对象存储为底座的湖库：成本接近对象存储、体验接近数据库，并用热温冷分层让 agent 的记忆与 trace 数据能直接用于下一轮训练迭代。

演讲骨架

  1. AI 能力每升一级，同任务 token 消耗涨一个数量级；头部业务背后的数据量也逐年上升一个数量级，且合成、模拟数据会让增速继续加快。
  2. 数据量到十倍以内靠服务器内的性能与成本取舍，到百倍千倍后单机架构没有取舍空间，只能围绕对象存储重构，即 lakebase（湖库）。
  3. 湖库 = 数据库的使用体验和性能 + 湖的容量和成本；用本地缓存、远端缓存、对象存储的热温冷三层，让所有数据都能查询，只在需要时把数据提升到热层。
  4. 同一份底层数据同时支撑实时检索、交互式探索和批量挖掘，缩短数据迭代飞轮；下一步是把查询的共性和历史下沉到基础设施，再争取一到两个数量级。

讲者提出的框架

  • 湖库（lakebase）四条定义：使用体验像数据库、容量像湖可无限扩张、单位成本接近对象存储、性能接近数据库，四点合到一个系统里。
  • 热温冷三层与按活跃度分层：本地缓存、远端缓存、对象存储三层成本各差一个数量级，按用户活跃度或查询需要动态在层间提升数据。

推出 / 提供

  • Zilliz 湖库架构（lakebase）：围绕对象存储重新设计的 AI 数据基础设施，在其上承载向量、文本、JSON、标签等语义数据的检索与分析。
  • Milvus：自 2018 年开源的向量数据库，Zilliz 同时提供商业化服务。

非共识

  • 数据增长的真正瓶颈是资源与数据的匹配问题：有限容量对抗指数增长不可持续，必须把假设改为无限容量底座，而不是继续做服务器内优化。
    本质上来讲，如果拿数据库架构去承载指数级的 AI 数据增长，它是一个拿有限容量、有限资源去对抗指数增长数据的问题，两者是不匹配的。
  • 未来数据更多来自生成和模拟，随 token 消耗积累，数据增速在 27、28 年可能进一步加快。
    也就是说，未来的数据更多是伴随着 token 消耗去积累的。

信号

动机：token 消耗与数据的指数增长

我们从向量数据库，或者说从 database 到 lakebase，一个非常大的演进动机就是数据增长；当然这个过程也伴随着 AI 能力提升之后 token 消耗的增长。这里有两张图。前面一张图：从最早的 ChatGPT 到现在三年多，在场很多小伙伴可能是从对话开始了解这轮 AI 的；但如果大家之前试用过一些早期的产品，或者读过一些 research paper，其实最早是从 completion，也就是填词这个阶段做下来的。假设填词的 token 消耗是一个单位，那么到对话、到 reasoning、到最近的 agent——agent 这件事从 research 的角度其实也好几年了，只是现在落地开始爆发——包括现在有了一些自演进的能力之后，基本上每跳一级，同样一个任务的 token 消耗就上升一个数量级。这是关于模型智能的能力、能解决的任务复杂度和消耗的这一张图。 seg 1474–1483

另外一张图是关于数据的，这是来自我们的一个观察。我们从 23 年，其实再往前也一直在做，就是去跟用户交流，观察每一年单一业务里最大的那个业务，它背后的数据条目大概是什么量级。今年已经到了千亿级，就是最大的一个业务背后有千亿条数据——不是 1,000 亿，是千亿条这个量级；去年是百亿，前年是 10 亿。每一年都如此，已经持续了四五年，每年翻一个数量级。 seg 1484–1488

接下来从我们的观察来说，到 27 年、28 年，这个增长速度可能还要再加速。因为在 23、24 年这个时间段，更多的数据来自我们的现有系统，或者来自人；而到现在，比如最直观的世界模型也好、自动驾驶也好，大家越来越多地开始引入生成的或者模拟的数据，包括跟大家比较近的短剧这些。也就是说，未来的数据更多是伴随着 token 消耗去积累的。所以这个过程虽然已经是指数级、比较夸张了，但 27 年、28 年在 AI 大规模落地的过程中，还有可能会加速。 seg 1489–1494

从 database 到 lakebase

这是背景。回到 infra 这边，我们是这样看的：一倍到十倍的时候，大家讲得更多的是做性能优化、成本优化，在这样一个 trade-off 空间里面我们是有解的；但是到百倍、千倍之后，在一个服务器内的空间里去做设计上的 trade-off，基本上找不到这么大的空间，所以只能走到架构重构。十倍之前，我们更多讲的是如何做好一个 database；到百倍、千倍之后，这条路其实是比较难以为继的。所以我们也是跟很多头部企业客户一起，伴随着他们业务支撑的挑战，去做了一个非常大的架构重构，也就是 lakebase 这样的方式。 seg 1495–1501

这是一个回顾：一倍到十倍，我们做了什么事？当年 23 年到 24 年，一倍到十倍的玩法，更多的是做服务器内的一些设计 trade-off。当时我们做了——当然现在也有——性能型实例、容量型实例、成本优化型实例，更多的是去挖算法本身的红利，包括在服务器内 DRAM、NVMe 这样的架构上，去做面向不同 workload 的取舍。到 25 年、到今年，包括明年，十倍到百倍、千倍的时候，我们走到了 lakebase 这样的架构下面。我觉得整体上最核心的架构重点，就是围绕对象存储去重新设计整个 AI 数据基础设施；在我们这边，就是围绕对象存储去重新设计，或者说重新定义数据库系统。 seg 1502–1510

湖库这个事，大家听起来好像"湖"和"库"都比较熟悉。现在很多特别是大的中台客户，本身自己就有湖，湖上面一般有几种不同类型的数据库，中间通过数据管道去连接。但湖库不是指这件事。我们给一个通俗易懂的、产品能力上的定义：什么叫 lakebase，什么叫湖库？就是使用体验是一个数据库的体验；数据的容量和扩张能力像湖一样，是可以无限扩张的；每份数据的成本是湖的成本，也就是接近对象存储的成本；性能接近、甚至达到数据库的性能。所以，湖库就是使用体验和性能是数据库层面的能力，而规模和成本是湖的水平，我们把这四条做到一个系统里面去。这是最直观的湖库的定义。 seg 1511–1517

无独有偶，我们当时在做的时候，因为看到了很多头部企业数据增长的挑战，摸到了这里，那是 24 年到 25 年初。那段时间我们正好在 YouTube 上看到 Cursor 的 CTO 在 Stanford 的一个讲座。他们当时也遇到了这个问题：应用抛出来之后，编程爆发，泼天的流量来了之后，到底能不能接住。那个报告里讲，他们在 24 年底、25 年初的高速增长期，几个月内换了四套数据库，没有一套能撑得住他们的增长，真的是几个月。这个报告的标题，我印象中是国内一家媒体——我忘了哪家了——起的，exactly 就是"数据库选错，公司差点凉凉"。泼天的流量来了之后险些没有接住。他们最后在内部的自研系统里也走到了同样的位置：要围绕对象存储去重构整个 AI 数据基础设施。换了这条路之后，一切服务都稳住了，而且后面的增长曲线持续了很久，到现在还是比较稳定的。 seg 1518–1527

为什么数据库撑不住：端扎啤杯的比喻

当然，从数据库到湖库，背后为什么数据库就不行，为什么一定要走湖库的架构，为什么像 Cursor 这样的团队在数据库层面也很难解这个问题？今天时间有限，不会深入探讨大型系统的那么多设计约束。在座如果有像我一样偏"老登"的程序员朋友，比如参与过当年一些大型分布式数据系统，或者分布式高性能系统的构建，一定知道我在说什么：维护这种大型分布式系统，特别是传统的 C++ 代码，它的复杂度有多高；特别是这样一个系统，如果要把它的规模提高一个数量级，这个事有多难。 seg 1528–1535

之前一直没有找到一个比较好的、直观的例子去讲这个事，直到今天在飞机上，我想到一个很好的比喻：在数据库里支撑 AI 的指数增长，大概是什么感觉呢？不知道大家有没有看到过，像德国、北美的酒吧里，服务生会端非常多的扎啤杯，有的一个人能端非常多的扎啤杯，甚至还有一些比赛，比谁端的扎啤杯多，然后走一段距离，酒尽可能不洒或者少洒一些。我们在数据库架构里支撑 AI 数据的指数增长，就非常像这个过程。 seg 1536–1541

我们的工程师，不管是开发设计还是运维的同学，就是端扎啤的服务生；这些扎啤杯，就是部署数据库的服务器上的资源；里面的酒，就像是我们在指数增长的数据。也就是说，我们一边要端着这些酒，一边数据还在不停地往里面灌，酒不停地往里面灌，我们要保证一直端下去，同时酒是不能洒的。比赛里酒是可以洒的，但实际情况下如果洒了，就意味着一些非常严重的系统问题，一般都是最高级别的问题，比如 OOM，或者极限水位扩缩容，或者一部分数据不可用，甚至整个系统不可用，都是级别非常高的系统问题。本质上来讲，如果拿数据库架构去承载指数级的 AI 数据增长，它是一个拿有限容量、有限资源去对抗指数增长数据的问题，两者是不匹配的。 seg 1542–1551

那为什么 Lakebase 湖库这个架构可以呢？最关键的一点，就是把两边拉齐了：我们的数据基础设施的假设，是拿一个无限容量的基础设施去对抗指数级增长的 AI 数据，这两边至少看起来就匹配了。所以包括我们自己内部，还有我们很多头部企业客户——大家的研发能力都不弱——换到这个架构之后，开始把团队的精力从解决大规模系统的复杂度问题，包括把所有约束都塞到一个杯子里面这样的问题，转移到更聚焦地去解决规模和成本的问题。这是一个非常非常大的转变。 seg 1552–1557

湖库的三层：local cache、remote cache、对象存储

到这个阶段之后，就到了具体的湖库。当然，湖库并不是简单地把一个数据库的脑袋装到一个对象存储的身子上就结束了。这不是今天报告的内容：因为它是一个数据库系统的 redesign，包括 architecture、algorithm，还有我们的索引、数据分片，都围绕新的对象存储做了重新设计。把湖库的这些技术细节抛开，只看数据层面——这里显示得不是很好——其实是三层：上面一层还是对应传统的数据库这一层，就是服务器本地的 local cache，本地缓存；中间还有一层，在服务器和对象存储中间，有一个远端缓存 remote cache；最底下是对象存储，就是最冷的这一层。所以就是热、温、冷三层，图虽然比较乱，但幸好文字上我拿颜色区分出来了。 seg 1558–1566

以 AWS 为例，最底下这一层非常接近对象存储的成本，AWS 的话没记错应该是 0.025，差不多在这个位置；remote cache 是三毛；如果是在服务器上，也就是传统的数据库，每 GB 每月折算过来差不多是三块钱的成本，都是美金单位。到湖库这个阶段，就等于给我们的 AI 应用一个重新审视数据、价值以及如何服务的新空间。这一套推出去之后，我们会跟很多客户坐到一起去看：我们的业务里面到底哪些数据真的值得放到三块这一档去服务，哪些可能放在三分这一档就 OK 了。每一级之间是一个数量级。所以这样一个架构，可以很好地支撑接下来的数据，至少到 26、27 年，乐观一点的话可能到 28 年这个阶段数据的进一步增长。 seg 1567–1575

另外一个点，我刚才漏讲了：为什么原来的数据库系统不行？因为我们只能在最上面的热缓存、本地缓存这一层提供正常的数据访问和写入服务。现在湖库不一样了，在这样一个架构里面，你不管把数据放到最底下的对象存储这一层，还是远端缓存这一层，还是本地缓存这一层，它都可以提供业务功能上需要的查询、读写、分析任务。你更需要关心的是 trade-off 问题：哪些我可以降低成本放在下面，哪些我要服务质量高，多花一点钱放在上面。 seg 1576–1581

例子：在线服务与离线挖掘

举个例子，比如 AI 和 agent 应用，这个非常直接。假设有 100 万到 200 万的注册用户，传统上我们可能把所有用户数据全部放到数据库上，也就是最上面三块钱的成本。现在就有很大的变化：我们可以把这 100 万、200 万的全量注册用户全部放到对象存储上去服务，只把日活，比如 3% 到 15% 的用户放到上面，花三块钱的成本去支持；周活或者月活放到中间 remote 缓存这一层。当然这个图看起来是静态的，实际上它是动态的：如果用户新上来，最近活跃的用户会从最底下这层放到上面。如果再加上一些业务层面的信息，甚至有可能做到整体成本接近对象存储，但所有用户的服务质量接近最上面的数据库。 seg 1582–1588

举个例子，有一个前一阵子不怎么活跃的用户，他的数据已经落到了最底下最冷的这一层。他打开了这个 APP，或者登录了，业务侧就给 infra 一个信息，说帮我把这个用户的数据从第三层加载到第一层，这个过程是秒级的，很快。所以当用户真的打开应用、他的任务涉及数据查询的时候，绝大多数情况下他的数据已经在最上面最热的这一层了。所以这样一个架构，特别是加上一些业务侧非常容易拿到的信息打到系统侧，基本能达到成本很接近对象存储，而服务质量——而且是全部用户的服务质量——都很接近上面本地热数据库这样的级别。 seg 1589–1595

除了面向线上服务以外，线下的挖掘也非常类似。更多的是，我们不管是从外部数据源还是自己的服务积累了非常多数据，典型的场景就是要去找哪些 agent trace 也好、数据本身也好，是我的模型或者 agent 做得还不够好的，把这些挑出来之后，加到我的 harness 的部分，或者 post-training 的部分。以往我们可能要全量地去起一些 Spark 或者 Ray〔?〕 job，或者真的成本很高、能接受的话，就都放到一个数据库里面。现在结合刚才的架构，所有数据确实是放在对象存储的，但任何一个时间要对这些数据访问的时候，并不是全量数据——这里面有很多数据分片和加载技术的优化——只有这次查询一定涉及的那一部分数据会加载到上面来，随着任务结束或者请求结束之后，上层又回到零负载。 seg 1596–1604

所以整体来说，AI 方面我们接触最多的是三大类负载，就是这个图中间这一层。第一类是实时的 retrieval，或者 real time 的 search，典型的比如 memory；或者 IP 版权，比如我们生成了一个短剧，要看看有没有版权侵权问题；或者做一些多模态召回，比如我做多集的短剧或其他内容，要保持它的一致性；或者线上给用户提供搜索、推荐服务。这部分是实时召回。还有一部分是 interactive discovery，就是刚才说的，我要观察我的后台数据，看哪些数据能够帮助我进一步提升 agent 或者模型能力。还有一些是批量分析任务，比如去采后训练数据，解决多样性的问题，或者聚类，找一些分布中长尾的离群点，等等。 seg 1605–1614

数据飞轮与下一步

整体上来说，除了刚才说的 lakebase 能够帮助大家支撑指数级增长、提供容量和成本上比较好的方案以外，更多的一点是，因为我们整个架构是数据统一放到最底层，上面是计算，所以它能够很快打通整个迭代闭环，也就是让数据基础设施提高数据迭代飞轮的效率。刚才这个图可能比较复杂，这是一个简化的形态：底下是整个业务数据做统一的积累，上面的业务就是刚才说的三大类负载，整体上能够很好地对抗规模和成本的问题。 seg 1615–1620

当然，我们也有一些走得特别靠前的用户会问：lakebase 架构按照这个模式，比如 27 年我们就会看到千亿、万亿的应用，后面可能更高，是不是够用？lakebase 架构再往后要 10 倍、百倍的空间从哪里要？我们现在看到的一个很关键的点是，整个数据基础设施，特别是找数据这个环节，有点像大模型的 cache 一样：我已经查过、算过的东西，能不能不要再重新算了？这里有非常多的机会。比如说，基础设施系统要了解更多业务侧的信息：你不管是多次查询还是多轮查询，我希望更快地知道你可能多轮查询找了好几个地方，我能更快地告诉你，你多轮查询最后要查到的那个位置，我直接给你，以避免多轮查询。或者，不管是写代码也好、日常的任务也好，绝大多数情况下大家的查询是有共性的，把这些共性再压到基础设施里面，对有共性的部分，尽可能移除这些重复的查询。到下个阶段，我们觉得这里至少还会有一到两个数量级的提升空间。 seg 1621–1631
