Your Data Agent Needs More Than a Knowledge Graph -- From Semantic Layers to Executable Ontologies with Apache Ossie

Harrison Zhao · Datus AI · 2026-11-05 分会场 · 16:22–16:39 · 场次 d1b10 · 偏宣传

可信的数据 agent 不能只靠知识图谱，而要在语义层之上加本体，并配一个把 Apache Ossie 规范编译成确定性 SQL 的运行时（Datus 的 Dosi），像编译器之于代码 RL 那样给 agent 提供可验证的反馈；知识图谱告诉 agent 事物是什么，语义层告诉它怎么算，本体则是语义层上的“确定性 RAG”地图。

演讲骨架

  1. data agent 的瓶颈不是写 SQL，而是数字可信：从写 SQL、到信任数字、到做决策，本体（ontology）要解决的是第三阶段。
  2. 本体不等于知识图谱：图谱只告诉 agent “是什么”，缺少确定性引擎时多表 join 会算错（如 fan-out），行动层的难点也是决策是否可信。
  3. 在已有语义层之上叠加本体，用 Apache Ossie（跨厂商开放语义规范）统一指标定义，Datus 做了 Rust 实现的运行时 Dosi，把 spec 编译成确定性 SQL。
  4. 本体为语义层增加映射、规则、关系三类内容，可构成 North Star 指标驱动的“agent 探索、人验证、上线”决策闭环。

讲者提出的框架

  • data agent 三阶段：第一阶段写 SQL（大模型基本解决），第二阶段信任数字（指标定义），第三阶段做决策（本体要解决的）。
  • Ossie 四层架构：底层 SQL 表达式统一方言，第二层面向 BI，第三层指标（宽表查询接口），顶层本体（实体关系）。

推出 / 提供

  • Dosi：Rust 实现的语义运行时，把 Apache Ossie 的 YAML 规范翻译成多方言确定性 SQL，并拒绝 fan-out 等错误聚合，规划原生归因。
  • Datus 开源 data agent 与语义层：开源的数据 agent 和语义层实现，作为 Dosi 的上层应用。

非共识

  • 传统本体里手写推理机已不重要，大模型能覆盖推理，真正有价值的是概念与关系。
    So the hand-built or native reasoner is not important anymore.
  • 本体是“确定性 RAG”：用业务形状的地图而非向量检索来索引表与指标。
    And the last point: ontology is a deterministic RAG.
  • 数据领域缺的是类似代码里的编译器与数学里的 Lean 的验证工具，有了它 RL 才能让数据 agent 变可靠。
    Because reinforcement learning can learn from validation tools.

信号

  • 市场格局 / 规律Snowflake、Salesforce、dbt 发起 Open Semantic Interchange 并捐给 Apache（Ossie），语义层正从各家私有走向开放标准。
  • 市场格局 / 规律本体概念因 Palantir 重新流行，创业公司在已有语义层之上叠加本体，而非从零重建。
  • 关注的指标强调数字一致性、指标正确率与可归因（“为什么变了”）而非 text-to-SQL 基准分。

Hi everyone, I'm Harrison from Datus AI, and today I'm sharing about how we are moving from semantic layers to executable ontologies with Apache Ossie. As a co-founder and engineer in a startup, we have been working on an open-source data agent and the semantic layer for over a year and a half. Today I want to talk more about our opinion on ontology, why this problem is important, and what we learned from building this kind of real data system. seg 1207–1212

Why can't we trust the numbers?

The first question is interesting. We know that AI is becoming smarter every day, and it can now solve the hardest mathematics problems. At the beginning of last month, OpenAI released 722 papers on AI mathematics, and it solved a lot of problems, such as the Navier-Stokes problem and the Exponential Time Hypothesis, which is a very important, very basic computer science problem related to the NP and P problems. seg 1213–1219

But on the other side, the AI can solve such hard problems — so why can't we trust the numbers generated by a data agent? Maybe the first time we ask the agent what the Q3 revenue is, it gives a number, but if we change the context a little bit, it gives another answer. That's the problem: the large model is always a probabilistic model. Next-token prediction cannot guarantee something definite and deterministic. But that's not the problem of the large model. It's our problem, right? How can we improve that? seg 1220–1231

I think we can divide the development of data agents into three stages. The first stage is how to write SQL. The second stage is how we can trust the number. The third stage is how the agent can make decisions. We can do it step by step. Stage one is generally solved by the large model 〔?〕: after years of pre-training and post-training on SQL data, large models run pretty well on text-to-SQL benchmarks. The second problem is the definition problem. You need to define the metrics in your company — what revenue really means in your company and how it can be calculated correctly. And now we are not satisfied with just answering questions with a data agent. We need the agent to make decisions, to drive the AI-native organization forward. That's the problem ontology wants to solve. seg 1232–1253

What ontology is and what it isn't

Ontology is a bit of a buzzword recently, especially after Palantir brought this concept into the agent world. I want to talk about what it is and what it isn't, in my mind. First, it's not a new concept. Ontology was already around 20 years ago, but it was basically built on top of OWL or RDF/RDFS, with rule-based reasoners on top of that. Take a very simple example: Alice is Bob's parent, and the reasoner can infer that Bob is Alice's child. This is trivial for a large language model, because it can cover all this kind of reasoning now. So the hand-built or native reasoner is not important anymore. But the relationships and the concepts are still useful for the data agent and the large model. seg 1254–1269

The second point is that some people think of ontology as just another knowledge graph. Take this example: the left side comes from the Palantir and Apache Ossie websites. A flight can depart from or arrive at an airport, follow some route or region, and go to a destination at another airport. This is pretty useful. You can put this knowledge graph into your graph database, or directly into the prompt of your data agent, and it helps a lot. seg 1270–1281

But it still cannot solve the problems when we touch the data underneath. For example, one flight has 120 passengers. But if you join another table, like delayed flights, it may double or triple the number to 330 passengers, because it doesn't know the details of the relational database — the join type and so on. It's a pretty simple example, but in real use cases it will be more complicated. Large language models often fail on multi-table joins and the very complicated relationships behind the numbers. So we need a deterministic engine underneath the knowledge graph to make sure the numbers are calculated correctly. seg 1282–1298

The third point is action. Action is a very important part of the Palantir ontology. But in the agent era, it's relatively easy for us to expose an API as an MCP server or MCP tools and bind it into an agentic loop. That's pretty easy. The hardest part is: can we trust this decision? From raw data to metrics to decisions, how can we make it trustworthy? It usually becomes a process: from trusted metrics, to analytics, to business rules, and finally binding them to actions. The action can be an alert or a real CRM action; both are okay. But the key problem is: can we trust it? seg 1299–1313

Building on the semantic layer: Apache Ossie

So we know that we need to build an ontology to improve our data agent. But how can we build this kind of thing? Do we already have some basics, or do we need to start from scratch like Palantir? I have been working in the big data area for many years, and I know every company has had its big data movement. All of them are built on top of the dimensional model — or, another way of saying it, the semantic layer. For the past two years, Snowflake, Databricks, dbt — all kinds of vendors — have provided their semantic layer solutions to narrow the gap between natural language and SQL. So we have quite a lot of ways to build such things. Ontology is just a top layer on top of the existing semantic layer, or we can create the semantic layer based on your existing SQL and context. seg 1314–1325

But now there's another problem: every vendor has its own semantic layer, its own spec for metrics — different formats, different APIs, and different definitions. How can we share them across dashboards, BI tools, and AI agents? That's the origin of Apache Ossie. In September last year, 2025, Snowflake, Salesforce, and dbt created this project under the name Open Semantic Interchange. They want to exchange different formats into one, and translate from one to another — just a plain YAML file in your own file system. This year they contributed it to the Apache Software Foundation as Apache Ossie. Here is a very simple example where we have the semantic model and the ontology layer in just one file. seg 1326–1338

Here is the architecture of Apache Ossie. We have four layers. The bottom layer is the SQL layer, the foundation of the expression language. It can unify different database dialects into one expression language. Layer two is for BI: you can imagine that Tableau, Superset, or any kind of BI tool needs an interface to directly access this kind of semantic layer. The third layer, the most important one, is about metrics. Most data agents just access these metrics using a wide-table query interface, because it reduces the complexity for the data agent of figuring out how to join many tables together. And the top layer is ontology. You can think of it as talking about entity relationships and knowledge-graph-related things. seg 1339–1349

Dosi: a semantic runtime

So that is only one piece of our solution. Back to the example I talked about, the mathematics: what does the large model really need? Why can it solve such coding problems and mathematics problems this year? Because reinforcement learning can learn from validation tools. Just imagine that Lean is a formal language and the validator, the compiler, in mathematics; and GCC or rustc, any kind of compiler, is a kind of validation tool. So what is it in data, in the semantic layer? Because Apache Ossie is just a spec, not a compiler engine. seg 1350–1359

So we built one. It's Dosi, a semantic runtime. It does just one thing: translate the Apache Ossie spec, a YAML file, into deterministic SQL for every dialect. We support over 20 dialects, and it runs pretty fast — 10 times or 100 times faster than the previous MetricFlow or Cube 〔?〕 — because it's written in Rust. And most importantly, it can generate deterministic SQL 〔?〕 for the semantic layer you already built. It can reject some errors, like the fan-out problem or some complicated wrong aggregations. And in the last part, we are building some native attribution to make it easy to answer "why" questions. Because the data agent doesn't just need to figure out what the number is; it also needs the capability of fast attribution — why the data changes. seg 1360–1371

Here are the two layers. The left diagram is about the semantic layer: tables, datasets, metrics, joins, and grain, also with some aggregation. The right part is about a map: concepts, relationships, and how to map these concepts onto the datasets beneath. So ontology is more like a RAG, but it's not using vector search to figure out which table or which metrics we need. It's using a business-shaped map to accelerate or index the whole catalog 〔?〕. seg 1372–1385

What ontology adds to the semantic layer

Here is a sample of what exactly ontology adds to the semantic layer. It adds just three components. The first is mapping. Different businesses have different aliases, different ways of speaking, for a term. We can even map different semantic models: sales has a semantic model, finance has a semantic model, supply chain has another one. We can use one ontology map to map them together and use it across different business domains. seg 1386–1397

The second is rules. Take status as an example. In one scenario, maybe status can only be "open" or "resolved", but in the database there may be five or ten values. For different values, we can set a specific value domain, so that Dosi rejects the wrong answer or the wrong function call. seg 1398–1404

The last part is relationships. We can build an ontology beyond joins, with maybe some linear regression or other kinds of relationships. seg 1405–1408

Use case: a North Star metric feedback loop

So here is the final demo, a use case: how can we use ontology in real-world workloads? Maybe this diagram is a little hard to read, so I'll talk generally about the idea of this use case. Imagine that we are running an e-commerce business. The North Star metric is repeat purchase rate. We already have a metric system, including orders, revenue, customer count, marketing, return rate and so on, organized as a metric tree. Now we can just ask a question: how do we improve the repurchase rate, the North Star metric, by creating, for example, a new promotion policy? seg 1409–1428

The agent can use this kind of ontology to choose a population segment — for example, customers with at least five orders, at least $1,500 in contribution margin 〔?〕, and a return rate below 20%. It becomes a feedback loop: we start with a North Star metric, the agent explores the data and possible rules, a human validates the rules, and they are put into production. It can be a pretty good feedback loop. It's not just another better SQL or better dashboard; it becomes better decisions based on trusted metrics and reusable 〔?〕 business rules. seg 1429–1439

Summary

So here's the last page, a quick summary. The knowledge graph tells the agent what things are. And the semantic layer — it's a two-layer system — the semantic layer tells the agent how to count the numbers. So every data agent needs a good semantic layer to set the agent's flow 〔?〕, because it can get the numbers correct, or make the numbers trustworthy. With a compiler that generates correct SQL, the agent can explore how many metrics and how many dimensions there are and build a metric system — a digital twin 〔?〕 of your business. And the last point: ontology is a deterministic RAG. It's a map over the semantic layer that lets the agent know your business well. That's all. Thank you. seg 1440–1450
