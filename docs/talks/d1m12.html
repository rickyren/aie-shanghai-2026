Kubernetes Is Not Your Sandbox

Mislav Ivanda · Daytona · 2026-11-05 主会场 · 14:52–15:05 · 场次 d1m12 · 偏宣传

Daytona 主张 Kubernetes 不适合做 agent 的 sandbox 基础设施：K8s 为无状态长驻服务设计，而 agent 需要有状态、短命、海量并发的隔离环境，所以应使用专业 sandbox 提供商（如 Daytona），而不是自己在 K8s 上自建。

演讲骨架

  1. sandbox 的含义已从跑生成代码，扩展到 shell 访问、agent 运行时、RL 大规模并发和 computer-use agent。
  2. Kubernetes 为长期运行的无状态 web 服务而生，而 agent 需要有状态、短生命周期、按需启停，需求恰好相反。
  3. 在 K8s 上补状态要挂外部存储，会带来 IOPS 下降、挂载慢、单节点密度降低；Daytona 用本地快照、快照分发、增量传输来解决。
  4. 基准测试显示总耗时更短、突发负载成本更低，因此应买 sandbox 服务，不要自建。

讲者提出的框架

  • sandbox 提供商三支柱：基础设施（性能/吞吐/并发）、primitives（fork、snapshot 等）、tools（给 agent 的工具并防止泄露密钥）。

推出 / 提供

  • Daytona sandbox：面向 agent 的有状态隔离计算环境，含本地快照、快照分发与增量传输。

非共识

  • 不要让 infra 团队默认用 K8s 来做 agent sandbox，“用 sandbox 来做你的 sandbox”，不要自造轮子。
    As we like to say: use a sandbox for your sandbox.

信号

  • 市场格局 / 规律sandbox 用途从跑代码演进到 agent 运行时，再到 RL 评测/后训练的大规模并发和 computer-use，需求侧由模型训练推动。
  • 关注的指标追踪 sandbox 启动时间、总任务耗时和突发负载成本，称成本与性能是 agent 领域的首要要求。
  • 市场格局 / 规律自建（K8s）与托管 sandbox 服务的竞争，类比自建认证与使用认证平台。

Hello everyone. My name is Mislav, and I'm a developer experience engineer from Daytona. Today I'll be talking about why Kubernetes is not a good option for agentic infrastructure. A disclaimer right at the beginning: this talk will not be about throwing hate at Kubernetes. Kubernetes is great. We also use it on our side for our control plane, as I guess most of you also use it in your companies. But I want to showcase why choosing Kubernetes for the agentic infra layer is not a good option, and notify you in advance not to go with this approach and to choose the other one. seg 836–843

Why Kubernetes? Because most of the time, when you start doing stuff with AI agents inside your company, you eventually come to the phase where you need isolated environments, either for running your agent-generated code or because your agent needs shell access, etc. Then you contact your infra team to set up a Kubernetes cluster for running pods and doing these tasks inside Kubernetes. That's why we chose Kubernetes for this topic. seg 844–850

What is a sandbox

Since we at Daytona are a sandbox provider, I think the best way to start is to explain what a sandbox actually is. Sandbox is not a new term; it existed before AI agents came into the picture. Back in the days when we were searching for solutions on Stack Overflow, you probably noticed the code sandbox environments where users could upload their solutions to some Stack Overflow problem, and you could run this code inside these sandboxes and check whether everything works and whether their solution is applicable to yours. Also, if some of you have dealt with, let's say, Stripe or Salesforce sandboxes, their sandboxes also refer to testing environments where you test everything before you go to production. seg 851–858

In AI agent terminology, a sandbox is defined as a compute environment which your agent uses for tasks that require isolation. So the common denominator between AI agent sandboxes and previous sandboxes is the isolation part. Defining a sandbox in this broad way, as an isolated compute environment, is pretty general; there's no precise mathematical definition of what a sandbox is. The reason is that things are changing really fast. seg 859–861

When the first AI agents came into the picture, they used sandboxes just for running their generated Python code or scripts. After that, models became more advanced and required shell access. After that, people figured out: hey, we can maybe move whole agents inside the sandbox and use the sandbox as the agent runtime. Then, for I would say more than half a year now, people have figured out that if they can spin up thousands or tens of thousands of these sandboxes with agents inside them concurrently, they can do pretty cool stuff, especially in the reinforcement learning space, like evals, benchmarks, post-training, model fine-tuning, etc. And then, for applications that don't expose APIs, like some enterprise apps on some OS, computer use agents, which can be considered general-purpose knowledge workers, started to emerge, and they had compute-level requirements. The same thing happened there: people figured out, hey, we can also run these agents at scale and again do the same stuff as in the RL space. seg 862–875

Kubernetes vs. agent requirements

Now back to Kubernetes. As I said, Kubernetes is exceptional for the task it was designed to do. It was released in 2014, and its main objective was to run containers at scale and run them reliably: recovering them from errors and failures, and letting you update running containers without downtime. It's ideal for running long-running, stateless web services. But with agents, the requirements are completely opposite. Agents need, number one, statefulness, to preserve their work: for example, when you stop an agent's work and resume it after two days, you want everything preserved in the sandbox. And most of the tasks agents do are short-lived: agents often spin up these sandboxes on demand, do some stuff inside them, and shut them down. So here we see completely opposite requirements and definitions between these two architecture types. seg 876–885

That's the task we took on at Daytona: basically rebuilding the infra layer for agents. We decided to divide the features every sandbox provider should implement into three pillars. The first pillar, infrastructure, is related to performance, throughput, and concurrency. The second one, we call it primitives, is mostly about features coupled with the infrastructure layer, like forking, snapshotting, etc. The third one is tools. Since the agent moved inside the sandbox, your goal as a sandbox provider is to enable tools for the agent so that it can do its task in the most optimal way. On the other hand, you also need to prevent the agent from doing dumb things, such as leaking your secrets. seg 886–894

This is what it takes to spin up a sandbox using Daytona, and on the right is what it takes to spin up a sandbox on Kubernetes from ground zero. We're not going into the details of this slide, but the question emerges: why would you want to do this? And it's not just about developer experience and ergonomics. It's also about performance and cost, which is, I would say, the number one requirement in this AI agent space. For example, you can see that by comparing the third row, sandbox spin-up times. seg 895–900

What Daytona does differently

A natural follow-up question is: what do we do to achieve these new features and requirements compared to Kubernetes? I've put here three short topics about what we do differently. Number one is local snapshotting. Everything inside Daytona, when a sandbox runs and stops, isn't deleted or wiped out; it's still preserved on the runner device or cache storage. So next time you resume the sandbox, it's basically just a start of the container. The main goal here is to prevent pulling, or cold starts where you need to pull the image from some Docker registry, etc. And our distribution algorithm prefers nodes that already have the sandbox image stored. seg 901–913

Number two is snapshot distribution. In short, if some user or company uses a certain snapshot at large scale and pretty often, we propagate that snapshot to more runners. And if some snapshots are not used, we deactivate them and clear them from nodes to save space. The third one is a delta-based approach: we don't transfer whole images, we only transfer differences, or deltas, which enables even cold starts to be pretty fast. seg 914–921

Back to Kubernetes. This is the flow required to spin up a sandbox, or a pod, on Kubernetes. As you can see, because of its nature, Kubernetes has these defined sequential steps that need to happen in order to start a pod. In the best case, you'll get a running pod or sandbox in one or two seconds, but mostly it will be in the order of tens of seconds. Also, because of these sequential steps, your throughput can only be around 100 pods or sandboxes per second. And the default density, the number of sandboxes you can place on one Kubernetes node, is around 110. seg 922–928

Statefulness

Next part: statefulness. As I mentioned, the number one agentic runtime requirement is statefulness. At Daytona, everything is stateful by default and everything is preserved, so when you resume the sandbox, everything is already on the disk. But Kubernetes is stateless. What does that mean? It means that if you want to achieve statefulness on Kubernetes, you have to mount some kind of external storage. And this is the trap, because once you do that, all of your file system operations go over the network, and your IOPS fall from around 500k on Daytona, which is near native, to around 50 to 60k when we're talking about EBS, for example. You also need to explicitly choose what parts you want to preserve; everything is not preserved by default like on Daytona. seg 929–939

And this is what it then takes to spin up a pod or a sandbox when you have external storage and statefulness in the picture. Typically it takes around 30 to 19〔?〕 seconds to mount the external volume to the node where the pod is running. When the external storage mount goes into an error state, you can only remount it after 6 minutes. Because of the limited number of these, let's say, sockets on the nodes, you can only mount 25 to 39 volumes on a single node. Previously I mentioned you can have 110, so the number of sandboxes you can have on a single node falls by three times. And you can only mount one volume per sandbox, per pod; you can't mount a single volume to be used by multiple sandboxes. So this is a pretty bad state you enter when you try to set up your own stateful Kubernetes for sandboxes. seg 940–951

Benchmarks and cost

To prove all of this, and not just talk about it, we did some benchmarks. The benchmarks consisted of three tiers of tasks. Tier zero was essentially running a sleep command and starting a sandbox, which surfaces the sandbox spin-up time. Tier one was doing some light CPU and file system work. And tier two was giving the agent actual SWE tasks to run, which essentially surfaces what your real time in production will be like when your agent actually solves real-world tasks. seg 952–957

These are the results for all three tiers. As you can notice, Daytona is the green one; it's at the bottom, and it was the fastest among all the options. And this is for one trajectory. Most people run thousands or tens of thousands of these trajectories concurrently, so you can sense how this accumulates over a large number. Translated to numbers: running the same workload on Daytona versus these Kubernetes options takes 36% less time. That's a huge number, because time is money and you need to move fast, especially in the AI domain. seg 958–967

Next, spiky workloads. These are workloads that require a lot of infrastructure for a certain amount of time, but outside that time the infrastructure sits idle and isn't utilized, yet you still pay for it. By contrast, when you use a sandbox provider, you spin up sandboxes on demand and just pay for the time the sandbox is up and running. We did a comparison on 1,000 sandboxes running for 176 hours; that's like running 9 to 5 daily for a month. The result is that it costs you 2.7 times less to run the same workload on Daytona than on your own Kubernetes setup. seg 968–978

So I hope, based on all of these slides, it's pretty obvious why using a sandbox provider is a better approach than using Kubernetes for the agentic infra layer, regarding developer experience, ergonomics, money, and time. As we like to say: don't reinvent the wheel. Just as it's not that smart to roll your own authentication system rather than use a well-established authentication platform, with sandboxes you should trust people who are experts in this field, because believe me, rolling your own sandbox isn't that easy. And if you mess up, you mess up big time: if secrets leak, you can basically kill your whole product. As we like to say: use a sandbox for your sandbox. That's it. Thank you. seg 979–987
