From 3D Generation to World Models: Building Persistent Interactive Worlds for Physical AI

Gavin Luo · VAST / Tripo AI · 2026-11-06 主会场 · 14:32–14:45 · 场次 d2m10

Tripo 面对 coding agent 能用代码搭场景的冲击，把定位改为 agent 的工具：规则可描述的部分交给程序，难以描述的细节（人脸、生物）交给 3D 模型；并推出开源的 EdenLive，让游戏程序持有世界状态、生成模型实时渲染画面，朝可持续运行的世界和机器人环境推进。

演讲骨架

  1. 三年前提出「物体、场景、世界」的三级阶梯；Tripo 在物体层已从 TripoSR 走到细节更丰富的 Tripo P2。
  2. 今年 coding agent 能用代码直接搭出室内场景，让 3D 公司必须重新回答模型该做什么；结论是「能描述的由 agent 写代码，只能识别的由模型学」。
  3. Project Eden 把世界状态显式放在程序里，由学习型模型负责渲染，使灭火、涂鸦等变化持久、多视角一致；EdenLive 是其实时渲染器并已开源。
  4. 仍有未解问题：角色漂移需要更好的记忆、控制不足、评测难（agent 会在可走性测试里作弊）。

讲者提出的框架

  • 能描述 vs 只能识别：能描述的内容（门的位置、得分、房间布局）由 agent 写代码；只能识别的细节（脸、生物形状）必须由模型从数据中学习。
  • 物体、场景、世界三级阶梯：先生成资产，再搭建能发生事情的场景，最终是持续运行、服务人和机器人的世界。

推出 / 提供

  • Tripo（含 Tripo P2）：文本或图片生成 3D 模型与角色，可供 agent 调用。
  • EdenLive：实时生成式渲染器：游戏程序保留规则与状态，模型据参考画面和提示生成更丰富的画面。
  • Project Eden：显式世界状态加学习型渲染，使世界变化被持久记录的研究预览。

非共识

  • agent 与 3D 模型的分工边界是能否被描述，而不是模型强弱。
    if you can describe it, an agent can write it; but if you can only recognize it, a model has to learn it.
  • 世界模型的状态应由程序显式持有，生成模型只负责渲染，所以风格改变不会改变得分归属。
    Keep the world state explicit: the program knows what happens — where the door is, whether it is open or closed, and what happens when you walk through it.

信号

  • 市场格局 / 规律coding agent 能力提升直接威胁纯 3D 生成公司，后者转而成为 agent 可调用的资产工具，并向世界模型延伸。
  • 发布 / 开源EdenLive 的模型权重和流式接口代码以 Apache 2.0 开源，支持实时渲染与离线重渲染。
  • 数据信号机器人示范视频被重渲染成不同视觉变体（手换成机械臂），用于扩充机器人学习数据，但物理准确性与有效性尚未验证。

Today we serve tens of millions of creators across nearly 200 countries and regions. Behind it, we have a research team; we have published over 60 papers at leading conferences and more than 50 open-source projects. But creating individual objects is only part of our ambition. The game engine handles the rules, the movement, and the score. EdenLive handles how the world looks. They work together: the game responds to what you do, and AI generates what you see. The staircase: objects, scenes, worlds

The story behind it actually started three years ago. At SIGGRAPH 2023, our CEO Simon showed this three-step staircase: first, generate an asset, an object; then build a scene where things can happen; and eventually build worlds that keep running, for people and also for robots. That gave us a direction. In three years we have made progress and found some new surprises along the way. seg 1839–1845

Let me start with objects. On the left is our open-source model, TripoSR, from early 2024. You put one image in and it gives you a rough 3D shape. On the right is Tripo P2. If you look at the wireframe, you can see how much structure the model has learned. For an artist, those details matter; they affect how much work comes after the generation. Here's one photo that turns into a mesh, a detailed sculpt, with a texture you can zoom right into. Look at the face: imagine trying to specify every detail in code. That likeness is something the model learns from data. seg 1846–1861

When coding agents started building 3D

Then something happened: coding agents got much better, and we had this new question. Two days after GPT-6 Astra came out, our team started a group chat called "Did Astra Solve 3D Today?" You can imagine how that felt for a 3D company like us. We had one rule: you can only post what you actually tried. Nothing from Twitter, nothing from YouTube, nothing from Xiaohongshu — you have to try it yourself. So people started asking agents to build scenes and sharing the results. Some of them were surprisingly good. For example, these indoor scenes were built entirely in code by agents, in tens of seconds, and no AI-native 3D model like Tripo was used. One of the researchers said, "I haven't found an indoor scene that has to use Tripo." Another colleague replied, "Honestly, it was a bit of a panic." Fair enough. A lot of a room can be specified — the dimensions, the layout, the furniture — and the agent was already good at turning those things into code. seg 1862–1884

So we had to ask: what should a 3D model do now? And if agents are the ones calling it 〔?〕, what does an agent actually need from us? Here is a useful division of labor we found. An agent can write a lot of what we can specify: put a door here, make it open, keep track of the score. A model can learn details that are much harder to specify: the face of a character, the shape of a creature. That gives the agent a powerful tool to work with, and people are already using that combination. All in all, as I put it here: if you can describe it, an agent can write it; but if you can only recognize it, a model has to learn it. That's where we come in. seg 1885–1894

If you caught Sac's talk yesterday, you have already met the creator behind this project. This is The Little Prince: Across the Stars. He built it in just 16 days using Claude, Blender, and Tripo. What I love about this example is how those tools came together: the agent helped build the game, and Tripo helped build the 3D assets that brought it to life. It's always nice to have your case study also on the speaker lineup. On the right-hand side is one of our Japanese creators, called Nano 〔?〕. It takes a drawing and turns it into a character that can move. These examples help us see the opportunities more clearly. As agents take on larger projects, they need assets to fill them. And once you have those assets, here comes the next question: how do you make the whole world work? seg 1895–1908

Project Eden: a world that keeps track

So here comes the second part. A 3D asset is a noun. A world needs verbs: opening a door, moving a chair, putting out a fire. And when you leave and come back, those changes should still be there. That's the next step on our staircase: a world that keeps track of what happened. That's the idea behind Project Eden. Keep the world state explicit: the program knows what happens — where the door is, whether it is open or closed, and what happens when you walk through it. Then let a learned model render what you see. So you can change the camera or the visual style, and the state is still there, keeping track of the same world. seg 1909–1923

Here is what that lets us do in the research preview. You put out a fire, and it stays out. Leave a mark on the wall, and someone who arrives later sees it too. And two players can look at the same race from different cameras, because both views come from the same state. seg 1924–1928

EdenLive

Now, to actually play in a world like this, it has to keep up with you. That brought us to EdenLive. Watch this submarine. The small view shows the game program's grey-box output. The main view is EdenLive's rendering. The program decides whether the submarine has reached the treasure and where to pick it up. EdenLive receives that unfolding scene and renders it. So the game has a clear objective, and the visuals follow what actually happens in the program. seg 1929–1939

Here is the loop if you want to build with it. A coding agent builds a simple game. You press a key, the game updates its state and renders a rough view, and EdenLive takes that view, a target first frame, and a text prompt, and generates the next frame. Important events can also arrive as short text descriptions. You see the result, act, and the loop continues. The useful part is the interface: reference footage. It can come from a game engine, an animation tool, or another program. Each game doesn't need its own custom state interface to the model. seg 1940–1949

EdenLive generates chunks using the reference frames received so far and a flexible amount of history, and it keeps generating. With the 5-billion-parameter model, our demo setup reaches 720p at 24 frames per second. There's also an offline mode for rendering existing footage. The detailed method and the benchmarks are in the paper we just published. seg 1950–1954

Here are some more examples: keep the layout and the motion, change the look. That opens up game previews, different treatments of animation, and re-rendering real footage. In the game examples, the program still owns the score; changing the style doesn't change who got hit. seg 1955–1960

The same ideas take us in another direction, and that is robotics, physical AI 〔?〕. In the inset, a person is handling an object. In the main view, EdenLive replaces the hand with robotic arms, while keeping the motion and scene layout. That gives us a way to explore visual variations of a real demonstration. We still need to test the physical accuracy and the usefulness for robot learning. But in the longer term, we want environments where robots can act, observe the consequences, and try again. That's the third step on the staircase we're working towards. seg 1961–1969

EdenLive is open source under Apache 2.0 — the model weights and the streaming interface code — so you can take these parts and build on them. If you actually try it, we'd love to hear where it breaks, what the successes are, and what the failures are. seg 1970–1976

Open problems

After all that introduction, there's also plenty left to solve if you think about world models. For example, a character can come back into view with details that have drifted, so we need better memory. Users need more control over what each grey box becomes. In the longer term, we need more control, and state transitions are also very important. seg 1977–1982

On the right-hand side is one of my favorites: evaluation. One of our agents actually passed a walkability check 〔?〕: you put a box-like object there, and it tells you that you can walk up the stairs, which is definitely not correct. So we really need tests that capture what people actually mean by a world that works. seg 1983–1991

Closing

So back to the question we started with. Agents are changing what a 3D company should build. They can do more of the work themselves, and they can put better models to work too. For us, that means helping them build worlds with richer detail, clear rules, and changes that last. There's a lot left to build, and that's what makes this journey very exciting. seg 1992–1997

I started with a question about what agents mean for a 3D company; let me leave you with a question about what they mean for you. What have you always wanted to build, but never had the team or the tools to attempt? Maybe it's a game you have been thinking about for years. Maybe it's a strange little world that only makes sense to you. Try it again. EdenLive is open source, and Tripo is there for your agent to use and for you to use. And there are still plenty of hard problems for us to solve together. If you want to work on those problems with us, come and find us. The world you have been imagining — you should build it. My name's Gavin, I'm from VAST. Let's build something fun. Thank you. seg 1998–2007
