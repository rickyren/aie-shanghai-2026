Post-Training at the Frontier: Teaching Open Models to Search and Browse the Web

Alex Triplett, Ryan Lee, David Li · You.com · 2026-11-05 主会场 · 10:52–11:09 · 场次 d1m05

You.com 把自己定位为 AI agent 和模型公司的搜索基础设施，并用与 NVIDIA/CoreWeave 后训练 Nemotron 的案例说明：用其 web graph 和搜索 API 生成经难度过滤的小规模可验证 RL 数据，就能让开源小模型的网页研究能力显著提升。

演讲骨架

  1. You.com 是为 AI agent 和 LLM 构建的网页搜索引擎，通过 Search、Contents、Answers、Research 等 API 以及授权的结构化数据提供，主打企业级规模、零数据留存和与模型公司的合作。
  2. 亚太负责人强调在亚洲设立总部和团队，服务中国模型公司与互联网大厂出海及全球实时信息接入，覆盖性能到成本的整条帕累托曲线。
  3. 案例：与 NVIDIA、CoreWeave 合作后训练开源 30B Nemotron，用 You.com 的 web graph 取中等热度网页生成难题，经难度过滤后做 SFT + RLVR。
  4. 结果与流程：很小的数据集和短时间训练即带来 BrowseComp 明显提升，且模型学会验证、减少工具调用；总结为强工具、真实网页造题、难度过滤、SFT、GRPO、度量准确率与效率的通用配方。

讲者提出的框架

  • 搜索型 agent 后训练通用配方：强工具起步，从真实网页造题，按难度过滤，用自有轨迹做拒绝采样 SFT 再 GRPO，最后同时度量准确率与效率。
  • RL 数据按热度与通过率筛选：取中等热度网页以避开模型已记住的内容和长尾垃圾，用 pass@8 过滤掉全对或全错的题，保留 1 到 7 次通过的题。

推出 / 提供

  • You.com Search / Contents / Answers / Research API：为 agent 和 LLM 提供全网搜索、整页内容抓取、多轮扇出研究，以及 World Bank、S&P、Polymarket 等授权结构化数据。
  • 模型公司搜索合作与后训练数据服务：为模型预训练、后训练和推理时联网搜索提供数据与搜索，案例为联合后训练 Nemotron。

非共识

  • 搜索 agent 后训练中，RL 数据集的质量比工具或环境更重要，小而精的数据集即可达到比其大几倍的数据集相近的收益。
    这个RL data set在你做后训练的时候，其实比tooling或者environment更重要。
  • 只奖励答案正确性也会带来效率提升的副作用，模型学会验证后不再继续无谓搜索。
    So you're actually seeing that you can gain both performance and efficiency when you're doing RL.

信号

  • 市场格局 / 规律搜索供应商把自己定位成模型公司的搜索伙伴，向上延伸到为开源模型做搜索后训练，并在亚洲设点服务中国模型公司和出海需求。
  • 数据信号RL 数据直接由搜索供应商的 web graph 与网页内容合成问答，辅以开源数据子集并做去污染，不依赖人工标注。
  • 关注的指标同时追踪 BrowseComp 准确率与工具调用数和 token 消耗，既要更准也要更省。
  • 市场格局 / 规律称机器搜索量已超过人类搜索，搜索被重新定义为面向 agent 的基础设施。

Case study：与 NVIDIA、CoreWeave 合作后训练 Nemotron

我现在想讲一下我们跟NVIDIA和CoreWeave合作的一个case study。我们跟NVIDIA一起合作，就是怎么用一个open-weight的30B的模型，让它跟一个solid的〔?〕模型在web browsing和research上有一样的performance。为什么用这种open-weight的model？是因为它们特别token efficient，而且要是你在data center里面用，也特别inference efficient。

seg 970–973

大概看一下这个stack。我们用了几个trainer〔?〕：第一个是NVIDIA做SFT，用他们的NeMo Gym在里面做RL，然后在CoreWeave的platform上也做RL。但最重要的其实是你的RL data set。这个RL data set在你做后训练的时候，其实比tooling或者environment更重要。为什么？因为要是这个模型遇到有足够难度的问题，它可以在后训练的时候自己做些学习，然后improve它的overall performance。

seg 974–980

看一下这个base model。这个base model在一个benchmark上，我们用了BrowseComp的benchmark——BrowseComp大概是1200多个multi-hop的browse web research的问题——做了一些evaluation。这个base model在BrowseComp上大概是37分，平均每个问题是168个tool call，然后用了差不多3 to 5 million，300万到500万的token，确实是很多的。

seg 981–987

我们也看到，稍微小一点的、不是特别强的model会有很多不一样的failure mode。在做这些特别复杂的research问题的时候，这些模型可能会有一种叫death loop的东西：this is when a model will search over and over and over again without finding the right information. 也会有weak tool use，因为这个模型不知道怎么用互联网搜索、不知道怎么用web browsing，它见到这些特别复杂的问题的时候，it doesn't know how to react properly. 最后，有时候这个模型可能也会查到对的答案，但是因为它自己不知道对的答案是怎么来的，它可能会再去做更多搜索、做更多tool call、用更多token，这是特别inefficient的。

seg 988–995

构建 RL data set

刚才大概说了一下，做RL data set其实是做后训练的时候最重要的一个部分。为什么？因为你看一个模型的pre-training corpus，它应该差不多把互联网上全部的token都有了，它自己的internal knowledge里有很多这种facts。所以你要找一些特别复杂的、不会在模型knowledge里面的问题来做后训练，这样它不会直接从它的weight里面拿一个答案出来，而是会学习怎么用这些网络搜索的tool、网络browsing的tool，做更多reasoning。

seg 996–1001

因为You.com有自己的互联网搜索API，我们其实有一个东西叫web graph。这个web graph你可以想成 it's just basically a cyclic graph〔?〕 of all of the web pages, hundreds of billions of web pages in the world, and then there's backlinks and links, so there's back edges and edges linking every web page. 这样我们可以自己算一些像Google或者Bing的PageRank这样的分数，或者agentic relevance的分数。

seg 1002–1008

我们其实是看哪些网站是不是特别popular的，就是medium popularity的网站。为什么？因为这些网站的信息就可能不在这个模型的weight里面。要是你看特别特别popular的网站，这些网站很多字其实是没用的，像Google的homepage，或者Vanta的SOC 2 logo的URL，因为特别多网站都有它们。要是你看特别rare或者unpopular的网站，很多字是long tail或者spam，所以这些也不是特别relevant。你要看中间popularity的网站来做这个data set。

seg 1009–1014

拿到这些网站之后——我们用了差不多几千个——你可以用一个模型在它的page content里面做一些Q&A pair，这样就可以有一个特别复杂的RL data set来让这个模型做后训练。我们拿我们自己的proprietary data，再加了一些open source的data，像OpenSeeker或者ASearcher的subset，来做这个RL data set。然后我们再做了另外一个步骤，就是decontamination：你做RL的时候，不想你的data set里面有这些RL benchmark的答案，所以要做decontamination。

seg 1015–1020

做完decontamination之后，我们用这个base model Nemotron 3.5 Lightning做一个pass@8的sweep〔?〕，就是先给它做8个run。为什么我们会做pass@8？因为你不想在RL data set里面用太复杂或者太简单的问题。要是一个问题8 out of 8 times the model can answer the question，那这个问题其实是没用的，这个模型都已经会了。要是这个问题太复杂，0 out of 8 pass rate，那说明the model may not be capable enough to answer these questions. So those are discarded as well. 所以留下来的问题就是pass between 1 and 7，这些就可以用来当你的RL data set。

seg 1021–1031

结果

我想今天说的最重要的就是：你可以用小的data set来做一些很大的performance gains。要是你跟另外一些data set比，像WebSailor或者OpenSeeker和ASearcher，它们比我们的大几倍，但是我们做到的performance gain其实跟它们差不多，用的是一个特别小的data set。我们一共有差不多5000个SFT trace、1500个RL task，然后一共只要花8个小时来做RL、做后训练。这1500个RL task都是用我们的web graph和搜索API来做的，所以其实没有另外一些RL method那么复杂。因为有时候做RL你可能要用一些human来做这些task，或者做RLHF；这里全部是RLVR。所以从时间角度来说，其实挺简单的。

seg 1032–1039

最后结果是怎么样？要是你记得，base model的performance是37分，做完RL、做完后训练〔?〕，我们的performance已经变成45.45分，在BrowseComp这个benchmark上。total是8点几、8.5分的performance gain，但其实是23%——22%的relative gain。

seg 1040–1045

我们还看到一个很interesting的behavior。你做后训练的时候，其实只是看这个模型拿的答案是不是对的，you don't reward the model for efficiency. But because the model learns more about how to use the relevant tools and your RL environment, and it also learns how to solve the tasks that you give the model, it actually becomes more efficient as a side effect. So you're actually seeing that you can gain both performance and efficiency when you're doing RL. 最后来看，SFT可能有3分的gain，后来5点几分的gain是在RL这部分。

seg 1046–1049

To make it more concrete, I can give an example here. 这个例子是BrowseComp里一个特别复杂的问题：一个公司是在2013年和2023年之间被收购的，这个CEO在收购的时候是从一个加州大学毕业的，然后问他在卖这个light bulb的时候开的是哪种车〔?〕。这个问题从模型角度来说不是个特别简单的问题。It needs multiple steps, multiple hops, and quite a long amount of reasoning to answer the question.

seg 1050–1055

So if you look at the model，看这个后训练之前最基本的model来回答这个task，它用了313个tool call，一共用了150个搜索、118个web fetch，然后用了1.3 million tokens，而且它最后的答案还是错的。但是你看后训练之后这个模型的behavior：一共只用了7个tool call，3个互联网搜索、1个web fetch，然后只用了7万多个token。为什么这个模型后来会这么好？是因为这个模型第一次就拿到答案了，然后它做了verification。它学到了：要是你拿到答案，你可以做一些verification，不用再continuously搜索。所以这是一个very interesting case of model behavior improving after post-training.

seg 1056–1064

通用流程

我现在只有40几秒，所以很快说一下，这可能是最重要的部分。The generalized process for post-training or RL: one, start with strong tools — in this case we started with strong search, but you want to start with a strong tool for anything that you're doing. Build questions with representative datasets, or in this case build questions from the real web. Filter by difficulty; that's very important for GRPO and RLVR. You can do SFT on your own traces — so rejection sampling, SFT, and then GRPO. And then finally, measure accuracy and efficiency; you can do a binary rubric or a multi-step rubric.
