Reinforcement Learning at Scale on Agent Substrate: Orchestrating Millions of Sandboxes

Tinsley Shi（诗婷） · Google · 2026-11-05 主会场 · 17:13–17:24 · 场次 d1m19 · 偏宣传

Google Agent Infra 推广其开源的 RL 后训练沙箱基础设施（Kubernetes 上的 agent sandbox，下一代为 agent substrate），主张 RL 的瓶颈已从算力转到沙箱调度，并通过预热池、镜像缓存、控制面和快照优化解决高并发、数据污染与空闲浪费。

演讲骨架

  1. 前沿实验室的 RL 后训练规模越来越大，瓶颈已转到如何持续调度海量沙箱。
  2. 大规模 RL 带来并发、镜像拉取、数据质量被基础设施故障污染以及沙箱大量空闲浪费 GPU 等问题。
  3. Google 的开源方案（基于 Kubernetes 的 agent sandbox）用预热池、镜像放置与缓存、控制面优化、精简网络 identity 实现百万并发、亚秒级首条指令。
  4. 下一代 agent substrate 用快照恢复和新的数据平面进一步提升密度、降低成本。

讲者提出的框架

  • RL 沙箱调度的四层架构：上层极简 Python SDK 让研究员只写算法/数据，下层处理镜像放置缓存、控制面和网络 identity 的高吞吐调度。

推出 / 提供

  • Agent Sandbox（开源）：为 RL 后训练设计的 Kubernetes 沙箱调度系统，支持预热池、镜像缓存、GPU 与 TPU 验证。
  • Agent substrate（下一代）：基于快照恢复和新数据平面的亚秒级起停，提高密度、降低成本。

非共识

  • RL 训练的数据质量问题有一部分来自沙箱基础设施而非模型或任务本身。
    这样你整体的训练数据其实就被污染了：它没有正确地评定任务是否真的完成，而是因为基础设施的问题被判定为没有完成。

信号

  • 数据信号RL 训练用的数据以海量打包好的代码仓库/SWE 类镜像形式存在，数量庞大且单个镜像很大，成为调度和存储压力。
  • 市场格局 / 规律前沿实验室普遍做 RL 后训练且规模不断扩大，基础设施厂商把 RL 沙箱调度当作新的服务对象，并以开源方式吸引国内实验室和创业者。
  • 关注的指标关注沙箱并发规模、首条指令延迟、预热装填时间、节点密度，以及沙箱真实工作时间占比。

大家下午好。我是来自谷歌 Agent Infra 的产品经理，我叫诗婷（Tinsley Shi）。今天我们来谈一下强化学习——强化学习训练应该是个非常热门的话题。有多少同学目前在做强化学习，或者试图学习强化学习的？有的话举个手好吗？还挺多的。那我感觉我今天可能要给大家上点难度，有点干货。我们开始。 seg 2071–2082

首先，为什么我今天讲的是百万量级？如果大家去看强化学习对模型训练有多重要，你会看到比如 Kimi K3、DeepSeek V4、Flash、GLM。强化学习的后训练在比如 coding 这类特定任务上，对模型效果的提升是巨大的，而且持续增长。今天所有这些前沿实验室都在做强化学习训练，并且规模越来越大。但是当我们跟研究员聊的时候，他们发现了一个很大的问题：我很大程度上想持续地训练，但是会 block 在基础设施上。这个基础设施，其实就是如何持续调度大规模的沙箱。 seg 2083–2091

我们从最简单的一个 RL loop 讲起。比方说我们要做一个训练，这个 task 是让 AI 输出一个 hello world，任务就叫“输出 hello world，用 python 写”。一般来说我们会给它一个镜像，镜像里面打包了一个基础的 python 库，然后 agent 在里面写。首先你要在沙箱里准备好这个镜像。因为它需要执行工作，有一些 tool call〔?〕，不再是单纯的对话，所以你就需要把这些不可信的、执行的 code 放在 sandbox 里。也就是说，每一次 LLM 思考完了以后，都会放到 sandbox 里去执行。执行完了之后，你会去看它写的到底是不是 hello world，还是说“hello，今天的 AI Engineer Shanghai”〔?〕，对吧？结束之后我们会进行一个评分，可以是 LLM 作为 judge 来评分，判断这个是对的还是错的。这就是每次 RL 强化学习 rollout 的大体流程。你会发现沙箱在每一步、每一条轨迹上都必须执行。 seg 2092–2106

但是在实践中，你会发现出现了很多问题。首先，我刚才说的只是一个非常简单的过程，实际上前沿实验室对一个任务通常会让 LLM 产生比如 16 个 rollout，而且每个任务的难度都指数级上升。比如小米有一个实时直播的 RL dashboard，上面显示单个任务就要执行 1000 个 task，并且每个 task 都要做 16 次 rollout。也就是说，单次沙箱的起停就要满足 16000 次。这在前沿实验室是一个非常常见的数字。但是对于普通的 agent serving 和 inference，你很少能达到这么大的并发量级。这就对传统的容器 infra 产生巨大的挑战，因为它没见过这么大的吞吐量。 seg 2107–2116

第二点，随着 code agent 这些 task 变得越来越难，今天这些前沿实验室训练时拿的数据，经常会打包成一个镜像，比如把一个 GitHub 仓库打包成镜像，像 SWE-bench，这些镜像还安装了各种依赖包。你会发现它们的 size 非常大，基本上每一个镜像都超过一个 GB，几个 GB 不等。而且他们训练的数据规模超大，如果你去看 Kimi K3 的技术报告，他们训练了超过 150 万个镜像。在这样大的体量下，我们的网络存储怎么把这些镜像拉取、解析、快速执行，又不影响整体的训练流程，是个非常大的挑战。 seg 2117–2124

第三点其实影响到数据质量。研究员经常说，在传统情况下，我们的沙箱大概要等几分钟，比如把镜像准备好等等。但在实际训练过程中，这些情况有可能被 reward 评估为这个任务没有完成，比如内存溢出或者超时等等。这样你整体的训练数据其实就被污染了：它没有正确地评定任务是否真的完成，而是因为基础设施的问题被判定为没有完成。这会影响到最终模型的权重输出。 seg 2125–2131

还有一个更大的问题：我们去看这些沙箱的过程中发现，80% 的时间它都是空的，只有 15% 的时间在真正工作。80% 的时间是在等模型产生，比如我要写什么 code，或者下一步的计划，等它的思维链思考。这个过程中大量的沙箱是空闲的。对于一个前沿实验室来说，要适应每天百万量级的轨迹，这对资源是极大的浪费。而且这些等待的过程也使得非常昂贵的 GPU，可能是百万美元的 GPU 集群，就在那儿等几分钟，这其实是巨大的浪费。 seg 2132–2137

我们的方案：Google 开源项目

我们今天聊的是一个 Google 的开源项目，是我们专门为强化学习后训练做的沙箱基础设施，如何能够高效地调度。我们给的数字是：第一，可以做到百万量级的同时并发，稳定持续地跑了 8 天，没有崩，没有产生一个沙箱错误。第二，首次指令的时间能够达到一秒以内，包括 P99 延迟也在一秒以内。第三，我们用预热池的方式装填沙箱，装填这 100 万个沙箱只需要 12 分钟，并且这个测试是通过 30 万个大规模镜像完成的，它们都是公开的，比如 SWE-bench，以及市面上大家有的数据集。这是我们今天能够做到的情况，理论上应该能满足大部分的场景。如果你不是超大规模的实验室，我觉得这是你今天就可以用的 open source 的东西。 seg 2138–2149

我们讲讲主要做了什么、遇到了哪些瓶颈、怎么解决的。我们的架构大概分成四层。第一层，研究员只想关心我的数据集是什么、我要用哪个算法、哪个 policy，所以上层是一个非常简单的 python SDK，你只需要写你的业务代码就可以，和底层 infra 调度没有任何关系。第二层是我们的后端，我们做了大量的工作，比如今天 30 万个镜像要部署到 4000 个 CPU 节点上，这个过程是怎么做的。我们通过一些动态的算法，使镜像放置在离节点更近的位置，通过 cache 的方式让镜像的拉取和解析更快。第三点，在传统的过程中，控制平面的 infra 经常会崩溃或者超时，因为它本身没有为这样前所未有的规模设计过。所以我们在控制平面上也做了大量的优化，使它能够承载高吞吐量的情形。 seg 2150–2159

我想谈一下遇到的一些瓶颈。比如刚才提到的 API server，我们在控制器、控制平面上做了大量的调整。第二个问题是网络的 identity。因为你是指数级上升的，比如一个批量处理的任务 X 乘以 16，量非常大，很容易使网络的 identity 也指数级上升，大部分情况下你会遇到各种各样的问题。所以我们对网络 identity 也进行了简化，使得你产生 1 万个沙箱，最多也只需要 512 个 identity，大幅降低了整体集群的压力。第三是镜像的分发，超大规模的镜像分发在每一个场景下都会产生挑战。 seg 2160–2166

最终我们实现的是，还能提升非常高的密度：一个节点上你能够部署 60 个沙箱，这对超大规模训练来说非常重要，能提升你的利用率。并且我们这个沙箱服务不止在 GPU 上验证，也在我们的 TPU 上做了验证：我们训练了 Qwen 的 379B〔?〕大模型，同时验证了它能够在一秒内完成所有的调度和首次指令执行。 seg 2167–2170

下一代：agent substrate

整体来说，我们还遇到了一些新问题。比如在这个大规模下，有些场景需要一些初始化脚本，你如何去做这件事，在预热池下已经有一些瓶颈；并且如何进一步提高沙箱的密度、降低资源成本。这也是我们下一代的架构，我们称之为 agent substrate，agent 基座。它能够通过 snapshot 快照和快速起停的方式，使你每一步的优化都通过快照恢复，以亚秒级的方式完成，这能大幅提升沙箱的密度、降低成本，使得空闲时间都被优化掉。最后一点是我们在控制平面上遇到的瓶颈，我们会用一个新的数据平面来突破吞吐的瓶颈。这也是我们的一个 demo，可以实现大规模的起停，并且是亚秒级的。 seg 2173–2179

时间有限，主要有三个 takeaway。首先，如果你是一个大规模实验室，在百万量级，或者是比它更小的实验，大部分情况下，我们目前的方案，叫 agent sandbox，基于 Kubernetes，已经能够满足你的需求。其次，我们正在开发下一代的架构，使整体的成本优化得更好，预计这个月底会发布一个项目。最后一点，我们所有的项目都是开源的，我们也非常希望能和国内的实验室或者创业者们一起探讨，欢迎大家在我们的开源社区 share feedback，谢谢大家。 seg 2180–2184
